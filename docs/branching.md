# ブランチ戦略とリリース

## ブランチ

| ブランチ | 役割 | 保護 |
|---|---|---|
| `main` | **リリース線。** ここにあるものが公開される | あり |
| `develop` | **統合線。** 既定ブランチ。作業ブランチはここから切る | あり |
| `release/vX.Y.Z` | **リリース準備線。** `develop` から切り、`main` へ PR。**バージョンを上げる場所** | なし |
| `<type>/<slug>` | 作業ブランチ。`develop` から切り `develop` へ PR | なし |

作業ブランチの `<type>` は Conventional Commits の型に合わせる
（`feat` / `fix` / `docs` / `chore` / `experiment` など）。

`release/` だけは型ではない。**バージョンを名乗るブランチ**であり、
名前の形は `release/vX.Y.Z` に固定されている（決定4-7）。

## 手順

```
Issue を立てる
  ↓
develop から作業ブランチを切る
  ↓
実装する
  ↓
develop へ PR を出す
  ↓
Strict Lead Engineer として自己レビューし、gh pr review で PR に投稿する
  ↓
指摘を修正し、対応をコメントで記録する
  ↓
develop へマージ
```

## リリース

**`main` へ直接向かう線は無い。** `develop` からリリース準備線を切り、そこを経由する。

```
develop
  ↓  release/vX.Y.Z を切る
release/vX.Y.Z
  ↓  バージョンを上げる（package.json と文書）
  ↓  main へ PR。自己レビューして投稿する
main
  ↓  マージ後にタグを打つ（vX.Y.Z）
  ↓
release/vX.Y.Z → develop へ PR   ← **戻しを忘れない**
```

### なぜ挟むのか

**バージョンを上げるコミットの置き場を作るため**である（決定4-7）。

`develop` → `main` を直接つなぐと、バージョンを上げるコミットは `develop` に入る。
`develop` は統合線なので、**まだリリースしていないものにリリース済みの番号が付く。**

### 戻しを忘れない

`release/vX.Y.Z` → `main` のあと、**`release/vX.Y.Z` → `develop`** の PR を出す。

飛ばすと、バージョンを上げたコミットが `develop` に無いまま次の作業が始まり、
**次のリリースで `develop` と `main` が同じ番号を名乗る。**

**これは検査していない。** 出し忘れても壊れるものが即座には無く、
機械が「戻しの PR がまだ無い」と「これから出す」を区別できないためである。

### CI が拒否するもの

`main` への PR は **`release/vX.Y.Z` からのみ**通る。
`develop` から直接出しても、作業ブランチから出しても落ちる。
`release/foo` や `release/v0.1` のように**形が違う名前も落ちる。**

branch protection は「PR を経由すること」しか要求せず head を制約しないため、
`branch-flow` ジョブで塞いでいる。

**前リリース版（`release/v0.1.0-rc.1` など）は通らない。** 必要になったら形を決め直す。

## 保護は二層ある

### 1. pre-push フック（手元）

`.githooks/pre-push` が `main` と `develop` への直接 push を拒否する。
`pnpm install` の `prepare` が `core.hooksPath` を設定するまで有効にならない。

**これは手元だけの防御である。** clone した別環境や GitHub の Web UI からの操作は止められない。

### 2. GitHub の branch protection（サーバ）

`main` と `develop` の両方に設定してある。

| 項目 | 設定 |
|---|---|
| PR 経由の変更のみ | 必須 |
| 必要な承認数 | 0（開発者が1人のため。自分の PR は承認できない） |
| 必要なステータスチェック | `verify`（CI）。`main` は `branch-flow` も |
| 管理者にも適用 | **する**（`enforce_admins: true`） |
| force push / 削除 | 禁止 |

**管理者にも適用している。** リポジトリ所有者であっても直接 push できない。
このプロジェクトは「規則は文書ではなく機械で強制する」という方針を取っており
（[agent-failures.md](./agent-failures.md) の教訓3）、所有者を例外にすると
その方針が成立しないため。

承認数を 0 にしているのは、GitHub が自分の PR への承認を許さないためである。
**PR を経由すること自体は強制されている。**

## 迂回する必要がある場合

手元のフックだけなら次で迂回できる。

```bash
SASHIGANE_ALLOW_PROTECTED_PUSH=1 git push
```

ただし**サーバ側の保護は迂回できない。**
どうしても必要な場合は branch protection を一時的に外すことになるが、
それは意図的な操作であり、**理由を [agent-failures.md](./agent-failures.md) に記録する。**

## バージョン管理

**決定4-6 で決めた**（[decisions.md](./decisions.md)、
[Issue #93](https://github.com/shun2218-dev/sashigane/issues/93)）。

| | |
|---|---|
| タグ形式 | `v0.1.0`。**リポジトリに1本**。パッケージごとには打たない |
| 揃えるか独立させるか | **揃える。** 依存解決の主体がいないので、組み合わせを作らせない |
| バージョンが指すもの | **配信スナップショットの識別子** |
| 出所 | `packages/tokens/package.json` の `version` **だけ**。原則4 によりトークン層の中に置く |
| 破壊的変更 | **セマンティックまたは差し込み口の名前が消えるか、意味が変わること。** 契約は名前表（`tokens.layers.json`）。`packages/tokens` の TS の export は契約ではない（配布されるのは生成物である） |

生成物のヘッダにバージョンが入り、規則の在り処はリリース済みならタグに固定される。

### 上げる場所は release ブランチだけ

**`develop` でも作業ブランチでも上げない**（決定4-7）。
`release/vX.Y.Z` を切ったあと、そのブランチの中で上げる。

| 上げる先 | |
|---|---|
| `packages/tokens/package.json` の `version` | **出所はここ1つ**（決定4-6） |
| 文書のバージョンへの言及 | 「まだ打っていない」「`0.0.0`（未リリース）」など、番号や状態を書いた箇所 |

**ブランチ名がそのバージョンを名乗る**ので、`release/v0.1.0` の中の `version` は
`0.1.0` である。**食い違ったまま `main` へ入れない。**

### 最初のタグ — `v0.1.0`（2026-09-05）

条件は「**レジストリ配信が動いていること**」だった。**揃った。**

- ドキュメントサイトが配信先として立っている
- **本番の URL に対して `shadcn` CLI を3つの深さとも通した。**
  落ちた木はコンパイルできる（[Issue #101](https://github.com/shun2218-dev/sashigane/issues/101)）

`0.x` のあいだは**破壊的変更でマイナーを上げる**（決定4-6）。
`1.0` の条件は、レジストリ配信が動いていて、**コンポーネントの実需要が固まっている**ことである。

**タグは `main` へマージしたあとに打つ。** 打つ先が無い状態で番号だけ進めない。

## 経緯

このブランチ戦略は最初から存在したものではない。
エージェントが「main への直接 push は禁止」という指示をブランチ戦略の指定と誤読し、
単一トランクのまま4 PR 進めた。詳細は [agent-failures.md](./agent-failures.md) を参照。
