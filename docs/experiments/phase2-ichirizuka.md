# Phase 2: ichirizuka にトークンのみを導入する

実施日: 2026-08-24
関連: [Issue #25](https://github.com/shun2218-dev/sashigane/issues/25) /
[ichirizuka#34](https://github.com/shun2218-dev/ichirizuka/issues/34) /
[decisions.md 決定5-10](../decisions.md)

## なぜやったか

**コンポーネントを1つも書かないうちに、トークン層だけを実プロジェクトへ導入する。**
原則4（依存は一方通行）と原則6（トークンのみのインストールが動く）の実証であり、
**ここで設計の穴を出すことが目的**である。

ichirizuka は `dependencies` が `next` / `react` / `react-dom` の3つだけという規約を持つ。
**これを破らずに導入できることが要件そのもの。**

## やったこと

生成した `tokens.css` を ichirizuka にファイルとしてコミットし（レジストリ方式の先取り）、
`app/globals.css` の `:root` にある14変数を sashigane のセマンティックへ写像した。

**変数名は変えていない。** セレクタ側の `var()` 参照112箇所はそのまま動く。
`:root` が「ichirizuka の役割名 → sashigane のセマンティック」の対応表として働く。

primary は従来の `--teal`（`#1f7a78`）を入力にした。パレットの警告は出ていない。

## 結果: 依存は増えなかった

`dependencies` は3つのまま。`npm run build` が通り、実データで描画されることを確認した。
**トークン層が React 非依存であることは実証された。**

以下はすべて、そのうえで出た穴である。

## 出た穴

### 穴1: 暗色モードを拒否できなかった — **トークン層を直した（決定5-10）**

`tokens.css` は `@media (prefers-color-scheme: dark)` を無条件で持つ。
ichirizuka は紙を模した**明色専用**のデザインで、暗色の設計を持たない。

OS が暗色設定の環境で開くと、**写像した10変数だけが暗色へ切り替わり、
生値のまま残っている15箇所と混ざって壊れた。** 実際にブラウザで観測した。

`[data-theme="dark"]` はあったが `[data-theme="light"]` が無く、**固定する手段が無かった。**

**トークン層を入れただけで、利用側が選んでいない見た目に飛ぶ。**
これは原則6 の「トークンのみのインストールが実際に動く」に反するため、
アプリ側で打ち消さず**トークン層を直した**（決定5-10）。
`[data-theme="light"]` / `[data-theme="dark"]` を出し、どちらにも `color-scheme` を伴わせた。

**ichirizuka 側で `data-theme="light"` を設定するところまでで、この穴は塞がる。**
適用は [ichirizuka#34](https://github.com/shun2218-dev/ichirizuka/issues/34) の PR。

### 穴2: 面の重なり方が逆

```
ichirizuka  paper L=0.940 → card L=0.978   カードが紙より 明るい
sashigane   bg-page L=0.970 → bg-surface L=0.883   面が紙より 暗い
```

sashigane は明色モードで `bg-page`(50) → `bg-surface`(100) → `bg-inset`(200) と、
**重ねるほど中間へ寄る**モデルを持つ（暗色モードでは逆向きに、やはり中間へ寄る）。

ichirizuka は逆で、**地を少し沈めてカードを白く浮かせる。** 紙に印刷された記録帳の見立てである。
どちらも実在する組み方だが、**現在のセマンティックでは後者を表現できない。**

### 穴3: 意図的に弱い注記が作れない

`--faint`（単位、最も弱い注記）は現在 2.16:1。sashigane の `text-faint` は 4.74:1。

原則5 は WCAG 適合を「そうなっているもの」にすると宣言しており、
**保証を下回る役割を構造的に持てない。**

ichirizuka の `--faint` は「km」「本」といった単位に使われている。
数値本体が `--ink` で十分なコントラストを持ち、単位は文脈から読める、という設計判断である。

**これは「アクセシビリティを守るシステムが、意図的な弱さを許さない」という衝突であり、
どちらが正しいかは自明ではない。** 現時点では sashigane の側を変えず、事実として記録する。

### 穴4: 中性色の色相を primary と独立に選べない — **穴ではなかった**

> **2026-08-24 追記。** 測ったところ、この色相差は**知覚できない**（ΔE 0.025）。
> 決定5-6 の根拠の記述は確かに誤っていたが、決定そのものは正しかった。
> [neutral-hue.md](./neutral-hue.md) を参照。
> **数値が大きいことと、それが問題であることは別である。**

決定5-6 により中間色は primary の色相で着色される。
ichirizuka は teal（192.8°）のアクセントに**青寄りのグレー**（ΔH −21〜−54°）を合わせていた。

**「アクセントは青緑、地は青」という組み合わせが表現できない。**
決定5-6 の根拠（観測した4本の中間色はすべて純グレーではなかった）は、
**「色が付いている」ことは示しているが「primary と同じ色相である」ことは示していない。**
pylabo の1件だけがそれを支持していた。

### 穴5: `font-family` のトークンが無い

`--display` / `--body` / `--mono` に対応物が無い。
sashigane が持つのは `font-size` と `line-height` だけである。

観測した4本すべてが3系統（見出し / 本文 / 数値）を持っており、**実需要は明確にある。**

### 穴6: 密度の軸が無い

`--gap: 28px`（ブレークポイントで 22px に変わる）に対応物が無い。
spacing スケールは `…24, 32…` で 28 を持たない。

問題は値そのものではなく、**「画面全体の密度を1つの変数で動かす」という軸が
トークンの語彙に無い**ことである（[roles.md](../roles.md) の「密度」節）。

### 穴7: JS から値を読めない

`lib/format.ts` の `effortColor()` は心拍を色へ写す関数で、
**RGB 三つ組を直書きして線形補間している。**

```
[0, [31, 122, 120]]     ← #1f7a78 = --teal
[0.5, [224, 167, 59]]   ← #e0a73b = --amber
[1, [201, 67, 107]]     ← #c9436b = --magenta
```

`app/layout.tsx` の `themeColor: "#e8eced"` も同じ形で `--paper` と二重管理になっている。

**CSS 変数だけでは、JS が値として色を計算する箇所に届かない。**
`dist/index.d.ts` は**型だけで値を持たない**。
加えて ichirizuka は `dependencies` を増やせないので、import する道もない。

### 穴8: 連続カラースケールが無い

穴7 と同じ箇所だが、別の欠落である。ichirizuka の心拍スケールは
**teal → amber → magenta を連続補間する**（145bpm → 180bpm）。

sashigane の識別色は**離散5色**で、色相環に等間隔（決定5-5）。
「2点/3点を補間する連続スケール」という概念そのものが無い。

### 穴9: 生成物のヘッダが自リポジトリ前提

`tokens.css` の先頭は「規則と根拠は docs/decisions.md を参照」と書いている。
**配布先のリポジトリには `docs/decisions.md` は無い。**

レジストリ方式では生成物が利用側リポジトリに落ちるので、
ヘッダは**落ちた先で意味を成す**必要がある。

## 写像で分かったこと

### `--teal` は6つの役割を兼ねていた

Issue #25 が「最初の試金石」と呼んだ点。実際に数えると6つあった。

| 用途 | 写像先 |
|---|---|
| リンク・`summary` の文字 | `--sg-color-accent` |
| フォーカスリング | `--sg-color-border-focus` |
| 進捗バー・棒グラフの塗り | `--sg-color-accent-mark` |
| 増加方向（`.delta-up`） | `--sg-color-accent` |
| 心拍スケールの下端 | `--sg-color-accent-mark` |
| easy の識別色 | `--sg-color-accent-mark` |

**「文字か、塗りか」で割れた**（決定5-7）。ichirizuka 側は `--teal` / `--teal-fill` / `--focus` の
3変数になった。`border-focus` は `accent-mark` と同じ段（400）だが、
**役割として別に用意されている**ので別変数にした。

**残る4役割は割れていない。** 「増加方向」は意味色であって accent ではないが、
sashigane の `success` は別の色相を持つため、割ると見た目が変わる。
ichirizuka では増加が teal であることに意味があり、**意味色と accent の区別を
利用側が持っていない場合にどう写すかは、まだ答えが無い。**

### 穴7 は実害が出た

導入の途中で、**凡例と実データの色が食い違う不整合が実際に生まれた。**
`.legend-ramp` は CSS のグラデーションなので新しい色に変わったが、
`effortColor()` は RGB 直書きなので古いままだった。

JS から値を読む手段が無いため、**3点を手で写して埋めるしかなかった。**
穴が塞がるまで、利用側に二重管理が残り続ける。
