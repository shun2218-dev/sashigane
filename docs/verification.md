# 検証: 生成スケールは実需要を覆えるか

[decisions.md](./decisions.md) で規則から導出したスケールが、
[roles.md](./roles.md) で観測した実需要を表現できるかを機械的に照合した記録。

**このファイルが README の根拠になる。** 設計したシステムが実需要を満たすことの証明であり、
満たさなかった箇所を隠さずに残すことがその信頼性を担保する。

検証日: 2026-08-23
検証方法: 4プロジェクトの CSS / SCSS / Tailwind クラスから
`padding` `margin` `gap` `font-size` `border-radius` `line-height` `letter-spacing`
`transition` `animation` の実値を全抽出し、生成スケールの最近傍と比較した。

覆えなかった箇所は2つに切り分けている。

- **(a) 役割の定義が足りない** → スケールまたは役割を追加する
- **(b) 過去の実装が不統一だっただけ** → 統一すべきものとして記録する

---

## 総括

| 項目 | 結果 |
|---|---|
| spacing（4px 以上） | ✅ 覆える（33/34 = 97%、±20%以内） |
| radius | ✅ 覆える（外れは全て過去の自己矛盾） |
| duration（遷移） | ✅ 覆える |
| font-size | ⚠️ **(a)** 上方向を3段延長した |
| line-height | ⚠️ **(a)** 漸近線を3系統に分けた |
| border-width | ⚠️ **(a)** 独立スケールとして新規定義した |
| ループアニメーション周期 | ⚠️ **(a)** duration とは別軸として新規定義した |
| letter-spacing | ⚠️ **(a)** 駆動要因が2つあることが判明した（2026-08-28 に確定。**第3の群は持たなかった**） |
| font-weight | ⚠️ **(a)** 検証時に見ていなかった。**4段が3本以上で使われている**（2026-08-28、決定1-13） |
| spacing 20 / 40px | ❌ **(b)** |
| font-size 18 / 22px | ❌ **(b)** |
| radius 5 / 10px | ❌ **(b)** |
| duration 120ms | ❌ **(b)** |
| 本文 15px | ❌ **(b)** |
| 負の margin | 📝 トークンではなくコンポーネント欠如の症状 |

**検証によって決定を2つ改訂した（1-3 font-size、1-4 line-height）。
新規に定義したスケールが2つある（border-width、ループ周期）。**

## spacing

| 判定 | 結果 |
|---|---|
| 完全一致 | 10/39 |
| ±20% 以内 | 33/37（0 と負値を除く） |
| **4px 以上に限れば** | **33/34（97%）**。外れは `6px` のみ |

**結論: 4px 以上の余白需要は生成スケールで覆える。**

### (b) 20px / 40px

ランプ形状を決めた際に「20 と 40 が無い」ことを代償として記録していた。
両方とも実測に現れる（20 は i / h / p の3本、40 は h / p）。しかし用途を見ると:

```css
.notice { padding: 18px 20px; }   /* ichirizuka */
.load   { padding: 18px 20px; }
```

**同一宣言内で 18 と 20 が混在している。** これは選ばれた値ではなくノイズ。
40px も pylabo に1箇所のみ。**(b) 不統一と判定。**

### (a) 1〜2px の水平 → border-width スケールを新設

覆えなかったのは `1, 2, 3px`。これは無視できない。

```css
/* ichirizuka: gap:1px + 背景色でヘアライン格子を作る手法。6箇所で使用 */
.hero-side { display: grid; gap: 1px; background: var(--rule); }

/* インラインコードの内側余白 */
.prose code { padding: 1px 5px; }
```

`gap: 1px` は**罫線幅を余白として使っている**ので、spacing ではなく border-width の値。
→ 決定1-7 として新設した。

## font-size — (a) 上限が足りなかった

当初の8段では **±5% 以内が 16/36（44%）**。
上限 39.06px に対し、実測は 48 / 54 / 66 / 74 / 76 / 100 / 132px まで伸びていた。

上方向を ×1.25 で3段延長（48.83 / 61.04 / 76.29）した結果:

| | ±5% 以内 | ±8% 以内 |
|---|---|---|
| 当初8段 | 16/36 (44%) | — |
| 改訂11段 | 19/36 (53%) | **28/36 (78%)** |

残る外れ: `9.5, 18, 22, 34, 36, 54, 100, 132`

| 値 | 判定 |
|---|---|
| 132px | `clamp(76px, 15vw, 132px)` の**可変域の端であって段ではない**。スケールが到達する必要はない |
| 9.5px | 表ヘッダの単位表記。a11y 上そもそも推奨できないサイズ → **(b)** |
| 18 / 22px | 最大の圧力点。18 は3本すべてに出現する → 下記 |

### 18px / 22px は (b) と判定した — ただし記録を残す

- pylabo の `prose h2: 18px / h3: 17px` は1px差。**選択ではなくノイズ**
- holosphere の 18px は Tailwind の `text-lg` 既定値で本人の選択ではない

**(b) と判定するが、上方向比率 1.25 が 16〜25 の帯で粗いことは事実として記録する。**
Phase 2 以降で圧力が再発した場合、この記録を根拠に比率の見直しを検討する。

## line-height — (a) 式が構造的に表現できない領域があった

**当初の式 `1 + 8/size` の漸近線は 1.0 なので、1.0 未満を生成できない。**

```css
/* ichirizuka の大型数値 */
font-size: clamp(76px, 15vw, 132px);  line-height: 0.82;
font-size: 54px;                      line-height: 1;
font-size: 42px;                      line-height: 1;
```

境界条件として「拡張時に下限クランプが必要」と記録していたが、
**必要だったのは下限ではなく上限の突破だった。**

同時に逆方向の問題もあった。pylabo の本文は `line-height: 1.8`、式は 1.5。
長文読解アプリなので行送りが緩いのは正しい。

### 修正: 漸近線だけを可変にする

```
line-height = a + (root ÷ 2) / size     a ∈ { 0.8 display, 1.0 ui, 1.2 prose }
```

係数 `root ÷ 2` は3系統すべてで共通。変えるのは漸近線1つだけ。

| 系統 | 実測との最大誤差 | 検証点 |
|---|---|---|
| display | 5.2% | 132 / 54 / 42 / 38 / 32 / 26px の6点 |
| ui | 6.0% | ichirizuka body（実測 1.6 に対し 1.5） |
| prose | 5.6% | pylabo body（実測 1.8 に対し 1.7） |

**「オーバーライド不可」の原則は維持される。**
コンポーネントが行高の数値を選ぶのではなく、テキスト役割が属する系統を選び、値は導出される。

## radius — 完全に覆えている

| 実測 | 判定 |
|---|---|
| 4, 8, 12, 16, 999 / 9999 | ✅ 一致 |
| 5px, 10px（pylabo） | **(b)** — 下記 |
| 6px（holosphere） | Tailwind の `rounded-md` 既定値。本人の選択ではない |

### pylabo の自己矛盾

pylabo は自前で `--radius-sm: 8 / --radius: 12 / --radius-lg: 16` を定義しながら、
別の場所で `border-radius: 5px` と `10px` を直書きしている。

**トークンを定義しても lint がなければ守られない**ことの実例であり、
原則3を lint で強制するという判断を裏づける観測。

### 傍証

shadcn が `--radius-sm: calc(var(--radius) - 4px)` と減算で導出しているのは、
「radius は減算で導出されるべき」という同じ結論に独立に到達した例。

## duration — (a) ループは別カテゴリだった

| 実測 | 判定 |
|---|---|
| 150ms / 300ms | 141.4 / 282.8 に対し −5.7%。実質一致 |
| 120ms | 100 に対し −16.7% → **(b)** |
| **700ms / 1000ms** | `animation: pulse 1s ease-in-out infinite` |

700 / 1000ms は遷移時間ではなく**無限ループの周期**であり、
「>500ms は鈍重」という知覚上の制約が適用されない。→ 決定1-6 に別スケールを新設した。

新スケール（アンカー 1000ms、比率 √2）は実測を高精度で覆う。

| 実測 | スケール値 | 誤差 |
|---|---|---|
| 700ms | 707.1 | +1.0% |
| 1000ms | 1000 | 完全一致 |

## letter-spacing — (a) 導出規則が想定より複雑だった

当初は「サイズから導出できる従属値」として先送りしていたが、実測13段階が出た。

```
+0.16 / +0.20 / +0.22em   ← すべて text-transform: uppercase のラベル
+0.08 / +0.10em           ← 小さい大文字ラベル
-0.01 / -0.02em           ← 大型数値
```

**駆動要因が2つある。**

- **サイズ** — 大きいほど負
- **大文字化** — 大文字は字面が詰まって見えるため字間を開ける必要がある

サイズだけの関数では表現できない。→ 決定1-9 に記録した。

### 確定させた（2026-08-28）

> [Issue #46](https://github.com/shun2218-dev/sashigane/issues/46)。**再測定した。**

サイズ駆動の側は、`letter-spacing = coefficient × (root / size − 1)` として
係数を逆算すると **2本・3サイズが独立に 0.023〜0.026 に収まった。**

| 出典 | サイズ | 実測 | 逆算した係数 |
|---|---|---|---|
| pylabo `__title`（講座） | 26px | −0.01em | 0.026 |
| pylabo `__title`（ホーム） | 40px | −0.015em | 0.025 |
| ichirizuka `.value` | 76〜132px | −0.02em | 0.023〜0.025 |

大文字化の側も強い。ichirizuka の正の値は**すべて `uppercase` と同時**、
holosphere の `tracking-wide` は **11箇所すべてが `uppercase` と同時**だった。

**当初の集計では見えていなかった第3の群がある。**

```
+0.01 / +0.02 / +0.04 / +0.05 / +0.06em   ← pylabo。11.5〜12.5px・font-weight: 700
                                              大文字化していない小さいラベル
```

サイズ駆動では説明できない（逆算した係数が 0.05〜0.18 とばらつく）。
**太さが効いている可能性があるが、font-weight は未決定**（Issue #53）。
駆動要因を特定できていないので**持たなかった**。決定1-9 に記録した。

## 本文 15px — (b) と判定した

ichirizuka と pylabo が**独立に本文 15px を選んでいた**。

```
ichirizuka  body { font-size: 15px; line-height: 1.6 }
pylabo      body { font-size: 15px; line-height: 1.8 }
```

一致は偶然ではなく好みの表明と見るべきだが、
**rem 出力の根拠（ユーザーのブラウザ設定を尊重する）と真正面から衝突する。**
root を 15px にすることは、ユーザーの既定値を上書きすることに他ならない。

→ **(b) 不統一と判定。root = 16px を貫く。**

なお line-height は 1.6 と 1.8 で割れており、こちらも (b)。
改訂後の式は ichirizuka を ui 系統（1.5）、pylabo を prose 系統（1.7）として
それぞれ 6% 以内で説明できる。
