# エージェントの失敗記録

**ガードレール（lint ルール / CI 検査 / git フック / Skill）を追加するときは、
必ずこのファイルに理由を書いてから追加する。**

ルールが先にあってはならない。失敗が先にあり、ルールはその対処として生まれる。
理由の書かれていないルールは、後から誰も消せなくなる。

## 書き方

各エントリは以下を含む。

- **日付**
- **何が起きたか** — 具体的に。「型エラーが出た」ではなく、どのファイルのどの記述か
- **なぜ起きたか** — エージェント（または人間）が何を前提にしていたか
- **追加したガードレール** — どのファイルの何を変えたか
- **そのガードレールが検出できること / できないこと** — 万能ではないことを明示する

### 2026-08-23 — 設計段階で私（Claude）が誤った生成規則を提示した

**何が起きたか**

spacing スケールの生成規則を「増分は2段ごとに倍化する」と説明し、
その規則から `0, 4, 8, 12, 16, 24, 32, 48, 64, 96` が生成されると述べた。
実際にコードで生成すると `0, 4, 8, 16, 24, 40, 56, 88, 120` になり、一致しなかった。

**なぜ起きたか**

値の並びを先に決め、それを説明する規則を後から言葉で組み立てた。
言葉の上では筋が通っていたが、機械的に実行される形で検算していなかった。
**「規則から値を導く」と主張しながら、実際には値から規則を後付けしていた。**

正しい規則は「`base × 2` 以降、×3/2 と ×4/3 を交互に適用する」。
`3/2 × 4/3 = 2` なので2段ごとに正確に倍になる。

**追加したガードレール**

同日中に**同じ誤りを2度目に起こした**ため（下記）、設計段階のうちに入れた。

- `scripts/metrics/scales.mjs` に期待値の自己検査を置き、
  規則が `docs/decisions.md` の値を生成しない場合は import 時点で例外を投げる

Phase 1 で `packages/tokens` に移した際、`docs/decisions.md` の表との一致も検査に加えた
（`scripts/check-docs-scales.mjs`）。

当初は「表を生成器から自動出力する」つもりだったが、**検査する方式に変えた。**
自動出力にすると、表が生成器の出力そのものになり「証人」として機能しなくなる。
人が書いた値と生成器の出力が独立に一致することに意味がある。

**検出できること / できないこと**

- 検出できる: 規則と値の不一致
- 検出できない: 規則そのものが設計として妥当かどうか。それは人間の判断が要る
- 検出できない: 期待値の側を書き換えて通す行為。
  **期待値は「規則から導いた値」ではなく「規則が正しいことの証人」である。**
  期待値を書き換えて通すのは、規則の誤りを隠すことに等しい

### 2026-08-23 — 同じ誤りを2度目に起こした

**何が起きたか**

上記の修正として書き直した spacing 生成規則が、また違う値を生成した。

```js
v *= ratios[out.length % 2];   // 配列の長さで交互判定 → 位相がずれる
// 生成: [0,4,8,10.67,16,21.33,32,42.67,64,85.33,128]
```

正しくは独立したカウンタで交互判定する。

```js
for (let i = 0; v < 96; i++) { v *= ratios[i % 2]; out.push(v); }
```

**なぜ起きたか**

1度目と同じ構造の誤り。**規則を書いた直後に出力を目視で確認していなかった。**
交互適用の位相という、目で追うと正しく見えて実行すると違う種類の誤りである。

**追加したガードレール**

「Phase 1 で入れる」としていた自己検査を、待たずに設計段階で入れた。
2度起きた時点で、後回しにする判断が誤りだったと判定した。

**検出できること / できないこと**

- 検出できる: 今回と同種の位相ずれ・off-by-one
- 検出できない: 期待値そのものが間違っている場合。期待値は人間が決定文書と照合する必要がある

### 2026-08-23 — 検証の出力を読み違えて、逆の結論を出しかけた

**何が起きたか**

Tailwind v4 の実験で「任意値記法 `p-[20px]` は生成されない」と読んだ。実際には生成されていた。

原因は Tailwind の挙動ではなく**検証手順の側**にあった。
出力を拾う正規表現がエスケープされたクラス名（`.p-\[20px\]`）のバックスラッシュに
マッチしておらず、存在するものを「無い」と表示していた。

同じ実験で、utilities が `@layer` 内にインデントされているために
`^\.p-` が一件もマッチせず、「ユーティリティが生成されていない」と読み違えてもいる。

**なぜ起きたか**

grep でフィルタした結果だけを見て結論を出した。
**フィルタが外れているのか、対象が存在しないのかを区別していなかった。**

この誤りは危険度が高い。生成規則の誤り（過去2件）は期待値検査で機械的に捕まるが、
**「検証手順が壊れていて何も検出していない」状態は、検査が全部緑になる形で現れる。**

**追加したガードレール**

ルールとして残す（下記）。自動検査は書いていない。
検証手順そのものの正しさを機械的に保証する方法は無く、
「壊れた検査は緑になる」という性質上、上位の検査を足しても同じ問題が再発するだけである。

**検出できること / できないこと**

- 検出できない（自動では）。人間の習慣で防ぐしかない種類の誤り

### 2026-08-23 — 規則を書いた同じコミットで、その規則を破った

**何が起きたか**

CLAUDE.md に「**仕様は記憶で書かない。動かして確かめる**」という教訓を書いた。
その**同じコミットで** `.claude/settings.json` に機能しない permission ルールを書いていた。

```json
"Bash(node scripts/metrics/:*)"
```

`:*` は末尾のワイルドカードとして `Bash(node scripts/metrics/ *)` と等価であり、
**末尾スラッシュの直後にスペースを要求する**。
実際のコマンド `node scripts/metrics/generate-scales.mjs` にはマッチしない。
正しくは境界を要求しない `Bash(node scripts/metrics/*)`。

**なぜ起きたか**

`:*` という記法を記憶で書いた。ドキュメントを確認していない。
自己レビューの段階で公式ドキュメントを読み、初めて気づいた。

**この失敗の意味**

これは単なる4件目ではない。

**「教訓を文書に書くこと」が「教訓に従うこと」を保証しないという実例**である。
規則を書いた本人が、同じコミットの中で同じ規則を破った。
しかも破ったことに、規則を書いている最中はまったく気づいていない。

したがって CLAUDE.md は必要だが十分ではない。
**機械的に検査できるものは、文書ではなく検査にしなければならない。**
文書は「機械化できないもの」にだけ使う。

**追加したガードレール**

permission ルールの正しさを機械的に検査する方法は現時点で無く、
「検査できないから文書に書いた」という判断自体は正しかったと考える。

ただし、この失敗から導いた教訓3 を書き足したことで**別の問題が顕在化した。**

CLAUDE.md は agent-failures.md の教訓を**要約して埋め込んでいる**
（参照ではなく要約なのは、リンク先を読むかどうかに依存させないため）。
その代償として二重管理になり、教訓を追加するたびにドリフトする。
**同じ構造の重複問題は既に2度起こしている**（スケール定義の3重複、README との規則重複）。

教訓3「機械的に検査できるものは文書ではなく検査にする」の最初の適用として、
`scripts/check-lessons-sync.mjs` を追加した。
agent-failures.md の教訓の見出しが CLAUDE.md に存在することを検査する。

```bash
pnpm check:lessons
```

わざと1件消して検査が失敗することを確認済み（教訓2 の実践）。

> **この検査は同日中に廃止した。** CLAUDE.md を `@` 参照中心に書き直したことで
> 二重管理そのものが消えたため。理由は上の「廃止したガードレール」を参照。

**この失敗は Phase 1 の設計にも影響する。**
lint・CI 検査を設計するとき、「CLAUDE.md に書いたから守られる」を前提にしない。

**検出できること / できないこと**

- 検出できない。設定ファイルの意味論の誤りは、動かしても静かに失敗する
  （権限プロンプトが出るだけで、エラーにはならない）
- **静かに失敗するものは、失敗したことにすら気づけない。**
  これが4件のうち最も危険な種類である

### 2026-08-23 — 原則1 を破るコミットが、原則1 の検査を書いた同じコミットだった

**何が起きたか**

`packages/tokens` を作った際、生成物 `packages/tokens/tsconfig.tsbuildinfo` を
コミットしていた。原則1「生成物はコミットしない」に反する。

**同じコミットで、生成物の混入を検出する CI 検査を書いていた。**
その検査は既知のパスだけを見ていたため、緑のまま通った。

```yaml
# 書いた検査（既知のパスの列挙）
git ls-files | grep -E '^(packages/[^/]+/dist/|apps/[^/]+/public/r/)'
```

`tsbuildinfo` は列挙に含まれていない。

**なぜ起きたか**

**列挙方式の検査を書いた。** 列挙し忘れたものは黙って通る。
`packages/tokens` の独立性検査（`check-tokens-isolation.mjs`）では
「react を禁止する」ではなく「相対パスと node: 以外を全部禁止する」形にしていたのに、
生成物の検査では同じ判断ができていなかった。**同じ日に、同じ設計判断を片方だけ間違えた。**

**追加したガードレール**

`scripts/check-no-build-output.mjs` を追加し、CI の直書き grep を置き換えた。
拡張子とディレクトリ名の両面から広く拾う。`.gitignore` に `*.tsbuildinfo` も追加した。

陰性対照で発火を確認済み。

**この修正中にもう1件やらかした**

スクリプトのブロックコメントに `packages/*/dist` と書いたところ、
`*/` がコメントを終端して構文エラーになった。実行して初めて気づいた。
**書いたコードは動かすまで動くとみなさない**（教訓1の一般形）。

**検出できること / できないこと**

- 検出できる: 名前から生成物と分かるファイル
- **検出できない: 名前から生成物と分からないファイル。**
  列挙方式より広いだけで、原理的には同じ弱点を持つ

### 2026-08-23 — 仕様に出てきた語を、決定済みと推測した

**何が起きたか**

ブランチ戦略を決めずに4 PR 進めた。`develop` ブランチが存在しない状態で、
`main` に未リリースの実装が積み上がっていた。

Phase 4 でレジストリを公開すると `main` が利用者の install 対象になるため、
**このままだと未完成のものを配布することになっていた。**
バージョン管理の方針も何も決まっておらず、タグは1つも無く `packages/tokens` は `0.0.0` のまま。

**なぜ起きたか**

指示にあった次の一文を、ブランチ戦略の指定として読んだ。

> Issue を立ててから branch を切る。main への直接 push は禁止（pre-push フックで機械的に防ぐ）

**この文が指定しているのは main の保護であって、ブランチ戦略ではない。**
`main` という語が出てきたことをもって単一トランクだと推測し、
「決定済みの事項」として扱って確認を取らなかった。

スケール・命名・比率については毎回選択肢を出して確認を取っていたのに、
開発フローは「動かせない設計原則」のリストに含まれていなかったため、
**決定すべき論点として認識されていなかった。**

**指摘されたときの二次的な誤り**

「なぜ develop が無いのか」と問われた際、最初の回答で
「単一トランクで良いと考えていた理由」を3つ挙げた。
**あれは後から作った理屈である。** 実際にはその判断をした瞬間が無い。

**存在しなかった思考を、あたかも存在したかのように再構成して説明した。**
これは失敗そのものより悪い。原因が隠れ、同じことが再発する。

**追加したガードレール**

- `develop` を作り、`main` をリリース線にした（[branching.md](./branching.md)）
- pre-push フックが `main` と `develop` の両方を守る
- **GitHub の branch protection を `enforce_admins: true` で設定した。**
  フックは手元だけの防御で、clone した別環境や Web UI からの操作を止められない。
  フックを迂回した push が実際にサーバ側で拒否されることを確認済み

ただし**この失敗はガードレールでは防げない類のものである。**
「決めるべきことを決めていない」ことを機械的に検出する方法は無い。
教訓として残す（下記）。

**検出できること / できないこと**

- 検出できない。**未決定の論点が存在することを、検査は知りようがない**
- 唯一の対処は、着手前に「何が未決定か」を明示的に列挙すること

**この対処の最中にもう1件やらかした（手順の記録）**

`branch-flow` が機能することを確かめるため、作業ブランチから `main` へ
検証用の PR を出した。検査は期待どおり失敗したが、**その作業ブランチには
既に生きた PR があり、両者が同じコミットを指していた。**

GitHub のチェック結果はコミット単位で紐づくため、
**検証用 PR の失敗が、生きた PR のチェック欄に混入した。**

生きた PR の base は `develop` で必須チェックは `verify` のみだったためマージ可否には
影響しなかったが、レビューする人間から見れば「失敗している PR」に見える。

→ **検査の陰性対照を PR で取るときは、使い捨てのブランチから出す。**
   生きた PR と同じコミットを指すブランチを使わない。

### 2026-08-24 — 決定文書に書いた判別規則が、自分の生成物に対して破れていた

**何が起きたか**

決定2-3 は「`--sg-{category}-{数字}` はプリミティブ、`--sg-{category}-{単語}` は
セマンティック。**1つの正規表現で層を判別できる**」と書いていた。
Issue #24 でこれを lint にしようとして生成物に当てたところ、**両方向に破れていた。**

| 種別 | 変数 | 何が起きるか |
|---|---|---|
| 偽陽性 | `--sg-text-heading-1` 〜 `-3`、`--sg-color-chart-1` 〜 `-5` | セマンティックなのに参照が禁止される |
| 偽陰性 | `--sg-radius-full` | プリミティブなのに参照が素通りする |

偽陽性の1つは `apps/docs/public/standalone.html` で**実際に使われていた**ため、
素朴に正規表現を入れていれば正しいコードが落ちていた。

**なぜ起きたか**

決定2-3 を書いた時点では、まだ色もタイポグラフィのセマンティックも生成していなかった。
`--sg-space-5` `--sg-blue-500` のような**例として挙げた名前だけ**を見て
「数字で終わるかどうかで判別できる」と一般化した。

その後に決めた命名は、いずれもその一般化に反していた。

- 見出しレベル（決定1-3 と typography のセマンティック）は `heading-1` のように**本質的に数字**
- 系列色（決定5-8）も `chart-1` のように**本質的に数字**
- `--sg-radius-full`（決定1-5）は「段ではない」プリミティブなので**本質的に単語**

**どれも決定2-3 より後に決めたものだが、決定2-3 との整合を誰も確認しなかった。**
決定文書は追記されるたびに整合性が落ちるが、それを検出する仕組みが無かった。

教訓1 は「生成規則を書いたら実行して出力と照合する」だが、
**照合していたのは値だけで、名前の規則は照合していなかった。**

**追加したガードレール**

規則を正規表現から**生成器が出す事実**に置き換えた。名前の形で推測しない。

- `packages/tokens/src/output/layers.ts` — `tokenLayers()` が
  `dist/tokens.layers.json` に「プリミティブ196個 / セマンティック40個」の名前表を出す。
  手書きの一覧ではなく、各 `*Vars()` が出した CSS 行から取り出す（決定2-6）
- `scripts/check-token-usage.mjs` — セマンティックの表に載っている名前**だけ**を許す。
  表に無い `--sg-*` はプリミティブでも打ち間違いでも落ちる（教訓5 の許可リスト方式）
- `packages/tokens/test/layers.test.ts` — 両層が互いに素であること、
  表が `tokens.css` の全変数を覆うこと、上記2件の回帰検査
- 決定2-3 を改訂し、「1つの正規表現で判別できる」という主張を撤回した

**このガードレールが検出できること / できないこと**

- 検出できる — プリミティブ参照、生成器が出さない `--sg-*` 名の参照、
  Tailwind の任意値記法（`p-[20px]` `[mask-type:luminance]` `bg-(--x)`）
- 検出できない — 実行時に組み立てられる class 名、CSS-in-JS、`style` 属性の生値、
  トークンを経由しない別名の生値（`--brand-blue: #3b82f6` など）。
  範囲は検査スクリプト冒頭に列挙してある（教訓5）
- **決定文書と実装のずれ全般は、依然として検出できない。**
  今回見つかったのは「lint にしようとしたから」であって、検査が見つけたのではない

**陰性対照**

Tailwind を使う消費者はまだ存在せず、任意値記法の検出は 0 件になる。
0 件は検査が壊れている場合と区別がつかないため（教訓2）、
**検出器を実行のたびにフィクスチャ16件へ当て、発火しなければ検査自体が落ちる**形にした。
加えて実ファイルへ意図的な違反を入れて発火を確認した（記録は PR）。

### 2026-08-24 — 尺度を1つ選んで閾値と比べただけで「知覚できない」と結論しかけた

**何が起きたか**

決定5-6 の根拠を検証する実験で、中性色の色相を変えたときの知覚差を OKLab 距離で測り、
**すべて 0.034 以下だった。** 決定5-5 が識別可能の目標としている 0.08 を下回るので、
「色相をどう選んでも知覚上区別できない」と結論し、決定文書と実験記録の両方にそう書いた。

自己レビューで実際に色を並べて目視したところ、**0.018 から差が見えた。** 結論が誤っていた。

**なぜ起きたか**

**0.08 は「識別色として見分けられるか」の閾であって、
「隣り合う面の差が見えるか」の閾ではない。** 別の問いに使っていた。

数値が出て、比較対象の定数もリポジトリの中にあったので、
**そのまま比べれば答えになると思い込んだ。** 定数が何を測るために決められたかを確認していない。

さらに悪いことに、**問いの立て方自体がずれていた。**
「差が見えるか」ではなく「色相を primary に揃えると達成できなくなる設計があるか」が
問うべきことだった。目視して初めてそれに気づいた。

**追加したガードレール**

無い。**これは検査で防げる種類の誤りではない。**

- 尺度と閾値の対応が正しいかは、意味の問題であって形の問題ではない
- 「その定数は何を測るために決めたか」を確認する手続きは機械化できない

教訓2「検証は生の出力を見る。フィルタした結果だけで結論を出さない」の範囲を広げて記録する。

### 2026-08-27 — 検査が案内していた逃げ道が、実際には機能していなかった

**何が起きたか**

`scripts/check-token-usage.mjs` は、コメントに書いたプリミティブ名も落とすことを自覚しており、
**逃げ道を文書として案内していた。**

> 説明でプリミティブ名に触れたい場合は `--sg-space-N` のように書く。

**この逃げ道は一度も機能していなかった。** 検出器は `/--sg-[a-z0-9-]+/g` で、
`N` は文字クラスに入らないが**その手前までが一致する。**

```
--sg-space-N       => "--sg-space-"
--sg-font-stack-*  => "--sg-font-stack-"
--sg-space-{段}    => "--sg-space-"
```

取り出された `--sg-space-` は名前表に無いので `unknown` として落ちる。
**書かれているとおりに書くと落ちる。**

[PR #62](https://github.com/shun2218-dev/sashigane/pull/62) で `--sg-font-stack-*` と
コメントに書いて実際に落ち、説明から名前そのものを外して回避した。

**なぜ起きたか**

理由は2つある。

1. **「落ちないこと」の陰性対照が無かった。** 陰性対照は「落ちるべきものが落ちる」側しか
   持っていなかった。案内した書き方が通ることは、一度も確かめていない
2. **手元では緑だった。** 検査対象は `git ls-files`、つまり**追跡下**のファイルである。
   新しく足したファイルは `git add` するまで検査に入らない。
   PR #62 ではコミットして初めて落ちた

2 は教訓2 の別の形である。**「緑だった」ことと「検査されていた」ことは別だった。**

**追加したガードレール**

- **末尾が `-` の一致を名前として扱わない**（`isName`）。`--sg-space-` は宣言として
  ありえない形なので、名前として見ないのが素直である。**切り詰めない**
  （`--sg-space` に丸めても、それはそれで表に無い名前になる）
- **陰性対照に「通るべき書き方」を3件足した。** 直す前は3件とも `unknown` で落ちる。
  同じ壊れ方をすれば検査自体が失敗する
- 出力を「**発火した件数**」と「**落ちなかった件数**」に分けた。混ぜると、
  通るべきものだけが増えても件数が伸びて、対照が効いているように見える
- 検査対象が追跡下に限られる性質を、`check-token-usage.mjs` と
  `check-no-build-output.mjs` の**両方のコメントに書いた**。
  後者ではその性質が目的そのものである（見たいのは「コミットされているか」）

**検出できること / できないこと**

- 検出できる: 逃げ道が壊れること。案内した3つの書き方が落ちるようになったら陰性対照が失敗する
- **検出できない: 未追跡のファイルの違反。** 性質としては正しい（生成物や作業中の
  ファイルまで検査したくない）が、**「手元で緑」と「CI で緑」がずれる**ことは残る。
  機械で塞ごうとすると「未追跡のソースがあったら落とす」ことになり、
  作業中に常に落ちる検査になるので採らない

  規則の隣に根拠へのリンクがあるかを検査する案は考えたが、
  リンクの有無と理由の有無は別物なので、**形式だけを満たした規則が増える**
- 唯一の対処は、**`@` で読み込まれる文書に書いてあっても、
  `decisions.md` に根拠が無いものは未決定として扱う**こと

### 2026-08-30 — 依存の衝突を、上げる道を調べずに下げて解いた

**何が起きたか**

コンポーネントテストを実ブラウザで走らせるため `@vitejs/plugin-react` を入れたところ、
`vite/internal` が解決できずに落ちた。peer を見ると `vite: ^8.0.0` で、
入っていたのは 7.3.6 だった。**そこで plugin-react を 6 系から 5 系へ下げた。**

利用者に「**なんで上げないで下げたの？**」と問われて調べたところ、
**下げる理由は無かった。**

| | |
|---|---|
| vite の最新 | **8.2.2**（存在する） |
| vitest 4.1.11 の peer | `vite: ^6.0.0 \|\| ^7.0.0 \|\| **^8.0.0**` |
| `@tailwindcss/vite` の peer | `^5.2.0 \|\| ^6 \|\| ^7 \|\| **^8**` |

しかも依存ツリーには既に `invalid: "^8.1.5" from obug` と出ており、
**8 を欲しがっているものが先にいた。**

**なぜ起きたか**

**エラーが消える方へ倒した。** 上げる道と下げる道を比べていない。
「peer が ^8 を要求している / 入っているのは 7」を見て、
**動いている側に合わせるのが安全だと考えた——その判断をした瞬間が無い。**

比べていれば1分で分かることだった。`npm view vite version` と
`npm view vitest peerDependencies` を打つだけである。

**これはこのセッションで4度目の同じ形である。**

| | 確かめずに前提にしたもの |
|---|---|
| Storybook | 「プロセス文書に書いてあるから決定済み」 |
| Fumadocs の決め手 | 「Tailwind 系だからサイトをトークンで組める」 |
| iframe | 「Fumadocs を使うならプレビューは隔離が要る」 |
| **依存の版** | **「peer が合わないから下げる」** |

**どれも測れば分かることだった。** そして4件とも、指摘されるまで気づいていない。

**教訓8 に足していた一文を、自分で削った直後でもある。**

> そして**軸に使う事実は測ってから書く。** 版・対応状況・制約を思い込みで書くと、
> 比較そのものが無効になる。

自己レビュー D2 で「これは教訓1・2 の系統で、適用先が増えただけ」として教訓から外した。
**外した判断は今も正しいと思う**（教訓を増やすことにはコストがある）。
**だが外した3時間後に、まさにその形を踏んでいる。**

**追加したガードレール**

**無い。** 「上げる道を調べたか」を機械的に検査する方法は無い。

強いて言えば、**依存を触ったときに `npm view <pkg> peerDependencies` を
打ったかどうか**だが、打ったことを検査できても**読んだことは検査できない。**

**検出できること / できないこと**

- 検出できない。**「比べなかった」ことは、成果物に痕跡を残さない。**
  下げた結果は動くので、CI も検査も緑になる
- 唯一の対処は、**依存の衝突を解くときに「上げる」「下げる」の両方を書き出してから選ぶ**こと。
  片方しか書いていないなら、それは選択ではない

### 2026-08-30 — 観測ゼロを、コンポーネントに機能を入れない根拠として利用者に示した

**何が起きたか**

利用者が Card の見出し領域・Button のアイコン・ボタンのローディングを挙げた。
4本を数え、ローディングについて「**観測ゼロ**」を先頭に置いた選択肢を出した。

利用者の回答:

> この問いに限らないですが、前にも言った通り観測に縛られすぎています。
> **私が伝えた需要とは観測対象のサイトやアプリ内の話ではなく、
> 一般的にサイトやアプリを作る上での需要を指しています。**

「前にも言った通り」とあるとおり、**同じ指摘を受けるのは2度目**である。

**なぜ起きたか**

**教訓7 が存在していたのに発火しなかった。**
2026-08-29 に「観測4本の中身を、役割を出すか出さないかの根拠に使った」を
記録し、教訓7 に「観測は『需要がある』には答えるが、『無い』には答えない」と書いた。

書いた範囲が**役割（セマンティック）に閉じていた。**
文面は「役割を落とすときは」で始まっており、
**コンポーネントの機能を入れるかどうかには届いていなかった。**

さらに深いところで、**「実需要」を「観測4本での出現回数」と読み替えていた。**
原則7 の「既存4本で3回以上書き直したものから始める」は
**最初の5個を選ぶための基準**であって、
**選んだコンポーネントが何を持つかの基準ではない。**
別の問いのために決めた基準を借りて比べている——教訓2 の後半がまた当たっている。

**利用者の申告は観測より新しい証拠である。**
4本は過去に書かれたもので、利用者はいま作ろうとしているものを知っている。
それを「観測ゼロ」の後ろに置いた時点で、重みづけが逆になっていた。

**直したもの**

- **教訓7 の範囲を広げた。** 役割だけでなく、コンポーネントが何を持つかにも当たると書いた
- **原則7 に「実需要とは何か」を書いた。** 観測4本は需要の裏づけであって、需要の定義ではない
- 決定 6-16 に、この線引きを決定として残した

**追加したガードレール**

無い。**検査で防げる種類の誤りではない。**
「観測に無いから入れない」と「設計として入れない」は、書かれた文からは区別がつかない。

**手順で薄める**: 機能を入れないと決めるときは、
**「観測に無い」を理由として書かない。** 書けるのは設計上の理由だけである。
観測は「入れる」側の裏づけにだけ使う。

### 2026-08-30 — 遷移の途中の計算値を、3度目に読んだ

**何が起きたか**

読み込み中のボタンが「沈まない」ことを、背景色の文字列で比べた。
手元では通るが **CI で落ちた。**

```
Expected: "oklch(0.5327 0.117 237.32)"
Received: "oklab(0.5327 -0.0631737 -0.0984788)"
```

**同じ色である。** 書き方だけが違う。
器は `transition-colors` を持っているので、描画直後に読むと
**補間の途中の値**が返り、Chromium はそれを `oklab()` で書く。

**なぜ起きたか**

**同じ形を3度踏んでいる。** focus の輪郭、hover の背景、そして今回である。
過去2回はどちらも「読んだ値が期待と違う」ところから
**実装の誤りを疑って**時間を使った。

対処はそのつど入れた（遷移を切る、`expect.poll` で待つ）が、
**次に色を比べるテストを書くときに思い出す仕組みが無かった。**

手元で通ったのは、**同じ機械で遅い経路を通っていた**だけである。
CI の方が速く、補間の途中に当たった。**手元で緑は「速さが違えば別」を含まない。**

**直したもの**

`expect.poll` で遷移が終わるまで待つ形にした。3回続けて緑を確認している。

**追加したガードレール**

無い。**検査で防げる種類の誤りではない。**
「遷移中に読んでいる」と「実装が違う」は、落ちた結果からは区別がつかない。

**手順で薄める**: **色を比べるテストを書いたら、`expect.poll` で待つ。**
器が `transition-*` を持っているかを先に見る。
持っているなら、直後の1回読みは**必ず**補間に当たりうる。
