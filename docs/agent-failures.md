# エージェントの失敗記録

**ガードレール（lint ルール / CI 検査 / git フック / Skill）を追加するときは、
必ずこのファイルに理由を書いてから追加する。**

ルールが先にあってはならない。失敗が先にあり、ルールはその対処として生まれる。
理由の書かれていないルールは、後から誰も消せなくなる。

## 書き方

各エントリは以下を含む。

- **日付**
- **何が起きたか** — 具体的に。「型エラーが出た」ではなく、どのファイルのどの記述か
- **なぜ起きたか** — エージェント（または人間）が何を前提にしていたか
- **追加したガードレール** — どのファイルの何を変えたか
- **そのガードレールが検出できること / できないこと** — 万能ではないことを明示する

## 記録

### 2026-08-23 — 設計段階で私（Claude）が誤った生成規則を提示した

**何が起きたか**

spacing スケールの生成規則を「増分は2段ごとに倍化する」と説明し、
その規則から `0, 4, 8, 12, 16, 24, 32, 48, 64, 96` が生成されると述べた。
実際にコードで生成すると `0, 4, 8, 16, 24, 40, 56, 88, 120` になり、一致しなかった。

**なぜ起きたか**

値の並びを先に決め、それを説明する規則を後から言葉で組み立てた。
言葉の上では筋が通っていたが、機械的に実行される形で検算していなかった。
**「規則から値を導く」と主張しながら、実際には値から規則を後付けしていた。**

正しい規則は「`base × 2` 以降、×3/2 と ×4/3 を交互に適用する」。
`3/2 × 4/3 = 2` なので2段ごとに正確に倍になる。

**追加したガードレール**

同日中に**同じ誤りを2度目に起こした**ため（下記）、設計段階のうちに入れた。

- `scripts/metrics/scales.mjs` に期待値の自己検査を置き、
  規則が `docs/decisions.md` の値を生成しない場合は import 時点で例外を投げる

Phase 1 で `packages/tokens` に移した際、`docs/decisions.md` の表との一致も検査に加えた
（`scripts/check-docs-scales.mjs`）。

当初は「表を生成器から自動出力する」つもりだったが、**検査する方式に変えた。**
自動出力にすると、表が生成器の出力そのものになり「証人」として機能しなくなる。
人が書いた値と生成器の出力が独立に一致することに意味がある。

**検出できること / できないこと**

- 検出できる: 規則と値の不一致
- 検出できない: 規則そのものが設計として妥当かどうか。それは人間の判断が要る
- 検出できない: 期待値の側を書き換えて通す行為。
  **期待値は「規則から導いた値」ではなく「規則が正しいことの証人」である。**
  期待値を書き換えて通すのは、規則の誤りを隠すことに等しい

### 2026-08-23 — 同じ誤りを2度目に起こした

**何が起きたか**

上記の修正として書き直した spacing 生成規則が、また違う値を生成した。

```js
v *= ratios[out.length % 2];   // 配列の長さで交互判定 → 位相がずれる
// 生成: [0,4,8,10.67,16,21.33,32,42.67,64,85.33,128]
```

正しくは独立したカウンタで交互判定する。

```js
for (let i = 0; v < 96; i++) { v *= ratios[i % 2]; out.push(v); }
```

**なぜ起きたか**

1度目と同じ構造の誤り。**規則を書いた直後に出力を目視で確認していなかった。**
交互適用の位相という、目で追うと正しく見えて実行すると違う種類の誤りである。

**追加したガードレール**

「Phase 1 で入れる」としていた自己検査を、待たずに設計段階で入れた。
2度起きた時点で、後回しにする判断が誤りだったと判定した。

**検出できること / できないこと**

- 検出できる: 今回と同種の位相ずれ・off-by-one
- 検出できない: 期待値そのものが間違っている場合。期待値は人間が決定文書と照合する必要がある

### 2026-08-23 — 検証の出力を読み違えて、逆の結論を出しかけた

**何が起きたか**

Tailwind v4 の実験で「任意値記法 `p-[20px]` は生成されない」と読んだ。実際には生成されていた。

原因は Tailwind の挙動ではなく**検証手順の側**にあった。
出力を拾う正規表現がエスケープされたクラス名（`.p-\[20px\]`）のバックスラッシュに
マッチしておらず、存在するものを「無い」と表示していた。

同じ実験で、utilities が `@layer` 内にインデントされているために
`^\.p-` が一件もマッチせず、「ユーティリティが生成されていない」と読み違えてもいる。

**なぜ起きたか**

grep でフィルタした結果だけを見て結論を出した。
**フィルタが外れているのか、対象が存在しないのかを区別していなかった。**

この誤りは危険度が高い。生成規則の誤り（過去2件）は期待値検査で機械的に捕まるが、
**「検証手順が壊れていて何も検出していない」状態は、検査が全部緑になる形で現れる。**

**追加したガードレール**

ルールとして残す（下記）。自動検査は書いていない。
検証手順そのものの正しさを機械的に保証する方法は無く、
「壊れた検査は緑になる」という性質上、上位の検査を足しても同じ問題が再発するだけである。

**検出できること / できないこと**

- 検出できない（自動では）。人間の習慣で防ぐしかない種類の誤り

### 2026-08-23 — 規則を書いた同じコミットで、その規則を破った

**何が起きたか**

CLAUDE.md に「**仕様は記憶で書かない。動かして確かめる**」という教訓を書いた。
その**同じコミットで** `.claude/settings.json` に機能しない permission ルールを書いていた。

```json
"Bash(node scripts/metrics/:*)"
```

`:*` は末尾のワイルドカードとして `Bash(node scripts/metrics/ *)` と等価であり、
**末尾スラッシュの直後にスペースを要求する**。
実際のコマンド `node scripts/metrics/generate-scales.mjs` にはマッチしない。
正しくは境界を要求しない `Bash(node scripts/metrics/*)`。

**なぜ起きたか**

`:*` という記法を記憶で書いた。ドキュメントを確認していない。
自己レビューの段階で公式ドキュメントを読み、初めて気づいた。

**この失敗の意味**

これは単なる4件目ではない。

**「教訓を文書に書くこと」が「教訓に従うこと」を保証しないという実例**である。
規則を書いた本人が、同じコミットの中で同じ規則を破った。
しかも破ったことに、規則を書いている最中はまったく気づいていない。

したがって CLAUDE.md は必要だが十分ではない。
**機械的に検査できるものは、文書ではなく検査にしなければならない。**
文書は「機械化できないもの」にだけ使う。

**追加したガードレール**

permission ルールの正しさを機械的に検査する方法は現時点で無く、
「検査できないから文書に書いた」という判断自体は正しかったと考える。

ただし、この失敗から導いた教訓3 を書き足したことで**別の問題が顕在化した。**

CLAUDE.md は agent-failures.md の教訓を**要約して埋め込んでいる**
（参照ではなく要約なのは、リンク先を読むかどうかに依存させないため）。
その代償として二重管理になり、教訓を追加するたびにドリフトする。
**同じ構造の重複問題は既に2度起こしている**（スケール定義の3重複、README との規則重複）。

教訓3「機械的に検査できるものは文書ではなく検査にする」の最初の適用として、
`scripts/check-lessons-sync.mjs` を追加した。
agent-failures.md の教訓の見出しが CLAUDE.md に存在することを検査する。

```bash
pnpm check:lessons
```

わざと1件消して検査が失敗することを確認済み（教訓2 の実践）。

**この失敗は Phase 1 の設計にも影響する。**
lint・CI 検査を設計するとき、「CLAUDE.md に書いたから守られる」を前提にしない。

**検出できること / できないこと**

- 検出できない。設定ファイルの意味論の誤りは、動かしても静かに失敗する
  （権限プロンプトが出るだけで、エラーにはならない）
- **静かに失敗するものは、失敗したことにすら気づけない。**
  これが4件のうち最も危険な種類である

### 2026-08-23 — 原則1 を破るコミットが、原則1 の検査を書いた同じコミットだった

**何が起きたか**

`packages/tokens` を作った際、生成物 `packages/tokens/tsconfig.tsbuildinfo` を
コミットしていた。原則1「生成物はコミットしない」に反する。

**同じコミットで、生成物の混入を検出する CI 検査を書いていた。**
その検査は既知のパスだけを見ていたため、緑のまま通った。

```yaml
# 書いた検査（既知のパスの列挙）
git ls-files | grep -E '^(packages/[^/]+/dist/|apps/[^/]+/public/r/)'
```

`tsbuildinfo` は列挙に含まれていない。

**なぜ起きたか**

**列挙方式の検査を書いた。** 列挙し忘れたものは黙って通る。
`packages/tokens` の独立性検査（`check-tokens-isolation.mjs`）では
「react を禁止する」ではなく「相対パスと node: 以外を全部禁止する」形にしていたのに、
生成物の検査では同じ判断ができていなかった。**同じ日に、同じ設計判断を片方だけ間違えた。**

**追加したガードレール**

`scripts/check-no-build-output.mjs` を追加し、CI の直書き grep を置き換えた。
拡張子とディレクトリ名の両面から広く拾う。`.gitignore` に `*.tsbuildinfo` も追加した。

陰性対照で発火を確認済み。

**この修正中にもう1件やらかした**

スクリプトのブロックコメントに `packages/*/dist` と書いたところ、
`*/` がコメントを終端して構文エラーになった。実行して初めて気づいた。
**書いたコードは動かすまで動くとみなさない**（教訓1の一般形）。

**検出できること / できないこと**

- 検出できる: 名前から生成物と分かるファイル
- **検出できない: 名前から生成物と分からないファイル。**
  列挙方式より広いだけで、原理的には同じ弱点を持つ

### 2026-08-23 — 仕様に出てきた語を、決定済みと推測した

**何が起きたか**

ブランチ戦略を決めずに4 PR 進めた。`develop` ブランチが存在しない状態で、
`main` に未リリースの実装が積み上がっていた。

Phase 4 でレジストリを公開すると `main` が利用者の install 対象になるため、
**このままだと未完成のものを配布することになっていた。**
バージョン管理の方針も何も決まっておらず、タグは1つも無く `packages/tokens` は `0.0.0` のまま。

**なぜ起きたか**

指示にあった次の一文を、ブランチ戦略の指定として読んだ。

> Issue を立ててから branch を切る。main への直接 push は禁止（pre-push フックで機械的に防ぐ）

**この文が指定しているのは main の保護であって、ブランチ戦略ではない。**
`main` という語が出てきたことをもって単一トランクだと推測し、
「決定済みの事項」として扱って確認を取らなかった。

スケール・命名・比率については毎回選択肢を出して確認を取っていたのに、
開発フローは「動かせない設計原則」のリストに含まれていなかったため、
**決定すべき論点として認識されていなかった。**

**指摘されたときの二次的な誤り**

「なぜ develop が無いのか」と問われた際、最初の回答で
「単一トランクで良いと考えていた理由」を3つ挙げた。
**あれは後から作った理屈である。** 実際にはその判断をした瞬間が無い。

**存在しなかった思考を、あたかも存在したかのように再構成して説明した。**
これは失敗そのものより悪い。原因が隠れ、同じことが再発する。

**追加したガードレール**

- `develop` を作り、`main` をリリース線にした（[branching.md](./branching.md)）
- pre-push フックが `main` と `develop` の両方を守る
- **GitHub の branch protection を `enforce_admins: true` で設定した。**
  フックは手元だけの防御で、clone した別環境や Web UI からの操作を止められない。
  フックを迂回した push が実際にサーバ側で拒否されることを確認済み

ただし**この失敗はガードレールでは防げない類のものである。**
「決めるべきことを決めていない」ことを機械的に検出する方法は無い。
教訓として残す（下記）。

**検出できること / できないこと**

- 検出できない。**未決定の論点が存在することを、検査は知りようがない**
- 唯一の対処は、着手前に「何が未決定か」を明示的に列挙すること

**この対処の最中にもう1件やらかした（手順の記録）**

`branch-flow` が機能することを確かめるため、作業ブランチから `main` へ
検証用の PR を出した。検査は期待どおり失敗したが、**その作業ブランチには
既に生きた PR があり、両者が同じコミットを指していた。**

GitHub のチェック結果はコミット単位で紐づくため、
**検証用 PR の失敗が、生きた PR のチェック欄に混入した。**

生きた PR の base は `develop` で必須チェックは `verify` のみだったためマージ可否には
影響しなかったが、レビューする人間から見れば「失敗している PR」に見える。

→ **検査の陰性対照を PR で取るときは、使い捨てのブランチから出す。**
   生きた PR と同じコミットを指すブランチを使わない。

## 教訓（ルールとして残す）

### 1. 生成規則を書いたら、必ず実行して出力を決定文書と照合する

言葉の上で筋が通ることと、コードが期待どおり動くことは別である。
「規則から値を導く」と主張するプロジェクトで、値を目視確認せずに規則を書いてはならない。

### 2. 検証は生の出力を見る。フィルタした結果だけで結論を出さない

「該当なし」を見たら、まず**フィルタが正しいか**を疑う。
対象が存在しないことと、フィルタが外れていることは区別がつかない。

**「何も検出されなかった」は成功ではなく、検査が機能していない可能性を含む。**
ゼロ件の結果には、意図的に該当するケースを1件作って検査が発火することを確かめる。

（実際、スケールの期待値検査はわざと規則を壊して発火を確認した。同じことを常に行う）

### 3. 機械的に検査できるものは、文書ではなく検査にする

規則を文書に書いた本人が、同じコミットの中でその規則を破った実例がある。
**「書いたから守られる」は成立しない。**

文書は機械化できないものにだけ使う。文書は最後の手段であって、最初の手段ではない。

### 4. 静かに失敗するものを疑う

設定ファイルの意味論の誤りは、動かしてもエラーにならない。
権限プロンプトが余分に出るだけで、誰も気づかない。

**エラーにならない仕組みほど、意図どおり動いていることを能動的に確かめる。**

### 5. 検査は「禁止するもの」ではなく「許可するもの」を列挙する

禁止リスト方式は、リストに無いものを黙って通す。
**列挙し忘れたケースがあることに、検査が緑である限り気づけない。**

同じ日に、独立性検査では許可リスト方式（相対パスと `node:` だけ許可）を採り、
生成物検査では禁止リスト方式を採って実際に見逃した。判断を揃える。

許可リストにできない場合は、**検査が原理的に見逃す範囲を検査自身のコメントに書く。**

### 6. 仕様に出てきた語を、決定済みと推測しない

指示の中に固有の語（ブランチ名、ツール名、ディレクトリ名）が出てきても、
**それがその領域の決定を意味するとは限らない。**
書かれているのは往々にして、より狭い1点だけである。

着手前に「この領域で決まっていないことは何か」を列挙し、
決まっていないものは決定として扱わない。

**判断の経緯を説明するとき、存在しなかった思考を再構成しない。**
「検討していない」が答えなら、そう答える。
後付けの理屈は原因を隠し、同じ失敗を再発させる。
