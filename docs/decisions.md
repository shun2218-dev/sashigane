# 設計決定

このファイルは実装前の対話で確定した決定を記録する。
実装はこのファイルに従う。決定を変える場合は、このファイルを先に更新する。

決定には版がある。検証（[verification.md](./verification.md)）によって修正された決定は
`改訂` として履歴を残す。何をどう間違えたかが、このプロジェクトの成果物の一部である。

---

## 0. 前提

- 唯一の根本定数は `root = 16px`
- すべてのスケールは規則から生成する。値を手で選ばない
- 既存プロジェクトは「需要の観測」には使うが「値のソース」にはしない
- 生成物はコミットしない

`root` から導けない次元（時間）だけが独自のアンカーを持つ。これは例外として明示する。

## 1. スケール

### 決定 1-1: 基準単位

```
root         = 16px          唯一の根本定数
spacing.base = root ÷ 4 = 4px
type.base    = root     = 16px
```

**出力単位は rem。** `tokens.json` には px で記述し、生成時に rem へ変換する。

理由: ユーザーがブラウザの既定フォントサイズを変更したとき、文字だけが拡大して余白が
据え置きになると詰まって読めなくなる。余白も連動させる必要がある。

**例外:** `border-width` / `outline-width` は px で出力する。これらは拡大させたくない値である。
spacing ではないので、spacing の一貫性は壊れない。

**検討して退けた案**
- 基準値 8px — sub-8 が必要な場面（アイコン↔ラベル、インラインバッジ、密なテーブル）が実在し、
  必ず例外が生まれる。例外が生まれた時点で「8px基準」という主張が嘘になる
- 基準値 2px — 1〜2px の調整は border / outline の責務。spacing に持たせると責務が混線する
- px 固定出力 — a11y を後付けでしか満たせない。原則5の思想と一貫しない

### 決定 1-2: spacing スケール

> **改訂あり。** 当初「増分は2段ごとに倍化」と記述したが、この規則は下記の値を生成しない。
> 値は正しく、規則の記述が誤っていた。以下が正しい生成規則。

**生成規則**

```
s[0] = 0
s[1] = base                      (= 4)
s[2] = base × 2                  (= 8)
s[n] = s[n-1] × 3/2   (n が奇数)
s[n] = s[n-1] × 4/3   (n が偶数)
```

`3/2 × 4/3 = 2` なので **2段ごとに正確に倍**になる。1段あたりの実効比は √2 前後。

**値**

```
0, 4, 8, 12, 16, 24, 32, 48, 64, 96      (10値)
```

隣接比: `1.5, 1.333, 1.5, 1.333, 1.5, 1.333, 1.5`

**根拠**

余白の知覚は小さい領域では絶対差、大きい領域では相対差で効く。
4px と 8px の差は明確に見えるが、64px と 68px の差は見えない。
したがって余白に単一の等比を当てるのは誤り。この規則は小域を密に、大域を疎に刻む。

**プリミティブは単一スケール1本。** 用途の区別（インライン用 / レイアウト用）は
セマンティック層で表現する。プリミティブを用途で分けると意味が二重管理になる。

**検討して退けた案**
- 線形（4の倍数すべて）— 段が多すぎてどの値も合法になり、lint による逸脱検出が機能しない
- 純幾何 ×2（4,8,16,32,64）— 16→32 の谷にカード内側余白の現実的な答えが落ちるため、
  密度の調整手段が構造的に存在しなくなる

**記録:** 20 / 40 を持たない。検証の結果これは (b) 不統一と判定した（verification.md 参照）。

### 決定 1-3: font-size スケール

> **改訂あり。** 当初「下3 / 上4 = 8段」としたが、検証で上限不足が判明したため上方向を3段延長した。

**生成規則**

```
アンカー = root = 16px（index 3）
アンカーより下 = ÷ 1.125
アンカーより上 = × 1.25
下3段 / 上7段 = 計11段
丸めない
```

**値**

| index | px | rem |
|---|---|---|
| 0 | 11.2373 | 0.7023 |
| 1 | 12.6420 | 0.7901 |
| 2 | 14.2222 | 0.8889 |
| **3** | **16.0000** | **1.0000** |
| 4 | 20.0000 | 1.2500 |
| 5 | 25.0000 | 1.5625 |
| 6 | 31.2500 | 1.9531 |
| 7 | 39.0625 | 2.4414 |
| 8 | 48.8281 | 3.0518 |
| 9 | 61.0352 | 3.8147 |
| 10 | 76.2939 | 4.7684 |

**なぜ単一比率でないか**

文字サイズの知覚は素直に相対差なので、本来は単一比率が正しい。
問題は知覚ではなく需要の分布にある。UI で必要なサイズは 12〜16px の帯に密集し、
24px 超は見出しだけで段が少ない。

加えて、見出しどうしはページ内の離れた位置で比較されるため大きな差が要る。
ラベルと本文は隣接して比較されるため小さい差で識別できる。
**比較される距離が違えば必要な弁別閾も違う。**

**なぜ丸めないか**

`size[n+1] / size[n] === ratio` をテストで検証可能な不変条件として保てる。
丸めた瞬間に「導出された値」ではなく「選ばれた値」になり、原則2が形骸化する。
生成物はコミットしないので、小数の見た目は人が読む機会がない。

**記録:** 18px / 22px は3プロジェクトに出現するが (b) と判定した。
ただし上方向比率 1.25 が 16〜25 の帯で粗いことは事実として記録する。

**上限を超える需要の扱い**

実測には 100px / 132px があるが、これは `clamp(76px, 15vw, 132px)` の形で現れる
**可変域の端**であって段ではない。スケールが到達する必要はない。
「2つの段の間を clamp で結ぶ」というセマンティック役割で表現する。

### 決定 1-4: line-height

> **改訂あり。** 当初は単一の式としたが、検証で 1.0 未満を生成できない構造的欠陥が判明した。
> 漸近線を3系統に分ける形へ修正した。

**生成規則**

```
line-height = a + (root ÷ 2) / size

a = 0.8   display  … 大型数値・ヒーロー
a = 1.0   ui       … 既定
a = 1.2   prose    … 長文
```

**係数 `root ÷ 2` は3系統すべてで共通。変えるのは漸近線1つだけ。**

**値**

| index | px | display | ui | prose |
|---|---|---|---|---|
| 0 | 11.2373 | 1.512 | 1.712 | 1.912 |
| 1 | 12.6420 | 1.433 | 1.633 | 1.833 |
| 2 | 14.2222 | 1.363 | 1.563 | 1.762 |
| 3 | 16.0000 | 1.300 | 1.500 | 1.700 |
| 4 | 20.0000 | 1.200 | 1.400 | 1.600 |
| 5 | 25.0000 | 1.120 | 1.320 | 1.520 |
| 6 | 31.2500 | 1.056 | 1.256 | 1.456 |
| 7 | 39.0625 | 1.005 | 1.205 | 1.405 |
| 8 | 48.8281 | 0.964 | 1.164 | 1.364 |
| 9 | 61.0352 | 0.931 | 1.131 | 1.331 |
| 10 | 76.2939 | 0.905 | 1.105 | 1.305 |

**根拠**

行高はサイズが大きくなるほど比率を下げる必要がある。小さい文字は行の折り返しを
目が追うのに垂直方向の分離が要る。大きい見出しは行高が広いと壊れて見える。
したがって line-height を独立したスケールとして持つのは誤りで、サイズからの従属値である。

**オーバーライドは認めない。** コンポーネントが行高の数値を選ぶことはできない。
選べるのはテキスト役割が属する**系統**だけで、値は導出される。lint で強制できる形は変わらない。

**検討して退けた案**
- 全サイズ固定 1.5 — 39px の見出しで行送りが明確に緩い
- 名前付き数段を選ばせる — サイズとの組み合わせをシステムが保証できない

### 決定 1-5: radius

**生成規則**

```
radius = spacing スケールの 0〜16 の範囲をそのまま使う
```

**値:** `0, 4, 8, 12, 16` + `full`

**根拠: 入れ子の同心性**

角丸のある容器に padding を取って角丸の要素を入れると、
`内側 = 外側 − padding` でないと同心にならず歪んで見える。
radius と spacing が同じ算術の上にあれば、この減算が閉じる。

```
16 − 4 = 12 ✓   16 − 8 = 8 ✓   16 − 12 = 4 ✓   12 − 4 = 8 ✓   8 − 4 = 4 ✓
```

生成時にこの閉包をテストで検証する。

**`full`（9999px / 50%）は段ではなく別カテゴリ。**
ピルとサークルはランプ上の極大値ではなく形状の種別なので、
`radius-5` のような名前を与えると誤用される。

### 決定 1-6: duration

時間は `root` から導出できない独立した次元なので、**独自のアンカーを持つ**。
これはシステム内で唯一の追加定数である。

**遷移（transition）**

```
アンカー = 200ms、比率 √2、下2段 / 上2段
→ 100, 141.4, 200, 282.8, 400
```

√2 を選ぶ理由は 2段で正確に倍になること。100 / 200 / 400 が誤差なく落ちる。

知覚上の有効域:

| 帯 | 意味 |
|---|---|
| <100ms | 瞬時として知覚される |
| 100〜200ms | 状態変化（hover / press / toggle） |
| 200〜300ms | 要素の出入り |
| 300〜500ms | 大きな面の遷移 |
| >500ms | UI としては鈍重 |

**ループ（infinite animation）— 別スケール**

```
アンカー = 1000ms、比率 √2、下1段 / 上1段
→ 707.1, 1000, 1414.2
```

パルス・スピナー・スケルトンのシマーは無限ループであり、
「>500ms は鈍重」という知覚上の制約が適用されない。同じスケールに乗せてはならない。

### 決定 1-8: elevation — **改訂（2026-08-29）**

> **保留を解いた。** 当初版は「影の色成分は色システム設計後に確定する」と書いて
> 実装を止めていた。色システム（決定5-1〜5-14）が確定したので実装したところ、
> **当初版が用意した2つの手段のうち、暗色側の1つが成立しないことが測定で分かった。**
> 記録は [Issue #81](https://github.com/shun2218-dev/sashigane/issues/81)。

**段数:** `h = 0, 1, 2, 3`

| h | 用途 | トークンに出すか |
|---|---|---|
| 0 | 平坦（面の上に直接置かれるもの） | 出さない。影を書かなければよい |
| 1 | 持ち上がり（カード、押下可能な面） | `--sg-elevation-raised` |
| 2 | 重なり（ドロップダウン、ポップオーバー、ツールチップ） | `--sg-elevation-overlay` |
| 3 | 前面（モーダル、ダイアログ、ドロワー） | `--sg-elevation-front` |

#### 幾何は h に比例する。新しい長さの定数は持ち込まない

物理モデルは当初版のまま——光源を上に置き、オフセットもぼかしも `h` に比例する。
オフセットの単位に `base`（= `root ÷ 4` = 4px）を取ると、出る値は全部 spacing の段に載る。

| h | オフセット | ぼかし |
|---|---|---|
| 1 | 4px | 8px |
| 2 | 8px | 16px |
| 3 | 12px | 24px |

`blurRatio = 2`（ぼかし ÷ オフセット）だけが新しい選択で、これは**光源の形**である
（光源の大きさ ÷ 光源の横ずれ）。`root` からは導けないので、ここで選んだことを明示する。

#### 濃さは h で変えない。面の梯子1段分として色システムから解く

**当初版の「単位面積あたりの濃度は h とともに低下」を撤回した。**
物理どおり `1/h²` で落とすと `h=3`（モーダル）の影が最も薄くなり、**浮きの順序が見た目で逆転する。**
`h` が表すのは広がりだけにする。

濃さは値として決めない。**`bg-page` の上に落ちた影の最も濃い点が、
1段深い面（`bg-surface`）と同じ相対輝度になるアルファ**を解く。

全360色相で `α = 0.2459 〜 0.2526`。色は中間色ランプの暗端を取るので、
決定5-6 により primary の色相を持つ——当初版が要求した
「影は純黒ではなく背景の色相を持たせる」が自動的に満たされる。

**面の深さでも変えない。** 深い面ほど「1段分」に必要なアルファは上がる
（page `0.246〜0.253` → 3段目 `0.331〜0.336`）が、page で解いた1つの値を全段で使っても、
できる影の対比は `1.28〜1.31` に収まる。面ごとに解き直すと影の色が面の数だけ増える割に、
見た目が動かない。

**これで明色の影と暗色の梯子が、同じ「1段」を別の媒体で表すことになる。**

#### 暗色モードでは影も明度差分も使えない — **当初版の撤回点**

当初版は `(影の仕様, OKLCH明度差分)` のペアとして定義し、
「明色モードは影を主、暗色モードは明度を主として使う」と書いていた。**両方とも塞がっている。**

**1. 影は機能しない**（当初版の主張は正しかった。いまは測った数字がある）

影の色を純黒・アルファ 1.0 にしたときでも、地に対して作れるコントラストの上限。

| モード | 上限 |
|---|---|
| 明色 | 10.91:1 〜 19.27:1 |
| **暗色** | **1.08:1 〜 1.73:1** |

**2. 明度差分も持てない**（当初版が想定していなかった）

決定5-2 は端点を**ちょうど 4.500 に解いている。** 余裕がゼロなので、面を持ち上げる余地が無い。

| モード | 面 | 持ち上げられる余地 Δ | 面1段分 |
|---|---|---|---|
| 暗色 | page(950) | **0.0000** | 0.0703 |
| 暗色 | surface(900) | **0.0001** | 0.0703 |
| 暗色 | inset(800) | 0.0008 | 0.0703 |
| 明色 | 全段 | 上限まで安全（明るくすると対比は上がる） | 0.0879 |

明度を足すと、**前景は面の文脈のまま背景だけが動く。**
これは [Issue #65](https://github.com/shun2218-dev/sashigane/issues/65) で塞いだ
「塗るだけの道」と同じ構造の穴である。エラーにはならない（教訓4）。

#### 決定: 暗色は輪郭で表す

`box-shadow` の同じ枠に `0 0 0 1px` を出し、`h` ごとに既存の境界3段を使う。

| 役割 | 明色 | 暗色 |
|---|---|---|
| `raised` | `0 4px 8px var(--sg-shadow-ink)` | `0 0 0 1px` の `border.subtle` |
| `overlay` | `0 8px 16px var(--sg-shadow-ink)` | `0 0 0 1px` の `border.default` |

**新しい定数を持ち込まない。** 段は面の深さで解き直された `roles.border` から取るので、
深い面では輪郭も一緒に動く。暗色の `surface` の上で `1.65〜1.69`（raised）と
`2.20〜2.31`（overlay）——明色の影が作る `1.28〜1.31` と同じ桁である。

##### 申告する限界: 暗色で伝わるのは順序であって量ではない

明色は `offset` も `blur` も `h` に比例するので、**`h` の量が見た目に出る。**
暗色は境界の段を1段ずらすだけで、しかも段は3つしか無い。
**`h` を増やしても頭打ちになる。**

媒体を変えた以上これは避けられない。避けられないものを書かずに済ませると、
限界ではなく仕様の一部として読まれる（教訓5）。

ichirizuka が box-shadow を1つも持たず**罫線と地の色差だけで階層を作っていた**という観測
（[roles.md](./roles.md)）が、そのまま暗色モードの手段になった。

##### これが無いと暗色の overlay に穴が残る

`overlay` は `surface` と**同じ段**に置いてある（決定5-13。最深段に置くと中の項目が
hover できなくなるため）。暗色モードでカードの上に出したドロップダウンは、
影も明度差分も無ければ**背景色が下地と完全に同一**で、境界も無く同化する。

#### プリミティブとしては出せない

**モードで媒体が変わり（明色は影、暗色は輪郭）、暗色の輪郭は面の深さでも段が変わる。**
プリミティブはモードにも面にも依存しない層なので、ここには置けない。
出るのは役割名だけである。

以前は `--sg-elevation-0: 0` 〜 `-3: 3` という**高さの数字**が出ていた。
CSS のどのプロパティにも入らない値であり、参照できる形をしていなかった。

影の色だけはプリミティブに置く。**`--sg-shadow-ink`。** ランプの一部ではなく、
ランプの暗端から解いた1つの値なので段を持たない。

> **決定2-1（プリミティブは index 統一）からの2つ目の逸脱である。**
> 決定2-3 が偽陰性の実例として名指しした `--sg-radius-full` と同じ形で、
> **数字で終わらないプリミティブ**にあたる。層は名前表で判定するので実害は無い。
>
> 2つ目が出た以上、「例外が1つある」ではなく**「この規約は段を持たない値で破れる」**
> と書いておく。段を持たない値は今後も出る（自己レビュー B3）。

#### 他形式への変換は機械的に行う（決定2-6）

`tokens.js` にも `tokens.d.ts` にも `tokens.scss` にも、他のセマンティックと同じ形で出る。

```js
'--sg-elevation-raised': '0 4px 8px #1013163f',   // 明色
'--sg-elevation-raised': '0 0 0 1px #2e353a',     // 暗色
```

**JS 経路に浮きの需要は観測されていない。** Phase 2 で読んだ3本はいずれも色を必要としており
（[experiments/phase2-holosphere.md](./experiments/phase2-holosphere.md)）、影は1件も無い。
それでも出るのは、決定2-6 が**変換を機械的に行う**と決めているためである。
役割ごとに出す・出さないを判断し始めると、その判断表がもう1つの真実になる。

**`--sg-shadow-ink` は8桁の16進（`#1013163f`）を作る。** 決定2-6 が16進にする理由として
挙げたのは「canvas や OG 画像が `oklch()` を解さない」だが、**8桁を解さない描画先があれば
同じ問題が同じ形で起きる。確かめていない。** 需要が現れた時点で確かめる（自己レビュー B4）。

#### 段はすべて役割として出す — **改訂（2026-08-29）**

> **当初版を撤回した。** 「[roles.md](./roles.md) のコンポーネント需要表に
> モーダル／ダイアログが無いので `h=3` は役割としては出さない」と書いていた。
> **4本がモーダルを持っていなかった、というだけである**（教訓7、
> [Issue #88](https://github.com/shun2218-dev/sashigane/issues/88)）。

観測4本はデザインシステム無しで書かれた ad-hoc な実装で、
**デザインにこだわって作ったものではない**（作者に確認済み。決定5-12 に記録がある）。
そこに無いことは、そのアプリの事情であって設計の答えではない。

そして**逃げ道は全部塞いである。** プリミティブ参照（原則3）・任意値記法（決定3-1）・
素の数値ユーティリティ（決定3-5）・不透明度（決定1-15）・アルファ修飾子（決定3-2 改訂）。
この状態で `h=3` を落とすと、**モーダルの浮きを書く手段が利用側に1つも残らない。**

`h=0` だけは役割を持たない。影を書かなければ平坦であり、
`box-shadow` には `none` という語があるので「無いことを表す変数」が要らない
（`--sg-space-0: 0` とは事情が違う）。

#### 変わらない前提

**重要な制約:** 面をアルファで組み立てている場合、重なる要素には使えない（下地が透ける）。
`bg-surface` と `bg-overlay` は「同じ色の別の段」ではなく、構成方法からして別の役割である。

**フラット構成を既定と仮定しない。** 観測した4本のうち ichirizuka は box-shadow を1つも持たず、
罫線と地の色差だけで階層を作っている。角丸・影ありを前提にしてはならない。
そのため **`data-sg-surface` は浮きを自動では付けない。** 面の宣言と浮きは別の指定である。

### 決定 1-9: letter-spacing — 値を確定した（2026-08-28）

**駆動要因が2つある。サイズだけの関数ではない。**

```
tracking = f(size) + (uppercase ? k : 0)
```

- **サイズ** — 大きいほど負（大型数値に -0.01 〜 -0.02em）
- **大文字化** — 大文字は字面が詰まって見えるため字間を開ける必要がある（+0.08 〜 +0.22em）

> **確定させた（2026-08-28）。** [Issue #46](https://github.com/shun2218-dev/sashigane/issues/46)。
> 「具体的な係数は Phase 1 で確定する」と書いたまま実装されていなかった。

#### 生成規則

```
letter-spacing = coefficient × (root / size − 1)     単位は em
coefficient = 0.025
```

**line-height（決定1-4）と同じ 1/size の形である。** 字間も行高と同じくサイズからの
従属値であって、独立したスケールではない。

**本文サイズ（root）で 0 になる。** 補正は本文からの差として定義される。
小さい段は正（詰まって見えるので開ける）、大きい段は負（開いて見えるので詰める）。
`size → ∞` の漸近線は `−coefficient` で、これが**システムが与える最大の詰め**である。

#### 値

| index | px | letter-spacing |
|---|---|---|
| 0 | 11.24px | 0.0106em |
| 1 | 12.64px | 0.0066em |
| 2 | 14.22px | 0.0031em |
| 3 | 16.00px | 0 |
| 4 | 20.00px | -0.005em |
| 5 | 25.00px | -0.009em |
| 6 | 31.25px | -0.0122em |
| 7 | 39.06px | -0.0148em |
| 8 | 48.83px | -0.0168em |
| 9 | 61.04px | -0.0184em |
| 10 | 76.29px | -0.0198em |

#### `coefficient` は root から導けない

**原則2 の4つ目の例外である。** 時間・画面幅・書体と同じく、独自のアンカーを持つ。

`0.025` は「大型見出しは −2〜−3% 詰める」という組版の慣行の中央に置いた。

**観測を先に測った。順序を偽らない。** 観測した負の値から係数を逆算すると、
2本・3サイズが独立に 0.023〜0.026 に収まった。

| 出典 | サイズ | 実測 | 逆算した係数 |
|---|---|---|---|
| pylabo `__title`（講座） | 26px | −0.01em | 0.026 |
| pylabo `__title`（ホーム） | 40px | −0.015em | 0.025 |
| ichirizuka `.value` | 76〜132px | −0.02em | 0.023〜0.025 |

**観測は値のソースではなく、アンカーの裏づけである**（原則2）。
慣行と観測が別々に同じところへ着いたので 0.025 に置いた。

#### 本文の段が 0 であることの確かめ方（教訓4）

`letter-spacing: 0` の**計算値は `normal` になる。** そして**無効な値も `normal` になる。**
`getComputedStyle` だけでは、0 が効いているのか宣言ごと落ちているのか区別できない。

```
letter-spacing: 0        → 指定値 "0px" / 計算値 "normal"
letter-spacing: bogus    → 指定値 ""     / 計算値 "normal"
```

区別できるのは**指定値**（`el.style.letterSpacing`）である。実ブラウザで確かめるときは
そちらを見る。他の段は `px` に解決されるので計算値で足りる。

#### 大文字化は加算項として持つ

```
--sg-tracking-caps: 0.08em
```

サイズと直交するので**段を持たない**。決定1-11 の `--sg-text-numeric-variant` と同じ構造である。
素の CSS では足して使う。

```css
letter-spacing: calc(var(--sg-text-label-tracking) + var(--sg-tracking-caps));
```

`0.08` は大文字化の慣行（+5〜+10%）の中央付近であり、
ichirizuka で**4回**使われていた値と一致する（0.08 / 0.1 / 0.16 / 0.22 のうち最頻）。

観測は強い。ichirizuka の正の値は**すべて `text-transform: uppercase` と同時**であり、
holosphere の `tracking-wide` は **11箇所すべてが `uppercase` と同時**だった。
**2本目でも同じ形で再現した。**

#### 持たなかったもの

| 観測 | 中身 | なぜ持たないか |
|---|---|---|
| pylabo +0.01〜0.06（4件） | 11.5〜12.5px・`font-weight: 700` の小さいラベル。**大文字化していない** | サイズ駆動では説明できない（逆算した係数が 0.05〜0.18 とばらつく）。**太さが効いている可能性がある**（当時 font-weight は未決定。[Issue #53](https://github.com/shun2218-dev/sashigane/issues/53) は決定1-13 で解いたが、**この係数は再測定していない**）。駆動要因を特定できていないものを規則にしない |
| ichirizuka `.section > h2` +0.01 | 26px の見出し、大文字化なし | **サイズ駆動は負を予測するのに正。** 1件のみで、書体固有の光学補正の可能性がある |
| ichirizuka `.wordmark-ja` +0.2 | 21px の**和文**ワードマーク | 観測1件。しかもワードマークはブランドの選択であり、決定1-11（書体名は利用側が差す）と同じ性質を持つ |
| holosphere `Logo` `tracking-tight` | サイズを呼び出し側から継承するワードマーク | 同上 |

#### Tailwind アダプタでの限界（申告）

`--text-{役割}--letter-spacing` で役割に束ねてあるので、`text-caption` と書けば字間も付く。

**`tracking-caps` は加算ではなく置き換えになる。** Tailwind の `tracking-*` は
`letter-spacing` を直接書くため、当てるとサイズ側の項が落ちる。
落ちる量は、観測された大文字化の全件（10.5〜11px）で **+0.003〜+0.011em**
——caps 項の 4〜13% である。素の CSS では `calc()` で正確に足せる。

**素の t シャツ語彙は出さない。** `tracking-tight` `tracking-wide` は存在しない。
字間はサイズから導出されるものであり、コンポーネントが選ぶものではない（決定1-4 と同じ形）。

#### 検討して退けた案

- **段ごとの表を持つ** — 自由度は高いが「値は規則から生成する」（原則1）から離れる
- **閾値以上の段だけ負の値を持つ** — 閾値という新しい定数が増える。
  1/size の式なら小さい段の正の値も同じ規則から出る

### 決定 1-10: breakpoint — 値を確定した（2026-08-26）

breakpoint はトークンに含める。密度の軸と直結するため。

container 幅 / topbar 高さ / content 最小幅などのアプリ固有寸法は**含めない**。
利用側の責務とする。

#### 利用側はどう果たすのか（2026-08-26 追記）

> [Issue #43](https://github.com/shun2218-dev/sashigane/issues/43) の判断。
> 決定3-1 の `--spacing: initial` が **`w-*` `h-*` まで巻き込む**ことが Phase 2 の2本目で分かった。
> 「利用側の責務」と書きながら、**果たす道を示していなかった。**

利用側が `@theme` に自分の名前を足す。**実際に通ることを検査で確かめている。**

```css
/* レジストリ方式なので生成物は利用側リポジトリに落ちている（原則6）。
   npm 解決ではなく相対パスで読む */
@import "./tokens.css";
@import "./theme.css";

@theme {
  --container-content: 72rem;   /* → max-w-content, w-content */
  --container-sidebar: 16rem;   /* → w-sidebar */
  --spacing-chart: 21.25rem;    /* → h-chart */
  --spacing-scroll: 16rem;      /* → max-h-scroll */
}
```

**幅と高さで事情が違う**（実測）。

| | 読む名前空間 |
|---|---|
| `w-*` `max-w-*` `min-w-*` `basis-*` | `--spacing-*` **または `--container-*`** |
| `h-*` `max-h-*` `size-*` | **`--spacing-*` のみ** |

**高さ専用の名前空間は v4 に存在しない。** `--size-*` を定義しても何も起きない。
そのため高さは `--spacing-*` に足すことになる。**2つを分けて理解する必要がある。**

- **決定3-1 が塞いだ動的生成は復活しない。** `p-5` は依然として書けない
- **利用側が名前を足した分だけ、余白の語彙も増える。**
  `--spacing-chart` を足すと `h-chart` と同時に `p-chart` `gap-chart` `m-chart` も書ける。
  つまり **21.25rem という段外の値が余白としても書ける状態になる**

後者は利用側が自分の責任で開けた口であり、こちらのスケールが緩んだわけではない。
**ただし「高さのために開けた口が余白にも開く」ことは避けられない。**

#### 寸法のスケールは持たない

観測した高さは2種類に分かれる。

| | 例 | 判断 |
|---|---|---|
| 小さな UI 寸法 | `h-2` `h-4` `h-6` `h-8` `h-12` | **すでにスケール上にある** |
| 同・スケール外 | `h-2.5` `h-5` `h-9` `h-10` | shadcn 既定値と ad-hoc。値のソースにしない（原則2） |
| 大きなレイアウト寸法 | `h-64` `h-40` `h-[340px]` | **アプリ固有。利用側の責務** |

**寸法のスケールを新設する根拠は観測されていない。** 原則7 に従い持たない。

#### 原則2 の3つ目の例外

> **当初は「含める」とだけ決めて値を書いていなかった。**
> [Issue #44](https://github.com/shun2218-dev/sashigane/issues/44) で
> `--sg-breakpoint-*` が1つも生成されていないことが分かり、確定させた。

**画面幅は `root = 16px` から導出できない。** 組版ではなく**機器の寸法**で決まるからで、
`root` は画面幅について何も言わない。時間（決定1-6）・書体（決定1-11）と同じ例外として明示する。

| 名前 | 値 |
|---|---|
| `sm` | `40rem`（640px） |
| `md` | `48rem`（768px） |
| `lg` | `64rem`（1024px） |
| `xl` | `80rem`（1280px） |

素の Tailwind v4 と同じ値を採る。**観測2本が実際にこの4段を使っている。**

| | 使っているもの |
|---|---|
| holosphere | `sm:` 52 / `lg:` 31 / `md:` 13 / `xl:` 9 |
| pdf-merge-app | `sm:` 31 / `md:` 25 / `lg:` 5 |
| ichirizuka | 780px 単一（素の CSS） |
| pylabo | 560 / 720 / 900px（素の CSS） |

素の CSS の2本は値がばらばらで、原則2 のとおり値のソースにはしない。
**4段という需要は Tailwind を使う2本が裏づけている。**
同じ値を採ることで利用側の学習コストがゼロになる。

`2xl` は持たない。観測に現れず、原則7 に従う。

#### CSS 変数はメディアクエリの中で使えない

```css
@media (width >= var(--sg-breakpoint-sm)) { … }   /* 無効。ブラウザは無視する */
```

`--sg-breakpoint-*` を出してはいるが、**効くのは Tailwind アダプタ経由だけ**である。
アダプタはビルド時に値を読むので、`@theme` には**値を直接書く**（決定3-3）。
素の CSS の利用者は値を直接書くことになる。

**これは実際にコンパイルして確かめた。** 他の名前空間と揃えて `var(--sg-breakpoint-sm)` を
渡すと、Tailwind は上の無効なメディアクエリを出す。ユーティリティ自体は生成されるので
「出たか」だけを見る検査は通り、**見た目も「レスポンシブが効かない」だけで気づきにくい**（教訓4）。
`scripts/check-tailwind-adapter.mjs` がメディアクエリに `var(` が含まれないことを検査する。

### 決定 1-11: font-family — 構造だけを規定し、書体名は差してもらう

> **原則2「値は導出する」が適用できない次元。** `duration` と同じく例外として明示する。
> ただし duration は独自のアンカーを持てたが、書体は**アンカーを決めることすらできない。**
> 具体的な書体名はブランドの選択であって、システムの選択ではない。

観測した4本すべてが3系統（見出し / 本文 / 数値）を持っており、実需要は明確にある
（[roles.md](./roles.md)、[Issue #30](https://github.com/shun2218-dev/sashigane/issues/30)）。
**決めたのは値ではなく「何をトークンにするか」である。**

#### 3つのスタックと、6つの差し込み口

```
--sg-font-stack-body:    var(--sg-font-brand-body-latin, ui-sans-serif),
                         var(--sg-font-brand-body-cjk, system-ui), sans-serif
--sg-font-stack-display: var(--sg-font-brand-display-latin, var(--sg-font-brand-body-latin, …)),
                         var(--sg-font-brand-display-cjk, var(--sg-font-brand-body-cjk, …)), sans-serif
--sg-font-stack-mono:    var(--sg-font-brand-mono-latin, ui-monospace),
                         var(--sg-font-brand-mono-cjk, monospace), monospace
```

トークンが保証するのは**順序**である。欧文 → 和文 → generic。
日本語のUIでは欧文書体を先に置いて英数字をそちらに担当させるのが定石で、
これは書体名を知らなくても規定できる、この次元で唯一システムが持てる知識である。

| 決めたこと | なぜ |
|---|---|
| 口は欧文・和文の2つ | next/font は書体ごとに別の変数を出す。順序を利用側に委ねると保証が消える |
| 既定値は必ず持つ | `var(--x, )` は空を返し、`font-family: , system-ui` で**宣言ごと無効になる**（教訓4） |
| display の既定は body の口へ落ちる | 専用の見出し書体を持つのは観測4本のうち1本。本文だけ差したとき見出しが system 書体に残るのは事故 |
| 口は**宣言しない** | 宣言するとフォールバックが効かなくなる。名前は `tokens.layers.json` が持つ（決定2-7） |

**差し込み口は `:root` に書く。** `--sg-font-stack-*` の `var()` は宣言された要素で置換されるため、
部分木で口を定義しても届かない。実測は [font-family.md](./experiments/font-family.md) の実験4。

#### 役割は2種類ある

サイズ役割（`caption` … `display`）に既定の書体を足したうえで、
**サイズと直交する書体だけの役割**を別に持つ。

```
--sg-text-body-family        サイズ役割の書体（サイズ・行高と3点で対）
--sg-text-numeric-family     サイズを持たない。段を持たないことが直交の印
--sg-text-numeric-variant    tabular-nums。書体だけ当てても桁は揃わない
--sg-text-code-family
```

`roles.md` の観測で `numeric` は eyebrow / 統計値 / 表ヘッダ / 凡例 / 目盛 と**全サイズ帯**に現れる。
1つの段に固定すると実需要を表せない。利用側は「サイズは caption、書体は numeric」と重ねる。

`label` は mono を既定にした。小さい大文字ラベルが mono で組まれているのは ichirizuka の観測による。

#### 記録: 原則7 に対して弱いもの — 2件

**1. `--sg-font-brand-mono-cjk` は実需要を観測していない。**
3つのスタックで形を揃えるために先回りで持った。等幅の和文書体を差す需要が
本当に現れるかは分かっていない。**現れなければ消す。**

**2. `label` に mono を割り当てた根拠は観測1件。**
「小さい大文字ラベルは mono」は ichirizuka だけの観測で、pylabo / holosphere は支持していない
（自己レビュー N1）。他のサイズ役割の書体割り当てが「本文か見出しか」という
構造から出ているのに対し、**これだけが1本のプロジェクトの趣味から来ている。**

既定を body にする案もあった。退けたのは、`label` という役割自体が
その観測から生まれたものだからである（[roles.md](./roles.md) のタイポグラフィ節）。
役割は採るが書体は採らない、という切り分けの方が恣意的になる。

**2本目で違う組み方を観測したら、そのときに割り当てを見直す。**

#### 同じ事実の2つの符号化

`tabular-nums`（`font-variant-numeric`）と `"tnum"`（`font-feature-settings`）の両方を持つ。
Tailwind v4.3.3 に `--font-*--font-variant-numeric` 修飾子が無く、
**アダプタ側は feature でしか書体と等幅数字を束ねられない**ため（実験2）。

### 決定 1-12: 密度は文脈である。骨格の余白だけが動く

> **Phase 2 の2本で観測した軸への対処。**
> [Issue #32](https://github.com/shun2218-dev/sashigane/issues/32)、
> 記録は [experiments/phase2-ichirizuka.md](./experiments/phase2-ichirizuka.md) と
> [experiments/phase2-holosphere.md](./experiments/phase2-holosphere.md)。

#### 観測

**同じ需要が、そのプロジェクトが持っている層で表現されていた。**

| | 密度をどこが持っているか |
|---|---|
| ichirizuka（コンポーネント無し） | CSS 変数 `--gap: 28px`（狭い画面で 22px） |
| holosphere（コンポーネント有り） | `PageContainer` の `px-4 sm:px-6` `py-8 sm:py-12`、`Card` の `p-4 sm:p-6 lg:p-8` |

**密度で動く余白はごく一部である。** holosphere の余白 572 箇所のうち、
ブレークポイントで動くのは **26 箇所（約 4.5%）**だけだった。
残りはコンポーネント内部の固定値で、画面幅と関係なく決まっている。

つまり密度の正体は「画面全体の余白」ではなく、**骨格の3箇所**である。

#### 決定: 骨格の余白をセマンティックにし、密度が段をずらす

> 決定2-3 は「spacing のセマンティックは**実需要が観測されるまで定義しない**。
> Phase 2 で ichirizuka に導入したときに、何が必要かが分かる」と書いていた。
> **2本の導入を終えて、必要なものが分かった。**

| 役割 | 何の余白か | 既定 | compact | comfortable |
|---|---|---|---|---|
| `--sg-space-page` | ページの左右 | 24px ✓ | 16px ✓ | 32px |
| `--sg-space-section` | セクション間の縦リズム | 48px ✓ | 32px ✓ | 64px |
| `--sg-space-surface` | 面の内側 | 24px ✓ | 16px ✓ | 32px ✓ |

✓ は観測がある値。**`comfortable` は3つのうち1つしか観測されていない**
（`Card` の `lg:p-8`）。残る2つは規則から出た外挿であり、値としては規則どおりだが
**需要は確かめていない。** 自動では選ばれないので、実害が出る前に観測が増える。

**値は実測と一致している。** holosphere の骨格の余白は、レスポンシブの対が
すべて**ちょうど1段**離れていた（`px-4`→`px-6` / `py-8`→`py-12` / `p-4`→`p-6`→`p-8`）。
ichirizuka の 28px → 22px はスケール外だが、**軸の需要としては同じもの**である（原則2）。

ランプは変えない。**密度が1段変わると、役割が参照する段が1段動く。**
面の文脈（決定5-12）とまったく同じ形である。

#### 既定は画面幅に従い、`data-sg-density` で固定できる

```css
@media (width < 40rem) { :root { /* compact */ } }
[data-sg-density="compact"|"default"|"comfortable"] { … }
```

テーマ（決定5-10）と同じ形で、固定用をメディアクエリより**後**に出して順序で勝たせる。
`comfortable` は自動では選ばれない。**観測されたのは2段だけ**で、
3段目は `Card` の `lg:p-8` 1件しかないため、明示したときだけ効く（原則7）。

**境界に `sm`（40rem）を選んだ理由。** 2件の観測は違う境界を指している。

| | 境界 |
|---|---|
| holosphere | `sm:` = 40rem。**Tailwind の段に載っている** |
| ichirizuka | 780px ≒ 48.75rem。**スケール外の ad-hoc な値**（`md` の 48rem に近い） |

原則2 に従い、スケールに載っている側を採る。ichirizuka の 780px は
`--gap: 28px` と同じく「軸の需要としては同じだが値は借りない」ものとして扱う。

#### なぜコンポーネントに任せないのか

holosphere は既に `PageContainer` と `Card` でこれを解いており、
Phase 3 のコンポーネントに持たせる選択肢もあった。

**原則6 が決め手になった。** ichirizuka は `dependencies` を増やさない規約を持ち、
**コンポーネントを受け取れない。** 密度がコンポーネントにしか無いと、
トークンのみの利用者には密度を表現する手段が残らない。

#### `page` が2つの意味を持つことについて

`--sg-color-bg-page`（面の1段目）と `--sg-space-page`（ページの左右余白）で
同じ語を使っている。カテゴリが違うので衝突はしない。

**別語にしない。** どちらも「ページという文脈」を指しており、
`bg-page` と `space-page` が同じ文脈に属することが名前から読めるほうがよい。

#### 動かないもの

**コンポーネント内部の余白は密度で動かない。** 実測の 95.5% がこれに当たる。
`gap-2` や `mb-4` は画面幅と関係なく決まっており、動かす理由が観測されていない。

文字サイズも動かさない。実測でブレークポイントに応じて動く文字サイズは
holosphere で4箇所（うち3件は `sm:text-4xl` という見出しの1段上げ）、
ichirizuka で2箇所しかなく、**見出しを画面幅で変えるという別の話**である。

### 決定 1-13: font-weight — 役割で持ち、値は差し替えられるようにする

> [Issue #53](https://github.com/shun2218-dev/sashigane/issues/53)。
> [#44](https://github.com/shun2218-dev/sashigane/issues/44) でアダプタが名前空間を
> 1行で落とすようにした結果、**`font-bold` が書けなくなった**ことで表に出た。
> それまでは列挙し忘れのおかげで素の Tailwind の値が通っており、
> **気づかれずに使えていただけ**である。

#### 観測（4本すべてのソースを読んだ）

| 太さ | ichirizuka | pylabo | holosphere | pdf-merge-app | 本数 |
|---|---|---|---|---|---|
| 400 | ×20 | ×8 | — | ×6 | **3** |
| 500 | ×25 | — | ×30 | ×36 | **3** |
| 600 | ×20 | ×14 | ×58 | ×13 | **4** |
| 700 | ×25 | ×18 | ×15 | ×2 | **4** |

**4段とも原則7 の「3回以上」を満たす。** それ以外の段（300 や 800）は**1件も無い。**

役割の割り当ても一貫していた。ichirizuka のセレクタを全件読むと次の形になる。

```
700  .value .load-value .goal-value .intensity-tile dd   大型数値・最強の強調
600  h2 .notice h2 .plan-phase .unit                     見出し
500  strong .masthead h1 .wordmark-ja                    やや強調・ラベル
400  th small span                                       既定
```

#### 決定: 既定値つきの差し込み口として持つ

```
--sg-font-weight-{役割}: var(--sg-font-brand-weight-{役割}, 既定)   プリミティブ
--sg-weight-{役割}: var(--sg-font-weight-{役割})                    セマンティック
```

| 役割 | 既定 | 用途（観測） |
|---|---|---|
| `base` | 400 | 既定 |
| `emphasis` | 500 | やや強調・ラベル・ボタン |
| `heading` | 600 | 見出し |
| `strong` | 700 | 大型数値・最強の強調 |

**太さは root から導けない。** そのうえ**使える段は書体が実装しているものに限られる。**
可変フォントなら連続だが、静的フォントに無い段を指定すると合成太字になり、
意図と違う見た目になる。**そして合成はエラーにならない**（教訓4）。
観測の中に両方の型があった——holosphere は可変フォント（Geist 100–900）で
`font-semibold` を58箇所使い、ichirizuka は静的フォントである。

そこで書体（決定1-11）と**同じ形**にした。システムは意見を持つ（既定を出す）が、
書体の実装に合わせて利用側が差し替えられる。**口は宣言しない。**
宣言すると `var()` のフォールバックが効かず、差していない口が空文字として解決されて
宣言ごと無効になる。

#### 口は `:root` に差す

```css
:root { --sg-font-brand-weight-heading: 800; }
```

**`:root` 以外に書いても効かない。** 口を読むのは `:root` で宣言されたプリミティブなので、
子孫に書いた値は誰にも読まれない。**エラーにはならない**（教訓4）。
書体（決定1-11）と同じ性質で、`tokens.css` のヘッダにも書いてある。

実ブラウザで確かめた。子孫に差しても 600 のまま、`:root` に差すと 800 になる。

#### 差した値は `tokens.js` に出ない

`tokens.js` は生成時に `var(口, 既定)` を**既定へ潰す。** そのため口に差しても
JS 側は既定を返す。**書体（決定1-11）も同じである。**

潰すこと自体は正しい（JS 側に `var()` を残すと、値として使った先で静かに壊れる）。
ただし決定2-6 が挙げた JS 側の実需要の1つは **OG 画像**であり、そこは
**まさに書体と太さを使う場所**である。**ずれてもエラーにならない。**

書体を含む話なのでここでは決めない。[Issue #71](https://github.com/shun2218-dev/sashigane/issues/71) に切った。

#### 役割名は書体の役割と衝突させない

**Tailwind では `--font-*`（書体）と `--font-weight-*`（太さ）が、どちらも
`font-{名前}` を作る。** 名前が衝突すると、片方が生成されないか、生成された規則の
中身が入れ替わる。**どちらもエラーにならない。**

そのため `body` `display` `label` は使わず、`base` `emphasis` `heading` `strong` にした。
**衝突していないことは検査が見ている。** クラスが「出たか」ではなく**規則の中身**を見て、
書体の役割には `font-family` が、太さの役割には `font-weight` が入っていることを
確かめる。役割名は生成物から取るので、役割を増やしても検査から漏れない。

実際に `base` を `body` に変えて**発火することを確かめた。**

```
✗ font-body が太さを当てていない（書体の役割名と衝突した可能性）
✗ font-body に書体が混ざっている。--font-body と衝突している
```

#### テキスト役割に束ねない

サイズ役割（`--sg-text-{役割}`）には行高・字間・書体を束ねているが、**太さは束ねない。**
太さはサイズと直交する。観測でも、同じ `h1` が ichirizuka では 500、
holosphere では 700 だった。`<strong>` やボタンのように**サイズ役割を持たない場所**にも
当てる必要がある。

#### 素の t シャツ語彙は出さない

`font-bold` `font-medium` `font-light` は**存在しない。** 太さは役割で書く。
`font-light`（300）は観測ゼロでもある。

#### 検討して退けた案

- **値を持たない（決定1-11 と完全に同じ）** — 差さないと何も効かない。
  書体名と違い、太さには**システムが意見を持てる既定**がある（観測が4本で一致している）
- **数値の段をそのまま出す（`--sg-font-weight-700`）** — 役割が無い。
  原則3 は役割で持つことを求めている

### 決定 1-14: 動きは骨組み表示だけを持つ。イージングは値を持たない

> [Issue #47](https://github.com/shun2218-dev/sashigane/issues/47)。
> Phase 2 の2本目で観測した穴 G5。**材料は揃っているのに出口だけが無かった。**

#### 観測（4本すべてのソースを読んだ。ビルド出力は除く）

| | ichirizuka | pylabo | holosphere | pdf-merge-app |
|---|---|---|---|---|
| 骨組み表示（pulse） | — | `@keyframes pulse` ×2 | `animate-pulse` **×40** | ×1 |
| `motion-reduce:` | `animation: none !important` | — | **×62** | — |
| イージング | — | `ease-in-out` | — | `ease-linear` ×4 / `ease-in-out` ×1 |
| **カスタム `cubic-bezier`** | — | — | — | — |

**骨組み表示だけが3本で観測される。** `spin` `accordion` `caret-blink` はどれも1本ずつで、
原則7 の「3回以上」に届かない。

**4本のどこにも自作の `cubic-bezier` が無い。** 使われていたのは CSS の組み込み語だけだった。

#### 決定: 骨組み表示だけを持つ

```css
@keyframes skeleton { 50% { background-color: var(--sg-color-deeper-bg) } }

[data-sg-skeleton] { animation: skeleton var(--sg-duration-loop-1) ease-in-out infinite; }
```

**周期はループスケールの中央の段から引く**（決定1-6）。ループは3段しかなく、
端に寄せる理由が無い。**値をここで決めない。**

**地の色を1段深い面との間で動かす**（下記の改訂）。骨組みは地しか持たないので、
色を動かしても文字の対比には影響しない。
骨組みの地の色は `data-sg-surface="inset"` で作る（決定5-12）。

**動きは外側、地の色は内側**に置く。行が揃って明滅する。

```html
<div data-sg-skeleton>
  <div data-sg-surface="inset"></div>
  <div data-sg-surface="inset"></div>
</div>
```

#### 道は1つ。`animate-*` は写像しない

**Tailwind にユーティリティを用意しない。** 用意すると、こうなる。

| 経路 | 動く | 動きを減らす設定 |
|---|---|---|
| `data-sg-skeleton` | ✓ | ✓ **トークン層が止める** |
| `class="animate-skeleton"` | ✓ | ✗ 利用側が `motion-reduce:` を書く |

**同じものに2つの道があって、片方だけが安全**という形になる。
面（決定5-12）でも hover（決定5-13）でも退けてきた形である。しかも忘れても何も言われない。

Tailwind の利用者も `tokens.css` を読み込むので、属性はそのまま使える。

#### トークン層が keyframes を持つ

**これはトークン層が「値」を超える。** それでも持つのは、`animation` ショートハンドが
`名前 周期 イージング …` を要求し、**名前の指す `@keyframes` が無ければ何も動かないから**である。
**エラーにはならない**（教訓4）。

#### 動かす量 — **改訂（2026-08-29）**

> **当初版を撤回した。** 透明度を `1 → 0.4` で動かし、`0.4` については
> 「pylabo の 0.25 と Tailwind 既定の 0.5 の中央付近に置いただけで**強い根拠は無い**。
> 不透明度を決めるときに見直す」と書いていた。決定1-15 で見直した。

```css
@keyframes skeleton {
  50% { background-color: var(--sg-color-deeper-bg); }
}
```

**地の色を「1段深い面」との間で動かす。** 動く量は elevation と同じ**面の梯子1段分**で、
新しい定数を持ち込まない。**根拠の無い値がトークン層から消えた。**

**`0%` と `100%` を書かない。** 書かなければ要素の現在の地の色が両端になるので、
面の色を変数として出さずに済む（決定5-12 改訂で塞いだ道を開け直さない）。

`--sg-color-deeper-bg` は面の文脈が控えている内部の値で、hover の規則と共有する
（決定5-13。以前は `--sg-color-hover-bg` という名前だったが、読む側が2つになったので
関係の名前に改めた）。どちらも読んでいるのは「1段深い面の地」という同じものである。

##### 申告する制約: 付ける先は面を名乗っている要素である

透明度は**子ごと薄める**ので、包んでいる要素に付けても動いた。色はそうならない。
`data-sg-surface` を持たない要素に付けると**動かす地が無く、`transparent` から補間される。**
**エラーにはならない**（教訓4）。

```html
<div data-sg-surface="inset" data-sg-skeleton></div>   <!-- 骨組みそのものに付ける -->
```

**サンプルページが実際に踏んだ。** 包んでいる `div` に `data-sg-skeleton` を付けており、
色に変えた瞬間に**動かなくなった**（見た目は「点滅しないだけ」なので気づきにくい）。
ブラウザで計算値を読んで見つけた。

#### 動きを減らす設定は、トークン層が尊重する

```css
@media (prefers-reduced-motion: reduce) {
  [data-sg-skeleton] { animation: none; }
}
```

**利用側の責務にしない。** 決定5-9 が「status は色だけで伝えてはならない」と決めたのと
同じ性質の制約で、**忘れても何も言われない**種類のものである。
`prefers-reduced-motion` は「見せない」ではなく「動かさない」なので、
アニメーションだけを止めて要素は残す。

観測でも holosphere が `motion-reduce:` を **62 箇所**で書いていた。
**書かなくて済むほうがよい。**

#### イージングは値を持たない

観測にカスタムの `cubic-bezier` が1件も無いので、**トークンとして値を持つ理由が無い。**

ただし `--*: initial`（決定3-3）が `--ease-*` も落としており、
**`ease-linear` は静的ユーティリティなので生きているのに `ease-in-out` は消えていた。**
食い違いなので `ease-in-out` だけ戻す。**戻すのは CSS の組み込み語であって、値ではない。**

```css
--ease-in-out: ease-in-out;
```

#### 検討して退けた案

- **`spin` などを一緒に持つ** — 観測1本ずつ。原則7 に届かない
- **keyframes を持たず名前だけ写像する** — Tailwind 既定の `pulse` に乗ることになるが、
  **素の CSS の利用者には届かない。** 原則4 は `tokens.css` 単体の利用者を一級として扱う
- **属性とユーティリティの両方を用意する** — 一度そうしたが、自己レビューで退けた。
  **Tailwind の経路だけが動きを減らす設定を尊重しなくなる**（上記）
- **イージングに独自のアンカーを置く** — duration や字送りと同じ形にはできるが、
  **観測がゼロ**である。需要が確かめられていないものを規則にしない（原則2）

#### 検査

- `test/tokens-css.test.ts` — keyframes とそれを使う規則が**対で**出ていること、
  周期がループスケール由来であること、**動きを減らす設定で止まること**、
  止める規則が動かす規則より後にあること。reduced-motion のブロックを消すと2件落ちる
- `scripts/check-tailwind-adapter.mjs` — **`animate-*` が1つも出ないこと**、
  アダプタが `@keyframes` を出していないこと（`tokens.css` と重複する）、
  `ease-in-out` と `ease-linear` が書けること

### 決定 1-15: 不透明度はスケールを持たない

> [Issue #83](https://github.com/shun2218-dev/sashigane/issues/83)。
> 決定1-14 が「スケールを持つべきかすら決めていない」と書いたまま残していた次元。
> `scripts/check-sample-page.mjs` の**見逃す範囲に名指しで載っていた。**

#### 薄められる幅はゼロである

各役割について「これ以上薄めると要件を割る」下限の α を、全360色相の最悪で取った。

| モード | text-muted | text-faint | accent | danger | accent-mark |
|---|---|---|---|---|---|
| 明色 | 0.924 | 0.986 | **1.000** | 0.960 | 0.983 |
| 暗色 | 0.584 | 0.879 | **1.000** | **1.000** | 0.378 |

**どの役割・どのモードでも割らない α は 1.000。** 決定5-2 が端点をちょうど 4.500 に
解いているので、`accent` は最悪の色相で余裕がゼロになる。**1% も薄められない。**

これは elevation（決定1-8 改訂）で暗色の明度差分が持てなかったのと**同じ理由**である。
保証を境界ちょうどまで解くと、後から何かを足す余地は残らない。

#### サンプルページ自身が踏んでいた

```css
.btn:hover { opacity: 0.88; }   /* .btn-primary / .btn-danger は塗りである */
```

要素の `opacity` は**塗りと文字を同時に下地へ寄せる。**
決定5-14 が「塗りの側から解いた」保証が、hover した瞬間に割れていた。

| | 塗りの上の文字（全360色相の最悪） |
|---|---|
| 通常 | **4.50:1** |
| `opacity: 0.88` の hover 中 | **3.17:1** |

`check:sample-page` は色を持ちうるプロパティしか値を見ないので**発火しなかった。**

#### 観測 — 用途はほぼ全部が「色を薄める」代用だった

**自作コードだけを数える。** pdf-merge-app の `opacity-50` 42件のうち**41件は
shadcn の生成コード**（`components/ui/`）で、開発者が書いたのは1件だけだった。
原則2 が言う「過去の実装は需要の観測に使う」の**「過去の実装」に生成コードは入らない。**

| 用途 | 値 | 出典 | sashigane での解き方 |
|---|---|---|---|
| 補助的な文字・アイコン ×7 | 0.7 | holosphere | `text-muted` / `text-faint`（段で持っている） |
| 無効状態 | 0.45 | pylabo | 未実装。観測1本なので持たない（原則7） |
| 棒グラフ・進捗バーの塗り | 0.75 / 0.85 | ichirizuka / holosphere | マークの段（決定5-7） |
| ドラッグ中のプレースホルダ | 0.5 | pdf-merge-app | 未実装。観測1本 |
| 明滅・出現 | 0.25 / 0→1 | pylabo / holosphere | 明滅は色で（決定1-14 改訂）。出現は 0→1 |

#### 決定: スケールを持たない。`0` と `1` だけを許す

`0` と `1` は「**見えない / 見える**」であって薄めではない。出現・退場の
アニメーションが観測されているので、ここは残す。

**中間の値は色で解く。** 薄い色が要るなら、それは**色の選択**であって不透明度ではない。

#### 検査にする（教訓3）

| 経路 | 検査 |
|---|---|
| 素の CSS | `check:sample-page` が `opacity` / `fill-opacity` / `stroke-opacity` の値を見る。**許すのは 0 と 1 だけ** |
| Tailwind | `check:token-usage` が `opacity-*` を落とす。`opacity-0` と `opacity-100` は通す |

**両方に要る。** 片方だけだと「同じものに2つの道があって、片方だけが安全」という形になる。
面（決定5-12）でも hover（決定5-13）でも動き（決定1-14）でも退けてきた形である。

`opacity-*` は**テーマを参照しない素の数値ユーティリティ**なので `@theme` では止まらない
（決定3-5）。決定3-5 は当初 `opacity-37` を「スケールを持たない次元だから対象外」と
していたが、**持たないと決めたので対象に入る。**

#### この決定が触れない範囲（教訓5）

**アルファを「色の選択」で一括りにしない。** 付ける先で壊れ方が違う。

| 書き方 | 何が起きるか | この決定で塞げているか |
|---|---|---|
| `opacity: 0.5` / `opacity-50` | 前景と背景が同時に下地へ寄る | **塞いだ** |
| `text-accent/50`（前景のアルファ） | **前景だけが下地へ寄る。壊れ方は上と同じ** | **塞いだ**（決定3-2 改訂） |
| `bg-danger/15`（塗りのアルファ） | 面が変わるのに前景が追随しない | **塞いだ**（決定3-2 改訂） |
| `oklch(… / 0.25)` を生成器が解いて出す | 色システムが対比を保証したうえで出す | 対象外（影がこれ） |

> **2行目と3行目は当初この決定では塞げていなかった。**
> [Issue #85](https://github.com/shun2218-dev/sashigane/issues/85) で
> 決定3-2 を改訂し、`/` 修飾子を色の役割に対して落とすようにした。
> `check:token-usage` が見る（`@theme` の管轄外なので lint でしか塞げない。決定3-5）。

3行目には**役割そのものが無い**という問題が残っていたが、**決定5-16 で解いた。**
淡い塗りは `--sg-color-{名前}-subtle` として持ち、その上の文字は塗りに対して解き直す。
**塞いだことで、表現手段が無い状態が見えるようになり、決めるところまで進んだ**
（[Issue #87](https://github.com/shun2218-dev/sashigane/issues/87)）。

4行目だけが本当に別種である。**生成器が解いて出したアルファ**は、
対比を保証したうえで出しているので不透明度の問題を持たない。影の色（決定1-8 改訂）がその例で、
濃さを値で決めず面の梯子1段分として解いている。

## 2. 命名規約

### 決定 2-1: プリミティブは index 統一

```
--sg-space-5        --sg-font-size-3       --sg-radius-2
--sg-duration-2     --sg-border-width-1    --sg-primary-500
```

> **例を差し替えた（2026-08-29、[Issue #91](https://github.com/shun2218-dev/sashigane/issues/91)）。**
> 当初は `--sg-elevation-1` と `--sg-blue-500` を挙げていた。前者は決定1-8 改訂で
> **落とした名前**（高さの数字は CSS のどのプロパティにも入らない）、
> 後者は**存在しない命名**である——色は決定5-1 で `primary` / `neutral` / status の
> ランプ名になった。決定2-1 は色システムより前に書かれている。
> **命名規約の例が、その規約に従っていない名前を挙げていた。**

**全カテゴリで index 統一。** 挿入耐性は今回の判断基準にならない。
全スケールが規則から生成されるため「段を挿入する」という操作が存在せず、
あるのは「規則を変えて全部再生成する」だけだからである。

判断基準は「プリミティブであることが一目で分かるか」。
**数字だけの名前は決して役割に見えない**ので、誤用がレビューで目に付く。

原則3が挙げた `--blue-500` は既にこの方式である。

### 決定 2-2: セマンティックは役割ベース

```
--sg-{category}-{role}-{variant}-{state}

--sg-color-bg-danger-hover
--sg-color-text-muted
--sg-color-border-focus
```

安定した軸から順に並べる。カテゴリ先頭にすると生成CSS・devtools補完・grep のすべてで同種がまとまる。
state を末尾に置くのは、state だけが実行時に切り替わる軸だからである。

### 決定 2-3: lint による層判別 — **改訂（2026-08-24）**

> **当初版の主張を撤回した。** 「`--sg-{category}-{数字}` はプリミティブ、
> `--sg-{category}-{単語}` はセマンティック。**1つの正規表現で層を判別できる**」
> と書いていたが、**自分の生成物に対して両方向に破れていた。**
> 経緯は [agent-failures.md](./agent-failures.md) の 2026-08-24 の記録。

| 種別 | 変数 | 何が起きるか |
|---|---|---|
| 偽陽性 | `--sg-text-heading-1` 〜 `-3`、`--sg-color-chart-1` 〜 `-5` | セマンティックなのに参照が禁止される |
| 偽陰性 | `--sg-radius-full` | プリミティブなのに参照が素通りする |

見出しレベルも系列番号も**本質的に数字**であり、名前を歪めてまで正規表現に合わせる理由がない。

#### 改訂後の規則

**層は名前の形ではなく、生成器が知っている事実で判定する。**

```
生成器 → dist/tokens.layers.json → lint が「セマンティックだけ」を許す
```

`tokenLayers()`（`src/output/layers.ts`）が、各 `*Vars()` の出力した CSS 行から
名前を取り出して2つの集合に分ける。手書きの一覧は作らない（決定2-6）。

`scripts/check-token-usage.mjs` は**セマンティックの集合に載っている名前だけを許す。**
表に無い `--sg-*` は、プリミティブでも打ち間違いでも等しく落ちる。
禁止するものを列挙するのではなく、許すものを列挙する（教訓5）。

#### index 統一（決定2-1）はそのまま

判別が正規表現でできなくなっても、**「数字だけの名前は決して役割に見えない」**
という決定2-1 の判断基準は変わらない。誤用がレビューで目に付くことに変わりはない。
失われたのは「lint を正規表現1つで書ける」という実装上の利点だけである。

#### 検査対象から外すもの

`apps/docs/public/standalone.html` は除外する。
`tokens.css` が単体で成立することを目で確かめる**検査用フィクスチャ**であり、
コンポーネントではない。プリミティブが解決することを見るのが目的そのものである。

加えて radius / duration のセマンティックは
**実需要が観測されるまで定義しない**と決めており（原則3・原則7）、現時点で代替が無い。

> **2026-08-26 追記。** spacing はここから外した。Phase 2 の2本を終えて必要なものが分かり、
> 骨格の3役割（`--sg-space-page` / `-section` / `-surface`）を定義した（決定1-12）。
> **コンポーネント内部の余白には依然としてセマンティックが無い。**
> 実測の 95.5% がそれに当たるが、役割として括れる形が見えていない。

### 決定 2-4: プレフィックスは `--sg-`

> **原則3の例（無プレフィックス）からの変更。**

Phase 2 で ichirizuka の既存 `:root` に重ねる。無プレフィックスでは名前衝突が起こりうる。
衝突は「動くが色が違う」という形で出るため CI で検出できず、目視で気づくまで残る。
これは避けるべき種類の失敗である。

### 決定 2-5: プリミティブは CSS に出力する

原則3の文面どおり、出力した上で lint により参照を禁止する。

より強い選択肢として「出力せず生成器の中間表現に留める」があり、
そちらは強制が lint ではなく構造になる。ただしセマンティック役割の洗い出しの精度に
完全に依存するため、現段階では採らない。
**v1 到達前に移行を検討する。**

### 決定 2-6: 他形式への変換は機械的に行う — **改訂（2026-08-24）**

```
--sg-color-bg-danger-hover  ↔  tokens['--sg-color-bg-danger-hover']  ↔  bg-danger-hover
```

手書きのマッピング表は作らない。

> **当初版の JS 側の形を撤回した。** `tokens.color.bg.danger.hover` のように
> ハイフンで機械的にネストすると書いていたが、実際の名前に当てると
> **40件中13件が衝突した。** 決定2-3 と同じ、1例からの一般化だった。

#### 何が衝突したか

値と入れ子が同じ名前を要求する組み合わせが13件ある。

```
color-danger    と color-danger-mark      → color.danger は文字列か、オブジェクトか
text-body       と text-body-leading
text-heading-1  と text-heading-1-leading
```

当初の例（`color-bg-danger-hover`）が成立するのは、
**`--sg-color-bg-danger` が存在しないから**にすぎない。

#### 改訂後の規則

**CSS 変数名をそのまま鍵にする。**

```js
tokens.light['--sg-color-danger']   // '#ca003d'
```

- 衝突が原理的に起きない
- `SemanticToken` 型とも、`var()` に渡す文字列とも一致する。**語彙が1つで済む**
- `DEFAULT` のような、CSS 側に対応物の無いキーを発明しなくて済む

書き味は `tokens.color.danger` に劣る。**それは受け入れる。**
名前を2種類持つコストの方が高い。

#### この出力の位置づけ

**生成時点の写しであって、実行時のテーマ切り替えには追随しない。**
CSS が届く場所では CSS 変数を使う。

これは「CSS の代わり」ではなく「**CSS が原理的に到達できない場所**のための別経路」である。
Phase 2 で観測した実需要は次の3つ（[experiments/phase2-ichirizuka.md](./experiments/phase2-ichirizuka.md)）。

| | JS 側の色 | CSS が届かない理由 |
|---|---|---|
| ichirizuka | 心拍 → 色の補間 | 実行時に値を計算する |
| holosphere | OG 画像の生成 | **サーバ側で描く。ブラウザもカスケードも無い** |
| pylabo | 講座ごとの識別色 | データに色が紐づく |

同じセマンティックが2形式に出るので**二重管理になる。**
`pnpm check:token-values` が出力どうしを突き合わせて一致を検査する。

#### JS 側が必要とするのは**色だけ**である（2026-08-29 に確かめた）

> [Issue #71](https://github.com/shun2218-dev/sashigane/issues/71)。
> 「差し込み口に差した値が `tokens.js` に出ない」ことを問題として立てたが、
> **holosphere の OG 画像の実装を読んで、需要が無いと分かった。**

`tokens.js` は `var(口, 既定)` を生成時に既定へ潰すので、**利用側が差した書体名や太さは
JS 側に出ない。** 上の表が挙げた実需要のうち OG 画像は「サーバ側で描く」ものなので、
**そこで書体と太さがずれるのではないか**と考えた。**ずれない。**

holosphere の `next/og`（satori）の実装はこうなっている。

| | 実装 | トークンから読むか |
|---|---|---|
| 書体 | `loadGoogleFont()` が **Noto Sans JP をサブセットしてバイナリで渡す** | **読まない。** satori は名前ではなくフォントファイルを要求する |
| 太さ | ローダが `weight: 400 \| 700` の**2つだけ取得する** | **読まない。** 取得したファイルにある太さしか出せない |
| 色 | `ACCENT = '#e879f9'` と**直書き** | **ここが需要である** |

**書体名も太さも、口に差した値を JS 側で読む理由が無い。**
satori はフォントファイルを渡す仕組みで、名前だけあっても描けない。
太さも「取得したファイルにある分」に縛られる。

**残る2本も読んだ。どちらも色だけである。**

| | 実装 | 何を読むか |
|---|---|---|
| ichirizuka `IntensityStrip` | ブラウザで描く**インライン SVG**。`fontFamily="var(--mono)"` | **書体は CSS 変数から読んでいる。** JS 側は色だけ |
| pylabo `CourseCard` | `style={{ '--accent': course.accent }}` | **データの色を CSS 変数へ流し込む。** 書体も太さも関係しない |

**3本とも、JS 側の需要は色である。** 色は差し込み口を持たない（primary から生成される）ので、
潰れて困る値がそもそも無い。

**さらに分かったこと。** 3つのうち **CSS が本当に届かないのは OG 画像だけ**である。
残る2本はブラウザで動いており、書体は現に CSS 変数から読んでいる。
決定2-6 が「CSS が原理的に到達できない場所」として3つ挙げたのは**広すぎた。**
ichirizuka と pylabo が JS を使うのは**値が実行時に決まるから**であって、
CSS が届かないからではない。

そのうえで、色の形式は **16進のままでよい。** satori の実装コメントは
「**flexbox と CSS の部分集合しか解さない**」と明言している。
`oklch()` を解すかは確かめていないが、**16進なら確実に通る。**
決定2-6 の改訂で「canvas は oklch を解する（実測）が satori は未検証」と書いた点は、
**確かめる必要が無くなった**——16進を出し続ける理由が、互換性ではなく需要の側から立つ。

**Issue #71 はこの記録をもって閉じる。** 需要が観測されたら開き直す。

#### 16進の丸めが保証を割っていた（改訂 2026-08-29）

> [Issue #52](https://github.com/shun2218-dev/sashigane/issues/52)。
> [#50](https://github.com/shun2218-dev/sashigane/issues/50) の自己レビューで見つけた。

決定5-2 は端点を要件**ちょうど**まで解く。**余裕がゼロである。**
`tokens.css` は `oklch()` をそのまま出すので影響しないが、
**`tokens.js` は16進に丸めるため、境界の段が丸めた瞬間だけ要件を下回る。**

全360色相 × 両モード × 全役割の **12960 通り**を測った。

| | 要件 | 最悪 | 割った件数 |
|---|---|---|---|
| 文字（`text-*` `accent` `status`） | 4.5 | **4.456** | **196 / 6480** |
| マーク（`*-mark` `chart-*`） | 3.0 | 3.093 | 0 |

**文字だけが割る。** マークは余裕があるので影響を受けない。

#### 決定: 要件を割ったときだけ、最も近い満たす16進へ寄せる

**「丸めで対比を落とさない」ではない。** それだと**半分の値が動く**
（全段 43560 件のうち 21560 件）。丸めは対比を上下どちらにも動かすので、
**要件を割ったときだけ**倒す。

寄せは **RGB 空間で最も近い**16進を選ぶので、明度だけでなく色相も彩度も動きうる。
**RGB の段数は知覚の量ではない**ので、知覚距離で測った。

```
ΔL 最大 0.0029   ΔC 最大 0.0020   ΔH 最大 14.11°   ΔEok 最大 0.0036
```

ΔH が 14° 出ているのは、**彩度がほぼ無い段では色相が定義できない**ためである。
実際の知覚距離 **ΔEok は 0.0036** で、決定5-5 の識別閾 0.08 も、
決定5-6 の改訂で「並べると差が見えた」とした 0.018 も大きく下回る。

どの役割にどの要件があるかは `colorRequirements()` が持つ。
**要件を持たないものは持たないと明示する。**

| 役割 | 要件 |
|---|---|
| `text-*` `accent` `status` | 文字 4.5:1 |
| `*-mark` `chart-*` `border-focus` | マーク 3:1 |
| `bg-*` | **無し。** 面そのものであって前景ではない |
| `border-subtle` `border-default` `border-strong` `chart-gridline` | **無し。** 装飾（決定5-12） |
| `on-*` | **無し。** 要件はあるが相手が**塗り**でページ地ではない（決定5-14） |
| `sequential-*` | **無し。** 帯として読めればよく特定の比を要求しない（決定5-11） |

**分類漏れは検査が捕まえる。** すべての `--sg-color-*` が
「要件あり」か「要件無しとして明示」のどちらかに入っていなければ落ちる。

#### 退けた案

- **端点の解に余裕を持たせる** — [PR #51](https://github.com/shun2218-dev/sashigane/pull/51) で試したところ、
  page 上の accent が1段濃くなり、決定5-7 の「濃いとくすんで見分けにくい」という
  目視判断に逆行した
- **`oklch()` を出す** — 「canvas が oklch を解さない」という当初の前提は、
  **いまのブラウザでは成り立たない**（実測。`ctx.fillStyle = 'oklch(...)'` は保持され、
  無効な値は拒否される）。ただし決定2-6 が挙げた実需要は
  **satori によるサーバ側の OG 画像**であり、**そちらは検証していない。**
  前提が崩れたことは記録するが、確かめずに形式を変えない
- **16進と oklch を併記する** — 利用側が選べるが、**16進を使う限り保証は成立しないまま**である。
  申告で扱う話になり、保証を成立させる解ではない

#### 検査

- `test/values.test.ts` — **全360色相**で、16進のまま要件を満たすこと。
  寄せる処理を外すと落ちる。分類漏れが無いこと
- 同 — **要件そのものが正しいこと。** 分類漏れは捕まっても、**間違った要件は捕まらない。**
  `accent` を誤って 3.0 にすると、検査はどれも 3.0 で判定するので通ってしまい、
  **保証が静かに緩む**（教訓4）。参照している段を**ランプごと**に役割と突き合わせる
  （段の番号だけでは足りない。明色では chart-2 と text-muted がどちらも 600 になる）
- 同 — **寄せが知覚できる量まで動かないこと。** 捕まえるのは「近傍探索をやめて大きく飛ばす」
  形の変更で、**近傍の中で最も遠い候補を選ぶ壊し方は捕まえられなかった**（探索半径が
  1〜2 で済むため知覚量に届かない）。**検査のコメントにそう書いてある**
- `scripts/check-token-values.mjs` — CSS と JS のずれを、**3つ同時に満たすときだけ**許す。
  素直な丸めが要件を割っていること／JS の値が満たしていること／
  ずれが RGB 各成分 4 段以内であること。**「違うが要件は満たす」だけでは通さない**
  （まったく別の色でも通ってしまう）

### 決定 2-7: 層は4種類ある — プリミティブ / セマンティック / 入力 / 内部

決定2-3 は層を2つ（プリミティブ・セマンティック）としていた。**書体で3つ目が要った。**
さらに hover の仕掛けで4つ目が要った（下記）。

`--sg-font-brand-*` は利用側が**定義する**名前である（決定1-11）。
参照してよい名前でも、参照を禁じる名前でもない。

| 種別 | 誰が定義するか | 参照 | 例 |
|---|---|---|---|
| プリミティブ | 生成器 | 禁止 | `--sg-font-stack-body` |
| セマンティック | 生成器 | 可 | `--sg-text-body-family` |
| **入力** | **利用側** | （定義するもの） | `--sg-font-brand-body-latin` |
| **内部** | 生成器 | **禁止** | `--sg-color-hover-text-muted` |

> **4つ目が要った（2026-08-27、決定5-13）。** hover の控えは、生成器が
> **自分の仕掛けのために**宣言する値であって役割ではない。参照されると
> hover していない要素に hover の色が乗る。プリミティブと同じく禁止側に置く。

`tokens.layers.json` に3つ目の集合を足し、`check-token-usage` は
**セマンティック ∪ 入力**を許す。差すこと自体は正当な行為であり、
「表に無い名前」として落とすと利用側が口を使えない。

**入力は生成物の中に宣言が無い。** 宣言すると `var()` のフォールバックが効かないためで、
他の2つのように出力行から名前を取り出せない。生成器が知っている事実として直接持つ
（`fontInputNames()`）。手書きの一覧ではないので決定2-6 とは矛盾しない。

`check:tokens-standalone` は「入力は宣言されていないこと」と
「入力への参照は必ずフォールバックを伴うこと」を検査する。

## 3. 生成物

| ファイル | 内容 | 依存 |
|---|---|---|
| `dist/tokens.css` | `--sg-*` の定義（プリミティブ + セマンティック） | なし |
| `dist/theme.css` | Tailwind v4 `@theme inline` アダプタ | Tailwind v4 |
| `dist/tokens.scss` | SCSS 変数 | なし |
| `dist/tokens.js` | セマンティックの**解決済みの値**（決定2-6） | なし |
| `dist/tokens.d.ts` | TS 型と `tokens.js` の宣言 | なし |
| `dist/tokens.layers.json` | 層の名前表。**配布物ではなく検査用**（決定2-3） | なし |

### なぜ Tailwind 用を分けるか

**Tailwind v4 に JS プリセットの概念はない。** CSS-first 設定に移行しており、
等価物は `@theme` ディレクティブを含む CSS ファイルである。

さらに v4 は固定の名前空間（`--color-*` / `--spacing-*` / `--text-*` / `--leading-*` /
`--tracking-*` / `--radius-*` / `--shadow-*` / `--breakpoint-*` / `--ease-*` / `--animate-*`）
からユーティリティを生成するため、**`--sg-color-danger` は Tailwind から見えない。**

そこで `@theme inline` で写像する薄いアダプタを別ファイルとして生成する。

```css
@theme inline {
  --color-danger: var(--sg-color-danger);
}
```

`@theme inline` は変数参照ではなく解決値を使うオプションで、まさにこの用途のためにある。

**Tailwind 対応が生成されたアダプタ1枚に閉じ込められること自体が、
トークン層が Tailwind 非依存であることの証明になる。**

### 決定 3-1: Tailwind v4 の動的 spacing を無効化する

> 当初「未解決」として Phase 1 に持ち越した論点。
> **実験（Tailwind v4.3.3）で確認し、決定に格上げした。** 実験記録は
> [experiments/tailwind-v4-spacing.md](./experiments/tailwind-v4-spacing.md)。

#### 問題

v4 の spacing 系ユーティリティは `--spacing` の乗算で動的生成される。

```
p-<number>  →  padding: calc(var(--spacing) * <number>);
```

`--spacing: 4px` を定義すると、**決定1-2 で除外した `p-5`(20px) `p-7`(28px) が
自動的に有効になる**ことを実験1で確認した。

#### 決定

```css
@theme inline {
  --spacing: initial;        /* 動的名前空間を無効化する */

  /* 名前は Tailwind の倍数規約に合わせる（決定3-3）。値は --sg-* から来る */
  --spacing-0:  var(--sg-space-0);   /*  0px */
  --spacing-1:  var(--sg-space-1);   /*  4px */
  --spacing-2:  var(--sg-space-2);   /*  8px */
  --spacing-3:  var(--sg-space-3);   /* 12px */
  --spacing-4:  var(--sg-space-4);   /* 16px */
  --spacing-6:  var(--sg-space-5);   /* 24px */
  --spacing-8:  var(--sg-space-6);   /* 32px */
  --spacing-12: var(--sg-space-7);   /* 48px */
  --spacing-16: var(--sg-space-8);   /* 64px */
  --spacing-24: var(--sg-space-9);   /* 96px */
}
```

**プリミティブの index と Tailwind の番号は一致しない。** アダプタが翻訳する（決定3-3）。

実験2で `--spacing: initial` により spacing ユーティリティが**一つも生成されなくなる**こと、
実験3で名前付きの段を定義するとその段だけが生成され `p-5` は生成されないことを確認した。

**スケール外の値は Tailwind から書けなくなる。lint ではなく構造で強制できる。**

`--spacing-*: initial` という書き方も等価に機能する（実験4）。
`--spacing: initial` の方が「動的乗算を止める」という意図が読み取りやすいため、こちらを採る。

#### 残る穴: 任意値記法

**任意値 `p-[20px]` `gap-[7px]` は依然として生成される。**

```css
.p-\[20px\] { padding: 20px; }
```

これは構造では塞げないため lint が必要。ただし**検査対象が任意値記法だけに狭まった**ため、
ルールは「Tailwind クラスの `[...]` 記法を禁止する」という単純な形で済む。
スケール外の数値クラスを列挙して弾く必要はない。

### 決定 3-2: アダプタは `@theme inline` を使う

実験5で、`--sg-*` を定義した CSS を `@import` した上で
`@theme inline` に写像すると、ユーティリティが生成されることを確認した。

```css
@theme inline { --color-danger: var(--sg-color-bg-danger); }
→ .bg-danger { background-color: var(--sg-color-bg-danger); }
```

`inline` の有無で出力が変わる（実験6）。

| | ユーティリティが参照するもの |
|---|---|
| `@theme inline` | `var(--sg-color-bg-danger)` — **`--sg-*` を直接参照** |
| `@theme`（inline なし） | `var(--color-danger)` — Tailwind の変数を経由（2段） |

不透明度修飾子（`bg-danger/15`）は**どちらでも機能する**。
`color-mix(in oklab, …)` に展開される。

> **撤回（2026-08-29、[Issue #85](https://github.com/shun2218-dev/sashigane/issues/85)）。**
> ここには続けて「status の淡い背景（roles.md で観測した 12〜15% の帯）は
> **アダプタ経由でそのまま表現できる**」と書いてあった。**取り消す。**
>
> この一文は決定5-13（面はアルファで作らない）と決定5-14（淡い塗りは
> ページ地との差が 3:1 に届かないので**別の決定として保留**）より前に書かれたもので、
> いまは両立していない。
>
> **アルファ修飾子は色の役割に対して使えない。** `check:token-usage` が落とす。
>
> | 書き方 | 何が起きるか |
> |---|---|
> | `text-accent/50` | 前景だけが下地へ寄る。**`opacity: 0.5` と結果は同じ**（決定1-15） |
> | `bg-danger/15` | 面が変わるのに**前景は面の文脈のまま残る**（決定5-12 と同じ穴） |
>
> 決定1-15 の測定によれば、どの役割も 4.5:1 を割らない α は **1.000**。`/99` でも割る。
> 生成器が解いた値が、利用側の1文字で別の値になる。
>
> **淡い塗りは表現手段が無くなる。** これは能力の後退ではなく、決定5-14 が
> 保留したままの状態を正しく反映したものである。半分だけ安全な道を残すより、
> 無い状態を見せるほうがよい（[Issue #65](https://github.com/shun2218-dev/sashigane/issues/65)
> で `--sg-color-bg-surface` を落としたのと同じ判断）。
>
> **行き先は [Issue #87](https://github.com/shun2218-dev/sashigane/issues/87) に残した。**
> 決めるべきことを決めていないことは機械的に検出できないので、
> 唯一の対処は明示的に列挙しておくことである（agent-failures.md）。

`inline` を採る理由は、**`--sg-*` を唯一のスイッチ点にするため**である。
inline なしだと Tailwind 側の `--color-danger` を上書きしても効いてしまい、
テーマ切り替えの入口が2つになる。

### 決定 3-3: アダプタは名前空間ごとに写像方針を変える

> 自己レビューで発見した。当初 `--sg-space-5` をそのまま `--spacing-5` に写像するコード例を
> 書いていたが、これは **`p-5` を 24px にしてしまう**（素の Tailwind では 20px）。
> Tailwind の数値は index ではなく**基準の倍数**を表す規約である。

#### 大原則: 名前空間は1行で全部落とす（2026-08-26 改訂）

```css
@theme inline {
  --*: initial;
  /* … 以降に写像を書く … */
}
```

リセットを書かないと**素の Tailwind の値がそのまま残る。**
実験で `bg-red-500` `rounded-2xl` `shadow-lg` `leading-tight` が生成されることを確認した。
`bg-red-500` が書ける時点で「トークンが唯一の正」は成立しない。

> **改訂の経緯。** 当初は所有する名前空間を10個**列挙**していた。
> [Issue #44](https://github.com/shun2218-dev/sashigane/issues/44) で
> **列挙し忘れた9個が素の Tailwind の値のまま通っていた**ことが分かった。
>
> `--container-*` `--font-weight-*` `--breakpoint-*` `--blur-*` `--drop-shadow-*`
> `--text-shadow-*` `--inset-shadow-*` `--perspective-*` `--aspect-*`
>
> `max-w-6xl` が 72rem を素の Tailwind から取っていた。**原則1 が成立していなかった。**
>
> 教訓5 がそのまま当たった例である。禁止リスト方式は、リストに無いものを黙って通す。
> `--*: initial` は**Tailwind が将来足す名前空間にも効く**ので、列挙し忘れが起こらない。
> 実験で全名前空間に効くことを確認した。

#### 落としたまま写像しない名前空間

`--*: initial` は所有していないものまで落とす。**落としたままにするものを明示する。**

| 名前空間 | 扱い | 理由 |
|---|---|---|
| `--container-*` | 落とす | container 幅は利用側の責務（決定1-10）。必要なら利用側が `@theme` で足す |
| `--aspect-*` | 落とす | 媒体の比率であってデザイントークンではない |
| `--font-weight-*` | **写像する** | 太さの役割（決定1-13）。`font-base` / `font-emphasis` / `font-heading` / `font-strong`。素の t シャツ語彙（`font-bold`）は落とす |
| `--shadow-*` | **写像する** | 浮きの役割（決定1-8 改訂）。`shadow-raised` / `shadow-overlay` / `shadow-front`。素の t シャツ語彙は落とす |
| `--blur-*` / `--drop-shadow-*` / `--text-shadow-*` / `--inset-shadow-*` / `--perspective-*` | 落とす | 奥行きの表現だが、観測4本に1件も無い（原則7） |
| `--breakpoint-*` | **写像する** | 決定1-10。落としたままだと `sm:` が1つも書けない |

#### `@theme` の管轄外にあるもの

`--*: initial` で落ちるのは**テーマ由来の値だけ**である。次は落ちない。

- **素の数値ユーティリティ** — `duration-137` `z-42` `opacity-88` `rotate-17`
  `order-9` `grid-cols-13` など。テーマを参照しないので `@theme` では止まらない。
  `duration-137` は決定1-6 のスケールを素通りする。**`p-5` と同じ性質の穴**で、
  対処は [#55](https://github.com/shun2218-dev/sashigane/issues/55) で検討する
- **静的ユーティリティ** — `aspect-square`（`aspect-ratio: 1/1`）のように
  値がユーティリティ側に埋まっているもの

**「素の Tailwind の値が1つも出ない」とは言えない。** 言えるのは
「テーマ由来の値は1つも残らない」までである。

#### 写像方針は名前空間の性質によって3通りに分かれる

**(1) 数値が倍数規約の名前空間 → 倍数で写像する（spacing）**

我々のスケールは倍数に直すと `0,1,2,3,4,6,8,12,16,24` となり、
**全段が素の Tailwind に存在する段と値まで一致する。**

| `--sg-space-N`（index） | 値 | Tailwind 名 | 素の Tailwind |
|---|---|---|---|
| 0〜4 | 0/4/8/12/16px | `p-0`〜`p-4` | 一致 |
| 5 | 24px | `p-6` | 一致 |
| 6 | 32px | `p-8` | 一致 |
| 7 | 48px | `p-12` | 一致 |
| 8 | 64px | `p-16` | 一致 |
| 9 | 96px | `p-24` | 一致 |

`p-5`(20px) `p-7`(28px) は我々のスケールに無いので定義しない。**存在しない段は名前も存在しない。**

**(0) 面は写像しない（color の一部）**

`--color-page` / `--color-surface` / `--color-inset` は**アダプタに出さない。**
面は `data-sg-surface` で宣言するものであり、塗るだけの道を残すと
前景がページ用のまま残って保証が崩れる（決定5-12）。

**(2) 語彙が値と対応する名前空間 → 値が一致する名前だけに写像する（radius）**

素の Tailwind v4.3.3: `xs=2 sm=4 md=6 lg=8 xl=12 2xl=16 3xl=24 4xl=32`(px)

| `--sg-radius-N` | 値 | Tailwind 名 |
|---|---|---|
| 0 | 0 | `rounded-none` |
| 1 | 4px | `rounded-sm` |
| 2 | 8px | `rounded-lg` |
| 3 | 12px | `rounded-xl` |
| 4 | 16px | `rounded-2xl` |
| — | — | `rounded-full` |

`xs`(2) `md`(6) `3xl`(24) `4xl`(32) は対応する段が無いので**定義しない。**

語彙が数値でないぶん、ずれても目立たず危険度が高い。
**値が一致しない名前に写像してはならない。**

**(3) 値が一致しない名前空間 → 素の語彙を捨てる（text）**

素の Tailwind: `xs=12 sm=14 base=16 lg=18 xl=20 2xl=24 3xl=30`(px)
我々: `11.24 / 12.64 / 14.22 / 16 / 20 / 25 / 31.25 / …`

一致するのは `base`(16) と `xl`(20) だけ。`2xl` は 24 対 25、`3xl` は 30 対 31.25 でずれる。

**t シャツ語彙を再利用してはならない。** セマンティック役割名を使う。

```css
--text-body: var(--sg-font-size-3);
--text-caption: var(--sg-font-size-2);
```

これは決定1-4 とも整合する。文字サイズは常に行高とペアで使われるべきなので、
プリミティブの段ではなくセマンティック役割が Tailwind に現れるのが正しい。

**(4) 修飾子が存在しない性質 → 別の名前空間へ出す（font-family）**

`--text-*--font-family` は**無視される**（実測: [font-family.md](./experiments/font-family.md)）。
書体は `--font-*` 名前空間へ出す。

```css
--font-*: initial;                                  /* font-sans / font-mono / font-serif を消す */
--font-body: var(--sg-text-body-family);
--font-numeric: var(--sg-text-numeric-family);
--font-numeric--font-feature-settings: var(--sg-font-feature-tabular);
--default-font-family: var(--sg-text-body-family);       /* preflight の html */
--default-mono-font-family: var(--sg-text-code-family);  /* preflight の code */
```

出すのは `roles.md` が観測した5つの書体役割（body / display / label / numeric / code）だけ。
サイズ役割は8つあるが書体は3通りしかなく、全部を写像すると
`font-heading-1` のような**サイズ役割と紛らわしく中身が同一**のユーティリティが並ぶ。

`--default-font-family` の差し替えを忘れると、preflight が素の Tailwind のスタックへ戻り
**本文だけがトークンの外側に残る。エラーにならない**（教訓4）。検査に入れてある。

#### 副産物: 決定1-4 の「オーバーライド不可」が Tailwind 上でも成立する

`--text-*--line-height` を使うとサイズと行高がペアで出力される。

```css
--text-body: var(--sg-text-body);
--text-body--line-height: var(--sg-text-body-leading);
```
```css
.text-body {
  font-size: var(--sg-text-body);
  line-height: var(--tw-leading, var(--sg-text-body-leading));
}
```

> **名前を実際の出力に合わせた（2026-08-29、Issue #91）。** 当初は実験記録
> （[experiments/tailwind-v4-spacing.md](./experiments/tailwind-v4-spacing.md)）の
> 手書きの入力をそのまま引いており、`--sg-line-height-3` と書いてあった。
> **行高にその名前は無い。** 3系統あるので `--sg-line-height-{display|ui|prose}-N` で、
> 写像が参照するのは**セマンティックの** `--sg-text-{役割}-leading` である（決定1-4）。

`var(--tw-leading, …)` はフォールバック構造なので、これだけでは `leading-*` で上書きできる。
**`--leading-*: initial` と `--spacing: initial` を両方入れると上書き手段が消滅する**
（`leading-tight` は名前付き、`leading-7` は `--spacing` 由来の動的生成なので、両方止める必要がある）。

実験で陽性・陰性の両方向を確認した。

### 決定 3-4: 生成物のヘッダは配布先で意味を成す形にする

> Phase 2 で ichirizuka にコミットした `app/tokens.css` の先頭は
> 「規則と根拠は docs/decisions.md を参照」と書いていた。
> **配布先にその文書は無い。**（穴9、[Issue #34](https://github.com/shun2218-dev/sashigane/issues/34)）

レジストリ方式（原則6）では生成物が利用側リポジトリへ落ちる。
落ちた先には `docs/` も、「原則3」という番号の定義も無い。

#### ヘッダは1箇所で持つ

`src/output/header.ts` の `outputHeader()` が5つの生成物すべてに同じヘッダを出す。
手書きで散らすと、直したつもりで1つ残る。

| 入れるもの | なぜ |
|---|---|
| ツール名（`@sashigane/tokens`） | 落ちた先で「何が作ったか」が分かる唯一の手がかり |
| **規則の在り処（絶対 URL）** | 本文に散っている「決定1-2」がこれで解決できる |
| 見出し番号が何を指すかの1行 | 番号だけでは、URL を開いても何を探すか分からない |
| primary の色相と段 500 | どの入力から出た生成物かが分かる。色を変えれば変わるので、意味のある diff |

| 入れないもの | なぜ |
|---|---|
| **生成日時** | 内容が同じでも毎回 diff が出て、利用側が「更新された」と誤認する |
| ~~**バージョン**~~ | **入れることにした（決定4-6）。** 落ちた先で「どのスナップショットを持っているか」を知る手がかりがこれしかない。生成日時と違い、動くのはリリースのときだけである |

#### リンク先は1行で差し替えられる

`DOCS_URL` は今リポジトリの `docs` を指しており、`HEAD` 参照なので決定を足しても古びない。
**v1 の前にドキュメントサイトを用意する予定で、そのときはこの定数だけを変える。**
生成器の他の部分は何も変わらない。

> **決めた（決定4-6）。** **リリース済みならタグに固定し、未リリースなら `HEAD` を指す。**
> 固定する理由は、ここに書いたとおり「配布された生成物より新しい決定を読む」のを防ぐためである。
> 未リリースのあいだ `HEAD` にするのは、固定する先が無いからである。

#### 検査

`pnpm check:output-header` が、全生成物について次を見る（教訓3）。

- 共通ヘッダで始まり、在り処が絶対 URL で書かれていること
- **リポジトリ相対のパスが本文に残っていないこと** — 穴9 そのもの
- 日時のような生成のたびに変わる値が入っていないこと

「同じ入力から同じ出力が出る」ことは `packages/tokens/test/output-header.test.ts` が見る。
**生成日時を入れた瞬間に落ちる。**

### 決定 3-5: 素の数値ユーティリティは lint でしか塞げない

> [Issue #55](https://github.com/shun2218-dev/sashigane/issues/55)。
> [#44](https://github.com/shun2218-dev/sashigane/issues/44) の自己レビューで見つけた。

#### 事実

決定3-1 は `--spacing: initial` で `p-5` を**構造的に**生成されなくした。
しかし v4 には**テーマを参照しない素の数値ユーティリティ**があり、`@theme` では止まらない。

候補を並べてコンパイルすると、**試した中で20個が生成された。**

```
z-42  order-9  col-span-13  row-span-7  aspect-3/4  scale-77  rotate-17  skew-9
grid-cols-13  opacity-37  delay-137  duration-0  duration-137  border-3
outline-3  ring-3  inset-ring-3  stroke-3  line-clamp-13  flex-13
```

> **これは全体の数ではない。** 私が候補として並べたクラスの中で生成されたものが20個だった、
> というだけである。**一覧は列挙で網羅できない**（Tailwind の全ユーティリティを
> 知らないと数えられない）。教訓2 の「測れるもので測っただけの結論を、
> 問いへの答えとして扱わない」に当たる。
>
> Issue は7個としており、そこに `border-3` が無かった。
> **決定1-7 の border-width スケールも素通りしていた。**
> （`font-750` は生成されない。決定1-13 は穴を開けていない。
> `divide-x-*` も実測では生成されない）

**この決定は列挙に依存しない。** 塞ぐ対象を「素通りするもの一覧」ではなく
**「スケールを持つ次元」の側から決めているので、一覧が不完全でも設計は変わらない。**
プレフィックスを増やせば同じ形で塞げる。

#### 対象はスケールを持つ次元だけ

生成されたもののうち、トークンがスケールを持っているのは **border-width（決定1-7）** と
**duration（決定1-6）** の2次元だけである。

`z-42` `order-9` `rotate-17` `scale-77` `skew-9` `col-span-13` `row-span-7`
`grid-cols-13` `aspect-3/4` は**スケールを持っていない次元**で、トークンの管轄ではない。
弾き始めると、**決めていない次元をトークンの管轄に引き込む**ことになる（原則7）。

> **`opacity-*` はここから外れた（2026-08-29）。** 当初はこの一覧に `opacity-37` が
> 入っていた。決定1-15 で「**持たない**」と決めたので、決めていない次元ではなくなった。
> 弾く理由も逆で、段の外の値だからではなく**次元そのものを使わせない**ためである。
> `opacity-0` と `opacity-100` は「見えない / 見える」なので通す。

#### 段の中は写像で塞ぎ、段の外は lint で塞ぐ

**border-width は写像できる。** 名前は px に合わせる（決定3-3 の倍数規約と同じ考え方）。

```css
--border-width-1: var(--sg-border-width-0);   /* border-1 → 1px */
--border-width-2: var(--sg-border-width-1);   /* border-2 → 2px */
--border-width-3: var(--sg-border-width-2);   /* border-3 → 3px */
```

**写像するとスケールの段は素の数値を上書きする。** 方向つき（`border-t-3` `border-x-3`）も
同じ名前空間を使うことを実測で確かめた。段の外（`border-4`）は Tailwind が素の px で
作り続けるので、そちらは lint が塞ぐ。

**duration は写像できない**——**と書いたが、誤りだった。**

> **訂正（2026-08-29、Issue #72）。** 「小数を鍵にできない」と書いたのは
> **エスケープの書き間違い**である。`--transition-duration-141\.4` は正しく効き、
> `duration-141.4` が生成される。**測り方を間違えて「できない」と結論していた。**
> √2 刻みのスケールは**全段そのまま届く。** 写像した。

同じ確かめ直しで、`--outline-width-*` `--ring-width-*` も効くと分かった。
**決定1-7 は「2 = フォーカスリング」と用途まで書いている**のに、
Tailwind では別の名前空間なので届いていなかった。こちらも写像した。

**写像するのは遷移の5段だけである。** 決定1-6 は遷移とループを
**知覚上の制約が違う別スケール**としている。同じ名前空間（`--transition-duration-*`）に
混ぜると、**ループの値を hover の遷移に当てられて**しまい、別スケールにした理由が
Tailwind の経路で消える。しかも書けてしまうので誰も気づかない。

**ループ周期に Tailwind の出口は要らない。** アニメーションは `data-sg-skeleton` の
1本である（決定1-14）。素の CSS からは `var(--sg-duration-loop-*)` で読める。

**`delay-*` は写像しない。** 観測4本に `transition-delay` が1件も無い（原則7）。
`inset-ring` `stroke` も同じ理由で写像しない。

#### `@theme` では構造的に止められない

決定3-1 は「動的生成を止める」ことで**書けなくした。** 素の数値ユーティリティは違う。
**テーマを一切参照しないので、テーマ側から止める手段が無い。**

そのため **lint が唯一の防御になる。** 教訓3 は「機械的に検査できるものは文書ではなく
検査にする」と言っているが、ここは**検査にしかできない**。
`p-5` と違って**手元で書けてしまい、CI で初めて落ちる。**

#### 許す数値は生成物から取る

lint が許す数値は `theme.css` の `--border-width-*` / `--transition-duration-*` から読む。
**手で並べない。** 写像を増やせば自動で通るようになり、写像を消せば自動で落ちる。

#### 検査

`scripts/check-token-usage.mjs` が `bare-number` として報告する。陰性対照は両側を持つ。

- 落ちる: `duration-137` `delay-137` `border-4` `border-t-8` `md:hover:border-4`
  `@apply border-4`（変種つき・方向つき・`@apply` の中でも見つかること）
- 落ちる: `opacity-88` `hover:opacity-50`（**持たないと決めた次元**。決定1-15）
- 落ちる: `text-accent/50` `hover:bg-danger/80` `border-accent-mark/20` `bg-chart-1/15`
  `@apply text-muted/70`（**アルファ修飾子**。決定3-2 改訂、Issue #85）
- **落ちない**: `border-1` `border-2` `border-3` `border-t-2` `md:border-x-3`
  （写像した段）／`z-42` `order-9` `rotate-17` `grid-cols-13`
  （スケールを持たない次元）／`opacity-0` `opacity-100`（見えない / 見える）／
  `w-1/2` `top-1/2` `aspect-3/4` `basis-1/3`（**分数の `/`**。アルファではない）

アルファの判定は**写像した色の役割名を生成物から読んで当てる。**
`/` の手前が役割名で終わっているかを見るので、分数と取り違えない
（`bg-chart-1/15` のように**役割名が数字で終わっていても**区別できる）。
禁止する記号を並べる形にすると、`w-1/2` を巻き込むか、
巻き込まないように書いたつもりで抜け道を作るかのどちらかになる（教訓5）。

`scripts/check-tailwind-adapter.mjs` は、写像した段が**我々の値を指していること**を
中身まで見る。索引で写像すると `border-2` が 3px になり、素の Tailwind と食い違う。

#### 見逃す範囲（申告）

**`inset-ring-<n>` `stroke-<n>` は塞いでいない。** 物理的には border-width と同じ
「幅」の次元だが、**観測がゼロ**なので写像しておらず（原則7）、段の集合が空になる。
需要が観測されたら写像し、同じ形で塞がる。

（`outline-<n>` `ring-<n>` は 2026-08-29 に写像して塞いだ。Issue #72）

**`0` は弾かない。**「無し」であってスケールの外の値ではない。
`border-0` `ring-0` は境界や輪郭を消す書き方で、`--sg-space-0: 0` が段として
存在するのと同じ性質を持つ。**段の外の値を弾く検査が、消す手段まで奪ってはいけない。**

**そして、この一覧自体が網羅でない。** 上に書いたとおり、素通りするユーティリティを
列挙で数え切ることはできない。**塞げていないものが他にもある前提で読む。**
見つけたら `SCALED_BARE` にプレフィックスを1つ足せばよい。

## 5. 色

> **色は静的な値の集合ではない。** 利用者が primary を1色選ぶと、
> セマンティックまで含めた全パレットが生成される関数として実装する。
> 生成物は提案であり人間が編集できるが、保証が崩れる入力・編集には警告を返す。

### 前提の訂正: 明度を揃えてもコントラストは揃わない

原則5 は「明度ステップを揃えることでコントラスト比が構造的に保証される」としているが、
**測ると成立しない。**

OKLCH の `L` は知覚的明度、WCAG のコントラストは相対輝度から計算される。この2つは一致しない。
同じ `L` のまま色相だけ変えたときの、白に対するコントラスト比:

| L | C | 最小 | 最大 | 振れ幅 |
|---|---|---|---|---|
| 0.55 | 0.05 | 4.73 | 4.99 | 1.06倍 |
| 0.55 | 0.15 | 4.54 | 5.27 | **1.16倍** |

最も暗く出るのは一貫して H≈150〜175°（緑〜シアン）。

**振れ幅は有界なので、「最悪の色相でも目標を満たす明度」を段の定義にすれば保証は成立する。**
原則5 の意図は守られるが、規則は「L を揃える」ではなく「最悪ケースから L を解く」になる。

---

### 決定 5-1: 入力は primary 1色。受け継ぐのは色相のみ

`L` と `C` は規則が決める。選んだ色に最も近い段を primary とし、
**元の色とのズレが閾値を超えたら警告する。**

| 警告 | 条件 |
|---|---|
| `primary-chroma-unreachable` | 選んだ彩度がその明度で sRGB に収まらない |
| `primary-lightness-shifted` | 選んだ明度に一致する段がない |
| `status-too-close-to-primary` | primary と status の色相が近すぎる |

### 決定 5-2: 明度は11段。端点を保証境界に解く

段は `50, 100, 200, 300, 400, 500, 600, 700, 800, 900, 950`。

**アンカー段（500）と下端（950）を、下記の要件をすべて満たすぎりぎりまで解く。**
上端（0.97）だけが固定。

| 面 | 段 | 目標 | 用途 |
|---|---|---|---|
| 50（明色） | 500 | 4.5:1 | 本文 |
| 50（明色） | 400 | 3:1 | UI 部品 |
| 950（暗色） | 400 | 4.5:1 | 本文 |
| 950（暗色） | 500 | 3:1 | UI 部品 |

**端点を固定値で持つことはできない。**
面は純白でも純黒でもなく、その明るさも彩度も primary に依存し、
さらに彩度はセット単位でも変わる。生成のたびに解き直す必要がある。

全360色相で検証した結果、拘束条件はちょうど境界に着地する（4.500 / 4.500 / 3.000）。
解いた端点の範囲は アンカー `0.531〜0.536`、下端 `0.161〜0.225`。

> **範囲の注記（2026-08-26）。** この表の「面」は **`bg-page`（50 / 950）だけ**を指す。
> 端点を解く相手は1段目に限られ、**深い面まで含めて解くと解が存在しない**（測定済み）。
> `bg-surface` / `bg-inset` の上での保証は、端点ではなく
> **役割が参照する段をずらして**成立させる。決定5-12 を参照。

**暗色モードは色を反転しない。参照する段を変えるだけで成立する。** ランプ1本で両モードが出る。

### 決定 5-3: 彩度は「同じ場面に並ぶセット」単位で揃える

| 対象 | 彩度 | 理由 |
|---|---|---|
| primary | 色相ごとの最大 | 単独で使われる。揃える相手がいない |
| **status 4色** | **色相ごとの最大** | 下記（再改訂） |
| 識別色 5色 | セット内で共通 | 系列は互いに対等であるべき |
| 中間色 | 全定義色相の共通値 × 0.2 | 下記 |

> **再改訂あり。** status もセット内で揃えていたが、テーマビルダーで目視して
> **danger だけが大きくくすんでいる**ことが分かった。
>
> | 色相 | セット共通 | 単独なら取れるC | 単独なら |
> |---|---|---|---|
> | danger | `#a84b53` | 0.213 | **`#ca003d`** |
> | warning | `#9e5900` | 0.123 | `#9e5900` |
> | success | `#078150` | 0.125 | `#008250` |
> | info | `#0c73ad` | 0.127 | `#0073af` |
>
> **共通値を引き下げていたのは warning（黄系）で、損をしていたのは danger だけ。**
> 赤はこの明度で高い彩度を保てるのに、黄に合わせて削られていた。
> `#a84b53` は危険を伝える色として弱い（Tailwind red-600 は `#dc2626`）。
>
> 代償として danger だけ彩度が高くなり、バッジが並ぶと danger が最も強く見える。
> **これは意味の上で自然**なので受け入れる。「同じ段は同じ強さ」より
> 「危険が伝わる」を優先する。
>
> 識別色は共通のまま。系列は互いに対等であるべきで、特定の系列だけ強く見える理由がない。

> **改訂あり。** 当初「定義した色相集合内での最大 C」を全ランプ共通にしたが、
> 識別色5色が色相環を一周するため、制約が全360色相とほぼ同じになっていた。
> `#e879f9` を選んでも `#875a8d` が生成され、**ブランドカラーとして機能しなかった。**

| primary | 全ランプ共通のとき | セット単位のとき |
|---|---|---|
| `#3b82f6` | `#4d6ea3` | **`#0061e6`** |
| `#e879f9` | `#875a8d` | **`#aa00bf`** |

識別色の彩度が伸びないのは、5色が互いに見分けられる必要があるため。
**チャート系列に必要なのは鮮やかさではなく識別性**という判断で受け入れる。

中間色の係数 0.2 は実測と一致することを確認した。

| 段 | 規則の出力 | 実測 |
|---|---|---|
| 900 | 0.0128 | pylabo dark bg = 0.0128 |
| 400 | 0.032 | pylabo `--line` = 0.030 |
| 50 | 0.0028 | ichirizuka `--card` = 0.0021 |

### 決定 5-4: status の色相は意味で固定し、±8° まで primary に引き寄せる

基準色相は実測から決めた。

| | 基準 | 根拠 |
|---|---|---|
| danger | 25° | Tailwind red-500 = 25.3° / pylabo err = 27.3° |
| warning | 70° | Tailwind amber-500 = 70.1° / ichirizuka amber = 79.6° |
| success | 150° | Tailwind green-600 = 149.2° / pylabo ok = 150.1° |
| info | 250° | blue = 262.9° / sky = 237.3° |

**引き寄せ幅を小さく（±8°）取るのは、色相の統一より意味の保存を優先するため。**
`roles.md` の観測（pylabo が「赤系は採点の失敗色と紛れるため実践は紫にしている」と記録）のとおり、
色の意味は文化的に固定されている。primary から相対角度で導出すると「青い danger」が生まれる。

色調の統一は**中間色の着色と L / C の共有**が担う。実際、引き寄せ率を上げても
上限角ですぐ飽和し、primary との角距離が縮んで識別性が下がるだけだった。

primary が status に近すぎる場合は許容域内で離し、
最小角距離（20°）を満たせなければ警告する。

### 決定 5-5: 識別色は primary から等間隔、status 帯を回避

系列数は 5。status の周囲 18° に入ったものは禁止帯の縁へ寄せる。

#### 根拠を訂正し、上限を宣言した（2026-08-28）

> [Issue #48](https://github.com/shun2218-dev/sashigane/issues/48)。
> Phase 2 の2本目で観測した穴 G6。

**当初の根拠は「holosphere が4系列、shadcn が5系列」だった。これは片方しか見ていない。**

holosphere には配信カテゴリごとの色が**10色** TS に直書きで存在する
（`CATEGORY_COLORS`。2026-08-05 から在り、観測日より前）。
4系列のチャートと10分類のチャートが**同じリポジトリに両方ある。**
決定5-5 は前者だけを見て 5 と決めていた。

**それでも 5 は変えない。数の問題ではなかったからである。**

#### 色で区別してよい上限は 6（測定）

上限を決めるのは色相ではなく**段**である。

**色相だけでは 4 色すら分けられない。** 段を固定して色相を N 等分し、
二色覚下の最小知覚距離を全起点で測ると、閾値 0.08 に届くのは3色（しかも起点による）までだった。

| 色数 | 3 | 4 | 5 | 7 | 10 |
|---|---|---|---|---|---|
| 最良（色相だけ） | 0.083 | 0.059 | 0.028 | 0.019 | 0.012 |

これが決定5-8（系列ごとに段を変える）の理由である。**段が識別を担っている。**

したがって**使える段の数が系列数の上限になる。**
マークは面に対して 3:1 を満たす必要がある（決定5-7）ので、使える段は限られる。

| モード | 面 | マークとして使える段 | 段数 |
|---|---|---|---|
| 明色 | 50 | 400 / 500 / 600 / 700 / 800 / 900 / 950 | **7** |
| 暗色 | 950 | 50 / 100 / 200 / 300 / 400 / 500 | **6** |

**識別色のランプで測っている。** primary とは別のランプで彩度も違う（決定5-3）。
いまは primary で測っても同じ集合になるが、**それは結果であって根拠ではない。**

段の割り当てを**探索して見つかった**最良の最小距離（総当たりではないので**下限**である）：

| 色数 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|
| 明色 | 0.220 | 0.153 | 0.127 | 0.101 | 0.082 |
| 暗色 | 0.219 | 0.180 | 0.132 | 0.101 | **段が足りない** |

**両モードで成立する上限は 6 である。** 暗色の使える段が6段しかないためで、
7色目は明色なら 0.082 で辛うじて閾を超えるが、暗色では置く段が無い。

**この結論は探索の精度に依らない。** 6色が成立することは、閾を超える割り当てが
**実在する**（探索が見つけた）ことで示される。7色が成立しないのは**段の数**の話で、
どれだけ探索しても6段に7色は置けない。表の数字は「少なくともこれだけは出る」という下限である。

**これは面 `page` での上限である。** 深い面では使える段がさらに減る（決定5-12）。

#### 上限を超える分類はどうするか

**色だけで区別しない。** 決定5-9 は「status は色だけで伝えてはならない」と決めており、
識別色にも同じことが当たる。

観測側も既にそうしている。holosphere は10分類に凡例とスクリーンリーダ用の表を併記し、
ソースにも「color is never the only channel」と書いている。
**10色目の `other` は中間色（slate）である** ——色相ではなく「その他」の受け皿として置かれている。

**上限を超えたら `other` に畳むか、色以外のチャネルを併用する。**
トークンは 6 を超える識別色を出さない。

#### 検査

`packages/tokens/test/color.test.ts` が、`categorical.count` が
**両モードの使える段数を超えていないこと**を見る。段を増やさずに count だけ増やすと落ちる。

### 決定 5-7: セマンティックの割り当ては「文字か、そうでないか」で段を変える

テーマビルダーで目視して分かったこと。

チャートの線・点・境界線は**文字ではないので 3:1 で足りる**（WCAG の非テキストコントラスト）。
文字と同じ段（明色モードの 500）を使うと沈んで見分けにくくなる。

| 用途 | 明色モード | 暗色モード | 必要なコントラスト |
|---|---|---|---|
| 文字 | 500 | 400 | 4.5:1 |
| マーク（線・点・境界） | 400 | 300 | 3:1 |

段500 で5系列を描いたときの実際の色:

```
#4c6da2 #8c5885 #995a3e #6a732f #007e76   ← 全部くすんで見分けにくい
```

段400 にすると:

```
#5f86c7 #ac6da3 #bc6f4e #838e3b #009b92   ← 見分けられる
```

**数値では気づけなかった。目で見て初めて分かった。**

### 決定 5-8: 識別色は系列ごとに段を変える

> **決定5-5 の補強。** 色相環に等間隔で配るだけでは、
> **二色覚のもとで系列が潰れる**ことが実測で判明した。
> 実験記録は [experiments/color-vision.md](./experiments/color-vision.md)。

全系列が同じ段（＝同じ明度・同じ彩度）だと、違いは色相しかない。
二色覚では色相軸が潰れるため、**2型色覚下で最小 ΔE が 0.003**（実質同一）まで落ちる。

```
2型色覚下  #6081c6 #7b85a1 #96894d #968841 #808593
                            ↑系列3   ↑系列4  ← 見分けられない
```

**系列ごとに段を変える。** 割り当ては通常＋二色覚3種すべてでの
最小知覚距離が最大になるものを全120通りから選ぶ（約 0.5ms）。
**探索であって恣意ではない。** 同じ入力からは必ず同じ結果が出る。

| | 使える段 | 最悪 ΔE |
|---|---|---|
| 明色モード | 400, 500, 600, 700, 800 | 0.085 |
| 暗色モード | 100, 200, 300, 400, 500 | 0.110 |

段の候補は**マークに必要な 3:1 を満たすもの**に限る（決定5-7）。
段300 は明色の面に対し 2.24:1 なので明色モードでは使えない。

#### 目標値 0.08 の根拠

既知のパレットを同じ指標で測って較正した。

| パレット | 最小 ΔE |
|---|---|
| **Okabe-Ito 5色**（色覚配慮設計の定番） | **0.086** |
| shadcn chart-1..5 | 0.047 |
| Tailwind 500 を5色 | 0.009 |
| sashigane（この決定の前） | 0.003 |

### 決定 5-9: status は色だけで伝えてはならない

status 4色の色覚特性下での最小 ΔE は **0.0077**（識別色の対処前 0.003 より悪い）。
2型色覚下では danger・warning・success がほぼ同一の色になる。

```
通常   #f7004d #c26f00 #009f63 #008ed6
2型   #9b8d45 #9c8b01 #8e8767 #5080d5
       ↑danger ↑warning ↑success   ← 取り違える
```

識別色と同じく段をずらすと 0.065 まで改善するが、**目標 0.08 には届かない。**
`danger` 25° と `warning` 70° は赤と黄で、1型・2型色覚で最も潰れやすい組み合わせであり、
色相を離せば意味が壊れる（決定5-4）。

**色だけでは解けない。**

#### 決定

1. **status の段はずらさない。** 届かない改善のために見た目の一貫性を捨てない
2. **status を色だけで伝えるコンポーネントを作らない。**
   アイコンまたはテキストラベルを必須とする

2 は WCAG 1.4.1（Use of Color）の要求そのものであり、
**色の識別性を上げることは補助にしかならない。**

#### Phase 3 への要件

status を表現するコンポーネント（Badge、Alert、フォームの検証表示など）は、
**アイコンまたはテキストによる非色の手がかりを構造的に必須にする。**
「アイコンを付けられる」ではなく「アイコン無しでは組み立てられない」形にする。

観測（[roles.md](./roles.md)）でも pylabo は
`.checks .is-pass svg` / `.is-fail svg` とアイコンを併用しており、
色だけで表現してはいなかった。**実装者は既にこれを知っていた。**

### 決定 5-6: 中間色は primary の色相で着色する — **根拠を改訂（2026-08-24）**

> **決定は維持する。根拠が誤っていた。**
> 当初は「観測した4本の中間色がすべて純グレーではなかった」を根拠にしていたが、
> **観測は「色が付いている」ことしか示しておらず、「primary と同じ色相である」ことは
> 示していなかった。** 実測は [experiments/neutral-hue.md](./experiments/neutral-hue.md)。

#### 観測は何を示していたか

accent の色相と中性色の色相の差を、観測対象4本（pylabo は2テーマ）で測った。

| | accent | 中性色の ΔH |
|---|---|---|
| pylabo (dark) | 261.7° | 2.7 〜 9.9° |
| pylabo (light) | 262.9° | −1.1 〜 12.1° |
| ichirizuka | 192.8° | 4.4 〜 **54.1°** |
| holosphere | 322.2° | **−26.4 〜 −38.2°** |
| pdf-merge-app | （shadcn 既定） | 中性色は C = 0 |

**色相の一致を支持していたのは pylabo だけだった。** 4本中1本。

#### それでも決定が正しい理由

**中性色の彩度が低いので、色相の選択は「グレーである」ことを変えない。**

| 対象 | 実際の値 | 色相だけ accent に合わせた値 | ΔE |
|---|---|---|---|
| ichirizuka `--ink`（ΔH 54.1°） | #14202b | #0e2322 | **0.025** |
| holosphere 地（ΔH −38.2°） | #0b0b14 | #100911 | **0.013** |

**色相差 54° が、知覚上は 0.025 にしかならない。**
識別色として区別できる最小の差は 0.08（決定5-5）。参考に、赤と緑の ΔE は 0.415。

生成器の側でも同じことが言える。全360色相・全11段で、
**色相を最も遠い 180° へ振っても ΔE は最大 0.0578**（中性色の彩度は最大 C = 0.0289）。

##### 「見えない」とは言えない

**0.08 は「識別色として見分けられるか」の閾であって、「隣り合う面の差が見えるか」の閾ではない。**
実際に並べて目視すると、この範囲でも差は見える。

| ΔE | 見え方 |
|---|---|
| 0.002 | 区別できない |
| 0.013 | かろうじて |
| 0.018 〜 0.025 | **隣接させると見える** |
| 0.034 | **はっきり違う** |

したがって主張はこうなる。

- 色相の選択は、面が**グレーであること**を変えない
- 差は**識別色として情報を担える大きさには決してならない**
- そして**その隣接比較は実際には起きない。** 利用者が見るのは1つのパレットであって、
  「primary の色相で着色した版」と「別の色相で着色した版」を並べた画面ではない

問うべきだったのは「差が見えるか」ではなく
**「色相を primary に揃えると、達成できなくなる設計があるか」**である。
答えは「無い」。どちらも低彩度の色付きグレーとして成立する。

**達成できなくなる設計が無い以上、入力を増やさない。** 決定5-1（入力は primary 1色）を維持する。

**背景と文字が画面の大半を占めるので、色調の統一に最も効く。**
色相の選択が見えない以上、揃えておく方が一貫する。

#### 前提が崩れる条件を検査する

新しい根拠は**構造に依存している。** 中性色の彩度を上げれば前提は崩れる。
根拠が観測ではなく構造にあるなら、構造の側を検査する（`pnpm test`）。

- 中性色は primary の色相を受け継ぐ
- **色相をどう選んでも知覚上の差が識別閾に届かない**

`neutralRatio` を 0.2 → 0.8 に上げると後者が落ちることを確認した。

#### 採らなかったもの

観測に反していた2本は、どちらも**明度に応じて色相をドリフトさせていた**
（明るい段ほど accent に近い）。規則性はあるが、**それも「達成できなくなる設計」を生まない。**
色調を揃える方が一貫するので採らない。

### 決定 5-11: 連続値の色帯は単一色相。段は明度スケールに載せる

> **推した案を測って退けた。** 明度に沿って色相も回す案（viridis 相当）を出したが、
> 二色覚のもとで**知覚明度の単調性が壊れる**ことが分かった。
> 測定は [experiments/sequential.md](./experiments/sequential.md)。

`roles.md` は観測の時点で「連続値の色帯は離散系列とは別の役割」と書いていたのに、
実装していなかった（[Issue #36](https://github.com/shun2218-dev/sashigane/issues/36)）。

**生成規則**

```
--sg-color-sequential-{1..10}
  明色モード  primary の段 100 → 950   （面に近い側から遠い側へ）
  暗色モード  primary の段 900 →  50
```

色を反転しているのではなく**参照する段を変えているだけ**である（決定5-2 と同じ形）。

| 決めたこと | なぜ |
|---|---|
| 単一色相 | 回すと二色覚下で順序が反転する。status 帯との重なりも増える（測定） |
| 段は明度スケールに載せる | 新しい定数を作らない。値の分解能はここで決まる |
| **面（`bg-page`）の段は入れない** | 入れると帯の最小段が面と同じ明度（コントラスト 1.00）になり、**値が最小のセルとデータが無いセルが区別できない**（自己レビュー B1） |
| 補間関数は持たない | 段に量子化すれば補間が要らない。配布物は値と型だけという形を変えない |

除くのは面の1段だけなので、閾値という新しい定数は持ち込まない。
結果として最小段のコントラストは明色 1.29 / 暗色 1.19 になる
（参考: GitHub の contribution graph の最小セルは白地に対し 1.09）。

**値は primary ランプそのものになる。** それでも役割として出すのは、
利用側がプリミティブを参照できないためである（原則3）。
**役割名が無ければ、連続値に使ってよい値が存在しないことになる。**

#### 凡例のグラデーションは利用側が組む

段が11本あるので `linear-gradient(to right, var(--sg-color-sequential-1), …)` で足りる。
グラデーション自体をトークンにすると、セマンティックが
「プリミティブへの1段参照」でなくなり、JS への書き出し（決定2-6）が壊れる。
**1行で書けるものをトークンにしない。**

#### データを段へ写す

`index = round(t × 9) + 1`（t は 0..1 に正規化した値）。
ichirizuka は RGB 三つ組を直書きして sRGB で線形補間していたが、
**sRGB の線形補間は中間がくすむ。** 段を選べば補間そのものが要らない。

#### 保証しないこと

**帯の上に置く文字のコントラストは保証しない。**

```
明色の文字（neutral 900）を帯の上に置いたとき
14.47 11.17 8.43 6.19 4.41 3.07 2.28 1.69 1.27 1.00 1.18
                          ↑ ここから 4.5:1 を割る
```

「コントラストは構造的に保証される」（README・原則5）が指すのは
**面と文字・面とマーク**であって、帯の上のラベルは含まれない。
各段に対して 4.5:1 を満たす文字色を役割として足す案はあるが、
**実需要を1件も観測していない**ので持たない（原則7）。必要になったら足す。

#### 受け入れたトレードオフ

**帯の中間段は `--sg-color-accent` と同じ色になる。** 単一色相を選んだ以上、
帯は primary ランプそのものなので避けられない。
回避するには色相を回すしかなく、それは単調性を壊す。

離散系列（`chart-1..5`）とは値が重ならないことは確認済み。

#### 持たなかったもの

**diverging（中央が中性で両端が対立する帯）は持たない。** 観測が1件も無い（原則7）。
ichirizuka の心拍スケールは3色を使っているが、値の大小を表す
**単調な帯であって diverging ではない。**

#### 検査

`test/sequential.test.ts` が全36色相・二色覚3種・両モードで単調性を見る。
**退けた多色相の帯を陰性対照として当て、検出器が発火することを確かめてから本体を見る**（教訓2）。

### 決定 5-10: テーマは両方向に固定できる

> **Phase 2（ichirizuka への導入）で見つかった穴への対処。**
> 記録は [experiments/phase2-ichirizuka.md](./experiments/phase2-ichirizuka.md)。

`tokens.css` は3つの形でセマンティックを出す。

| 出し方 | 意味 |
|---|---|
| `:root` | 既定（明色） |
| `@media (prefers-color-scheme: dark)` | OS の設定に従う |
| `[data-theme="light"]` / `[data-theme="dark"]` | **利用側が固定する** |

固定用の2ブロックはメディアクエリより**後**に出す。`:root` と詳細度が同じなので、
順序で勝たせる。

**どのブロックも `color-scheme` を伴う。** スクロールバー・フォームコントロール・
既定の選択色はブラウザ自身が描くもので、**CSS 変数は届かない。**
これが無いと、暗色に切り替えても明色のスクロールバーが暗い面の上に出る。
「テーマを固定できる」と言う以上、UA が描く部分も固定の対象に含まれる。

#### なぜ両方向なのか

当初は `[data-theme="dark"]` しか出しておらず、**明色に固定する手段が無かった。**

Phase 2 で ichirizuka（紙を模した明色専用のデザイン）へ導入したところ、
OS が暗色設定の環境で**写像した10変数だけが暗色へ切り替わり、
生値のまま残っていた15箇所と混ざって壊れた。**

暗色モードを持たないアプリは実在する。トークン層を入れただけで
**利用側が選んでいない見た目に飛ぶのは、原則6 の「トークンのみのインストールが実際に動く」に反する。**

暗色専用のアプリも同じ理由で存在しうるため、対称に両方向を出す。

#### 検査

`packages/tokens/test/tokens-css.test.ts` が、両ブロックの存在・メディアクエリより後にあること・
中身が `:root` と一致することを検査する。

**順序と詳細度の話なので、静的検査だけでは効くことを証明できない。**
実ブラウザで OS を暗色/明色に振り、`data-theme` の有無で
`--sg-color-bg-page` と `color-scheme` の解決値が変わることを目視した（記録は PR）。

### 決定 5-12: 面は文脈である。深い面では役割が1段深い段を指す

> **Phase 2 の2本目（holosphere への導入）で見つかった穴への対処。**
> 記録は [experiments/phase2-holosphere.md](./experiments/phase2-holosphere.md)、
> [Issue #50](https://github.com/shun2218-dev/sashigane/issues/50)。

#### 問題

決定5-2 の保証は面を **50 / 950** と明示している。実装もテストもそのとおりだった。
**しかし文字が最も多く載るのは `bg-page` ではなくカード（`bg-surface`）である。**

暗色モードの `bg-surface` の上で測ると、こうなっていた。

| 役割 | 対 bg-page | 対 bg-surface | 対 bg-inset |
|---|---|---|---|
| text-faint | 5.26 | **4.49** | **3.57** |
| accent | 4.51 | **3.85** | **3.06** |
| danger | 4.66 | **3.98** | **3.16** |

明色モードでは `border-focus` が `bg-inset` の上で **2.24:1** になる。

**`bg-surface` と `bg-inset` は一度も測られていなかった。**
教訓2 の「測れるもので測っただけの結論を、問いへの答えとして扱わない」がそのまま当たる。

#### 退けた案: 端点を深い面に対して解き直す

**解が存在しない。** 実際に解かせると探索が下限に張り付き、暗色側が 2.05:1 まで落ちた。

明色は「濃いアンカー」を要求し、暗色は「明るい段400」を要求する。
ランプは1本なので両立しない。

#### 退けた案: 面の段を詰める

**効かない。** 決定5-2 は段500 を面50 に対して**ちょうど 4.500** に解いており、余裕がゼロである。
面を少しでも暗くすれば割る。面を page と同じ明度にする以外に解が無い。

#### 決定: ランプは変えない。役割が参照する段を面の深さでずらす

必要な段は**すべて既存の11段の中にある。**

| 面 | 文字（4.5:1） | マーク（3:1） |
|---|---|---|
| 明 `page`(50) / 暗 `page`(950) | 500 / 400 | 400 / 300 |
| 明 `surface`(100) / 暗 `surface`(900) | 600 / 300 | 500 / 200 |
| 明 `inset`(200) / 暗 `inset`(800) | 700 / 200 | 600 / 100 |

`page` の行は**改訂前と完全に同じ**である。既存の見た目は変わらない。

段は表で持たない。**要件を満たす最も浅い段**を生成のたびに解く。
文字の3段（default / muted / faint）は `faint < muted < default` の順序を保ったまま選び、
`default` だけは面によらずランプの端（900 / 100）に固定する。

**マークは「3:1 を満たす最も浅い段」ではない。** 文字の段より1段明るい側を取る。
最小を満たす段にすると明色で段500 になり、決定5-7 で目視したとおり
チャート系列が全部くすんで見分けられなくなる。このランプは明るい段ほど彩度が乗る。

#### 面の作り方は1つだけ

```html
<body data-sg-surface="page">
  <article data-sg-surface="surface">…</article>
</body>
```

`[data-sg-surface]` は **背景と前景を同時に決める。**

**塗るだけの道は塞いだ。** Tailwind アダプタから `--color-page` / `--color-surface` /
`--color-inset` を落としてあり、`bg-surface` は存在しない。
残すと「塗ったが文脈は page のまま」という状態が作れてしまい、
コントラストが落ちても**エラーにならない**（教訓4）。

`data-theme` が既に同じ形（文脈で変数を差し替える）なので、仕組みは一貫している。

##### 改訂（2026-08-27）— 塞いであったのは Tailwind アダプタだけだった

> [Issue #65](https://github.com/shun2218-dev/sashigane/issues/65)。
> 決定5-14 の作業中に、`--sg-color-bg-page` の唯一の使い道が
> 「前景に借りる」だったと分かったことから見つけた。

`tokens.css` には `--sg-color-bg-page` / `-surface` / `-inset` / `-overlay` が
**そのまま残っていた。** 素の CSS を書く利用者は面を塗るだけにできた。
原則4 は「トークンのみのインストールが実際に動くこと」を層分離の証明としており、
`tokens.css` 単体の利用者は一級の利用者である。**その経路にだけ穴が空いていた。**

**サンプルページ自身が踏んでいた。**

```css
kbd { background: var(--sg-color-bg-surface); … }   /* 前景は page の文脈のまま */
```

```html
<p class="caption field-ok">保存しました。<kbd>⌘</kbd> <kbd>S</kbd> で…</p>
```

`.caption` は `text-faint`、`.field-ok` は `--sg-color-success` である。
page の前景を `bg-surface` の塗りに載せたときの**全360色相の最悪**：

| | `text-default` | `text-muted` | `text-faint` | `success` | `danger` |
|---|---|---|---|---|---|
| 明色 | 10.81 | 4.87 | **3.64** | **3.43** | **4.05** |
| 暗色 | 10.81 | 5.91 | **4.21** | 4.51 | **3.79** |

`check:sample-page` は名前が名前表にあることしか見ないので捕まらなかった。

**`--sg-color-bg-surface` / `-inset` / `-overlay` を落とす。** 面は `data-sg-surface` で作る。
`kbd` は `data-sg-surface="surface"`、進捗の溝は `data-sg-surface="inset"` に直した。
溝は借り物ではなく**「凹んだ面」そのもの**である。

**壊れるのは文字だけではない。** 溝を直したところ、その上のバーのコントラストも直った。

```
明色: 溝(段200) の上のバー   前(page の文脈の accent-mark) 1.79  →  後(inset の accent-mark) 3.49
暗色: 溝(段800) の上のバー   前                            4.27  →  後                      6.41
```

`colorMark` は**その面に対して 3:1** を満たすように解かれている（決定5-7）ので、
面を偽ると保証の外に出る。明色の **1.79:1** は、WCAG が非文字の図形に求める 3:1 を
大きく割っていた。

**これは破壊的変更である。** いま影響が出ないのは、タグを1つも切っておらず
`main` へのリリースをまだ行っていないからである（[branching.md](./branching.md)）。
バージョン管理を決める前に直しておく。

**`--sg-color-bg-page` だけは残す。** 理由は2つある。

1. **どの面の文脈のまま塗っても割らない。** 全360色相 × 両モード × 面4段で最悪 4.50 で、
   深い面ほど余裕が増える（深い面の前景は端へ寄るので、ページ地の上ではむしろ強くなる）。
   **塗って壊れる道が存在しない**ので、塞ぐ理由がない
2. **CSS が原理的に届かない場所が値を必要とする**（決定2-6）。サーバ側で描く OG 画像には
   ブラウザもカスケードも無い。Phase 2 で holosphere が実際に踏んだ

そのため `--sg-color-bg-page` は**サンプルページからは参照されない。**
使う場所は CSS ではなく JS であり、`check:sample-page` が未使用と報告するのは正しい。

不変条件（1）は文書ではなく検査で持つ（教訓3）。

#### 重ね方の向きは選べない

> [Issue #29](https://github.com/shun2218-dev/sashigane/issues/29) の判断。
> Phase 2 の1本目で「面を重ねる方向を利用側が選べるようにするか」を保留していた。

sashigane は**重ねるほど中間へ寄る。** 明色は暗く、暗色は明るくなる。

```
明色  page L=0.970 → surface L=0.883 → inset L=0.795
暗色  page L=0.186 → surface L=0.255 → inset L=0.325
```

ichirizuka は逆で、紙（L=0.940）よりカード（L=0.978）を明るくしていた。

#### 2件目の観測で、これは明色1件だけの話だと分かった

holosphere（暗色のみ）は `page #0b0b14` → `card #12121b` で、**sashigane と同じ向き**だった。
逆向きは ichirizuka の1件しかない。

そして **ichirizuka の向きは設計判断ではない。**

> 作者に確認した（2026-08-26）。観測対象4本はいずれもデザインシステム無しで書かれており、
> **デザインにこだわって作ったものではない。**「一貫していない」「一般的でない」組み方を
> 含んでいる前提で読み、修正の対象として扱ってよい、という回答だった。

原則2 が言う「過去の実装は需要の観測には使うが値のソースには使わない」の、
**値だけでなく組み方にも同じことが当たる。**

#### 退けた理由は実装コストではない

選べるようにすること自体は難しくない。段の割り当てを反転すれば、
決定5-12 の導出（面ごとに要件を満たす最も浅い段を解く）は**向きに依存しないのでそのまま動く。**

これは推論ではなく**実際に反転させて確かめた。**

```
light 面200 文字 4.77  マーク 3.51  中間色 4.98  ✅
light 面100 文字 4.68  マーク 3.45  中間色 4.92  ✅
light 面 50 文字 4.50  マーク 3.12  中間色 4.77  ✅
dark  面800 文字 6.23  マーク 8.53  中間色 4.82  ✅
```

**問題は明色でページ地が白でなくなることである。**

```
「重ねるほど明るく」を3段やる場合の唯一の割り当て
  page L=0.795   surface L=0.883   inset L=0.970
```

段50（L=0.970）より明るい段は**存在しない**（上端は固定、決定5-2）。
3段積むには**ページ地を段200 まで下げるしかなく、ほぼ白からはっきりした灰色になる。**

紙に印刷された記録帳の見立てなら妥当かもしれないが、
**それは1件の、しかも意図が確認できていない観測のために、既定の見え方を変える判断**になる。

#### 決定: 向きは1つ。選択肢を持たない

原則7 に従う。**逆向きを選んだ実例は、いま1件も無い。**
ichirizuka の向きは設計判断ではなかったので、観測数は実質ゼロである。

考え直す条件は「意図してページ地を白でなくしたい」という需要が出たときで、
そのときも「利用側が重ね方を選べる」ではなく
**面の起点をどこに置くか**という別の設計として扱う。

#### 深さは重なりの回数ではなく名前で決まる

```html
<div data-sg-surface="surface">
  <div data-sg-surface="surface">…</div>   <!-- 内側も surface 扱い -->
</div>
```

**数える設計にしない。** CSS だけでは重なりの回数を数えられず、
利用側が深さを管理することになる。名前で決めれば宣言した場所を読むだけで分かる。

#### 連続値の色帯も面ごとに変わる

決定5-11 は「**その面が使う段は帯に入れない**」と決めている。
面の1段目に固定していると、カードの上で**帯の下端がちょうど 1.00:1** になり、
値が最小のセルとデータが無いセルが区別できなくなる（自己レビューで実測）。

除く段を面ごとに変える。**段数は10のままなので `--sg-color-sequential-1..10` の
顔ぶれは変わらない。** 全120色相で測って、帯の下端の最悪コントラストは 1.12 で
`page` と同水準、知覚明度の単調性も保たれることを確認した。

#### 保証しない範囲

- **識別色（チャート系列）は `page` と `surface` まで。**
  暗色の `inset` では 3:1 を満たす段が4つしか残らず、5系列を配れない。
  配れない面では変数を出さないので、親の面の値をそのまま継承する
- **`tokens.js` は `page` の値だけを持つ。** CSS が届かない場所（OG 画像など）のための
  経路であり、そこに面の重なりは無い（決定2-6）
- **`tokens.scss` は変数の別名なので、文脈は CSS 側で効く。** SCSS 単体では解決しない

#### 検査

`packages/tokens/test/color.test.ts` が、**全360色相 × 両モード × 面3段**で
文字 4.5:1・マーク 3:1・系列 3:1 を検査する。面の深さを無視するように壊すと
**8件が落ちることを確認した**（page の行は落ちない）。

連続値の帯は `test/sequential.test.ts` が面ごとに検査する。
除く段を `page` 固定に戻すと**発火することを確認した。**

実ブラウザでも、`data-sg-surface` を重ねると `--sg-color-danger` と
`--sg-color-text-faint` の解決値が面ごとに変わることを両モードで目視した。

### 決定 5-13: hover は面の文脈である。梯子は4段で止まる

> **Phase 2 の2本目（holosphere への導入）で見つかった穴 G3 への対処。**
> 記録は [experiments/phase2-holosphere.md](./experiments/phase2-holosphere.md)、
> [Issue #45](https://github.com/shun2218-dev/sashigane/issues/45)。

#### 問題

[roles.md](./roles.md) は5つの役割を**観測済みとして記録している**のに、
どれもトークンになっていなかった。holosphere から移すとき hover の面を `bg-inset` で
代用したが、`bg-inset` は「凹んだ面」であって「hover した面」ではない。

| 役割 | 観測 | 今回 |
|---|---|---|
| `bg-hover` | i p h | **持つ**（面の文脈として） |
| `bg-overlay` | h s | **持つ**（`surface` と同じ段） |
| `border-strong` | p | **持つ** |
| `chart-gridline` | h | **持つ** |
| `bg-surface-subtle` | p | **退ける**（下記） |
| `bg-active` | i p h | **保留**（下記） |

#### 塗るだけの `bg-hover` は存在しえない

前景を面の文脈のまま据え置き、背景だけ1段深くして測った。**全360色相の最悪。**

| 面 | hover 背景 | `text-faint`（要 4.5） | `accent`（要 4.5） | `accent-mark`（要 3.0） |
|---|---|---|---|---|
| 明 `page` | 100 | **3.64** | **3.45** | **2.39** |
| 明 `surface` | 200 | **3.66** | **3.49** | **2.59** |
| 明 `inset` | 300 | **3.58** | **3.45** | **2.56** |
| 暗 `page` | 900 | **4.21** | **3.82** | 5.39 |
| 暗 `surface` | 800 | **3.57** | 4.27 | 6.24 |
| 暗 `inset` | 700 | **3.58** | **3.38** | 4.84 |

決定5-12 が塞いだ穴（面を塗ったのに前景が浅いまま）がそのまま再発する。
**`--sg-color-bg-hover` を単体のセマンティックとして持つ道は、ここで消える。**

#### 決定: hover は「1段深い面の文脈」である

背景と前景を同時に切り替える。決定5-12 の面と同じ仕組みに乗る。

```html
<article data-sg-surface="surface">
  <button data-sg-interactive>…</button>   <!-- hover 中は inset と同じ段の文脈 -->
</article>
```

`data-sg-interactive` を付けた要素だけが対象である。
付けなければ何も起きないので、**塗るだけの道は存在しない。**
Tailwind アダプタにも `bg-hover` は無い。

#### 梯子は4段で止まる

`inset` の hover は4段目（明 300 / 暗 700）を要求する。**5段目は成立しない。**

| | 明 面400 | 暗 面600 |
|---|---|---|
| `text.default`（決定5-12 で 900 / 100 に固定） | **最悪 4.21**（4.5 を満たすのは 9/360 色相） | 最悪 4.87 ✓ |
| 固定を外して最深段を使う | 950 なら満たすが**ランプの端**で、muted / faint の置き場が無い | 100 の浅い側は 50 のみ。3段そろわない |

**1色で測ると答えを間違える。** primary=315° では明色の面400 が 4.55 で通ってしまう。
保証は全色相で成立していなければ意味がない（決定5-1、教訓2）。

4段はちょうど埋まる。`page` `surface` `inset` の3つと、`inset` の hover が要求する1つである。
**4段目は名前を持たない。** `data-sg-surface` では名乗れない。
名乗れてしまうと、その中の要素が hover したときに行き先が無くなる。

#### 規則は1本だけ。値は継承で届く

```css
@media (hover: hover) {
  [data-sg-interactive]:hover {
    background-color: var(--sg-color-deeper-bg);
    --sg-color-text-default: var(--sg-color-hover-text-default);
    …
  }
}
```

面のブロックが `--sg-color-hover-*` に「1段深い役割一式」を控えておき、
hover の規則はそれを現在の役割へ移すだけである。

**セレクタで面ごとに書き分けない。** `[data-sg-surface="inset"] [data-sg-interactive]:hover`
のように書くと、勝敗は詳細度と出力順で決まる。`overlay` は梯子の途中に戻る面なので
「入れ子の深さ」と「出力の順序」が一致せず、`overlay` の中の `inset` か
`inset` の中の `overlay` か、**どちらかの入れ子が必ず外れる。**
外れても背景が変わらないだけでエラーにはならない（教訓4）。

CSS の継承に解かせれば「最も近い面が控えた値」が届くので、入れ子に依らない。

`@media (hover: hover)` で囲うのは、触る画面で hover が張り付いて残るためである。

#### `bg-overlay` は `surface` と同じ段に置く

roles.md が挙げた overlay の理由は「アルファ面は下地が透けるので重なりに使えない」だが、
**sashigane の面はすべて不透明なのでこの制約は既に満たされている。**
`data-sg-surface` は名前で深さが決まる（決定5-12）ので「下地に依らない」も満たされている。

残るのは「浮いて見える」だけで、それは決定1-8 の elevation の責務である。

> **2026-08-29。** elevation を実装した。当時「暗色は明度差分」と書いていたが、
> **暗色では明度を持ち上げる余地が無い**ことが測定で分かり、輪郭に改めた（決定1-8 改訂）。
> `overlay` を `surface` と同じ段に置く以上、**暗色でこれが無いと下地と同化する。**

最深段（明 300 / 暗 700）に置けばどの面の上でも浮くが、
**その中の項目が hover できなくなる。** ドロップダウンは overlay の中に hover する項目が
並ぶ形なので、これは実用上の破綻である。`surface` と同じ段に置く。

**暗色モードで `inset` の上に開くと、overlay のほうがわずかに暗い。**
境界で区切られるので沈んで消えることはないが、浮いては見えない。
elevation を実装するまでの既知の限界として残す。

#### `border-strong` と `chart-gridline`

境界は要件を持たない装飾なので、面と一緒に深い側へずらす規則（決定5-12）に足すだけでよい。

| | 明 `page` | 明 `inset` | 暗 `page` | 暗 `inset` |
|---|---|---|---|---|
| `chart-gridline` | 100 | 300 | 900 | 700 |
| `border-subtle` | 200 | 400 | 800 | 600 |
| `border-default` | 300 | 500 | 700 | 500 |
| `border-strong` | 400 | 600 | 600 | 400 |

`chart-gridline` は**面のすぐ外側の段**を取る。`border-subtle` は面から depth+2 段外側なので、
グリッド線は必ずその内側に入る。**新しい定数は持ち込まない。**

`border-strong` は hover とは別に要る。hover の面では境界も自動的に濃くなる（`page` の 300 が
hover 面では 600 になる）が、**選択中の行や強調した区切りは hover ではない。**

#### 退けた案: `bg-surface-subtle`

「ページとカードの中間」だが、明色の 50 と 100 の間に段が無い。
静的な面として足すと `page → subtle → surface → inset` で4段を使い切り、
`inset` の hover が5段目を要求して成立しない。**`bg-hover` と両立しない。**

段を足す（ランプを12段にする）道もあるが、`lightnessesFor` は添字で補間するので
**全段の明度が動き、決定5-2 を解き直すことになる。**
観測は p の1件のみで、その1件は「デザインにこだわって作ったものではない」と
作者が明言している4本の1つである（決定5-12 の記録）。needs が確かめられていない側を退けた。

#### 退けた案: `bg-active` を hover と同じ形で持つ

`active` を「2段深い面」とすると `inset` で5段目を要求して成立しない。
「行き先が無ければ最深段に飽和する」という例外規則を作れば通るが、
**例外規則は後から誰も消せなくなる。** 押下の表現は Phase 3 で
コンポーネントを書いてから決める。

#### 控えは「参照してよい名前」ではない

`--sg-color-hover-*` は hover の規則が読むための値であって、利用側が書く役割ではない。
**参照されると、hover していない要素に hover の色が乗る。** 塗るだけの道が裏口から復活する。

そのため名前表（`tokens.layers.json`）に**第4の種別 `internals` を足した。**

| 種別 | 参照 | 例 |
|---|---|---|
| `primitives` | **禁止** | `--sg-neutral-500` |
| `semantics` | 可 | `--sg-color-text-muted` |
| `inputs` | 利用側が**定義する** | `--sg-font-brand-body-latin` |
| `internals` | **禁止** | `--sg-color-hover-text-muted` |

`check:token-usage` と `check:sample-page` は、これを「名前表に無い」ではなく
**「参照してはいけない」として報告する。** 打ち間違いと混ざると直し方が分からない。

内部の値は **`tokens.css` にしか出さない。** `tokens.js` にも `tokens.d.ts` にも
`tokens.scss` にも出ない。面の文脈を持たない出力に控えだけあっても意味がない。

#### 保証しない範囲

- **hover した要素の中の要素を hover しても文脈は変わらない。** 控えは面の側にしか無いので、
  内側は外側と同じ段になる。コントラストは割らないが、内側の hover は見えない
- **最深段では文字が3段から2段に減る。** `text.muted` が `text.default` と同じ段になる
  （全360色相で観測）。hover 中だけの話であり、コントラストは割らない
- **`bg-overlay` は浮いて見えない**（上記）
- **塗りのある要素には `data-sg-interactive` を付けない。** hover の規則は
  `background-color` を直接指定し、詳細度は `.btn-primary`(0,1,0) より
  `[data-sg-interactive]:hover`(0,2,0) のほうが高い。付けると**塗りが中間色の面に
  置き換わる**（アクセント色のボタンが灰色になる）。hover の面は「面の上の要素」の
  ためのものであり、塗りは面ではない。塗りの hover は Phase 3 で決める

#### 検査

- `test/color.test.ts` — **全360色相 × 両モード × 面4段**。4段目（名前を持たない hover の面）も
  検査に含める。境界の4段が面から遠ざかる順に並ぶことも見る
- 同 — **5段目が成立しないことを検査で持つ。** ランプの段数を増やすなどで置けるようになったら
  落ちる。落ちたらこの決定を読み直すことになる
- `test/tokens-css.test.ts` — hover の規則が1本だけであること、`(hover: hover)` の中にあること、
  面のブロックより後にあること、そして**規則が参照する控えを面を作るブロックが全部持っていること**。
  控えを1つ落として発火することを確認した
- `test/layers.test.ts` — 名前表が **`tokens.css` の宣言を1つ残らず覆う**こと。
  生成した CSS から直接取るので、別経路で足した宣言を数え落とせない。
  内部の値が他のどの層とも互いに素で、`tokens.js` にも `tokens.d.ts` にも出ないこと
- `scripts/check-token-usage.mjs` — `bg-hover` と `bg-overlay` が出ないこと、
  内部の値の参照が `internal` として発火すること（陰性対照2件）
- `scripts/check-sample-page.mjs` — サンプルページが新しい役割を実際に使っていること（原則3）。
  内部の値を踏んでいないこと。**この検出にも陰性対照を通す**（教訓2）
- `scripts/check-tailwind-adapter.mjs` — `bg-hover` と `bg-overlay` が出ないこと

**実ブラウザで確かめた。** 詳細度と継承の話なので静的検査では効くことを証明できない。
両モードで、`data-sg-interactive` を hover したときに背景と `--sg-color-text-faint` が
同時に1段深い面のものへ変わることを確認した。入れ子は3通りとも意図どおりで、
とくに **`overlay` の中の `inset`** と **`inset` の中の `overlay`** が両方とも正しく解決する。
セレクタで書き分けていたら、このどちらかが外れていた。

### 決定 5-14: 塗りの上の文字は、塗りの側から解く

> [Issue #59](https://github.com/shun2218-dev/sashigane/issues/59)。
> テーマビルダーで primary に明るい黄色（`#f7de3b`）を選んだときの見え方から見つけた。

#### 問題

塗りの上に載せる文字の役割が無く、**面の色（`bg-page`）を前景に借りていた。**

```css
.btn-primary { background: var(--sg-color-accent); color: var(--sg-color-bg-page); }
```

値としては正しい。`accent` はページ地に対してちょうど 4.5:1 に解かれている（決定5-2）ので、
その裏返しも必ず 4.5:1 になる。**しかし塗りの側から導出していないので、塗りの段を変えた
瞬間に追随しない。** 面の色を前景に借りるのは意味の嘘でもある。

#### 先に観測を確かめた

Issue は「明るい塗り＋暗い文字」を想定していた。**観測4本を実際に読んだ結果、そのような
組み方は1件も無かった。**

| 組み方 | i | p | h | s |
|---|---|---|---|---|
| 塗り＝アクセント、文字＝白（直書き / `*-foreground`） | — | ✓ `.button--primary { background: var(--accent); color: #fff }` | ✓ `bg-fuchsia-500 text-white` | ✓ `bg-primary text-primary-foreground`（7箇所） |
| 淡い塗り＋アクセント色の文字 | — | ✓ **多数** `color-mix(in srgb, var(--accent) 7〜35%, transparent)` | ✓ **多数** `bg-amber-300/15 text-amber-200` | — |
| **明るい塗り＋暗い文字** | — | — | — | — |
| ボタンに塗りを使わない（境界のみ） | ✓ `.button { background: transparent }` | — | — | — |

状態色の塗りは色によって差があった。**`danger` の不透明な塗りだけが観測され、
`warning` / `success` / `info` の不透明な塗りは1件も無い。** h にあるのはすべて
`/15` `/20` のアルファ合成で、文字はその色自身である。

#### 決定: `on-{塗りの名前}` を持つ。値はランプごとに解く

塗りの上の文字は**中間色ランプの端**から取る。端は2つしかないので、
コントラストが高いほうを選べばよい。**新しい定数は持ち込まない。**

```
--sg-color-on-accent   --sg-color-on-danger   --sg-color-on-warning
--sg-color-on-success  --sg-color-on-info
```

全360色相 × 両モード × 面4段 × 全ランプで測った。

| | 深さ0 | 深さ1 | 深さ2 | 深さ3 |
|---|---|---|---|---|
| 明色（選ばれる段 / 最悪） | 50 / **4.50** | 50 / 6.04 | 50 / 8.13 | 50 / 10.79 |
| 暗色（選ばれる段 / 最悪） | 950 / **4.50** | 950 / 6.30 | 950 / 6.62 | 950 / 9.18 |

**選ばれる段はどの条件でも1つに収束する。** 深い面では塗りがさらに端へ寄るので、
余裕は増えるだけである。

#### 5つとも持つ理由

**いまはどれも同じ段に解かれる。** それでも名前を5つ持つのは、名前が塗りの側に
付いているためである。`danger` の塗りに `on-accent` を書くのは、`bg-page` を借りるのと
同じ種類の嘘になる。**導出はランプごとなので、将来値が分かれても自動で追随する。**

`warning` / `success` / `info` の不透明な塗りは観測ゼロだが、
**状態色は1つの役割の族であり、3つだけ穴を空けると、その穴を埋めるために
`bg-page` を借りる道が残る。** それはこの決定が消そうとしているものそのものである。

#### 退けた案: 明るい塗り＋暗い文字（塗りの段を選べるようにする）

Issue の動機（黄色を選んだら黄色いボタン）には直接答えるが、**観測がゼロである。**
原則2 は「過去の実装は需要の観測には使う」と言っており、
需要が確かめられていないものを規則にしない。

#### 退けた案: 淡い塗り（`accent-subtle` 相当）— **決定5-16 で採った（2026-08-29）**

p と h で**最も多い**組み方であり、需要はある。ただし2点が未決である。

```
淡い塗り（明色 段200 / 暗色 段800）の上の text-default   7.85 / 8.30  ✓
淡い塗りとページ地の差                                   1.60 / 1.36  ✗（部品の境界は 3:1）
```

**ページ地との差が 3:1 に届かないので、境界線を必須にするか面積で成立させるかを
決めなければならない。** 観測された2本はどちらもアルファ合成で作っており、
この設計は面をアルファで作らない（決定5-13）。**別の決定として扱う。**

> **2026-08-29。** 決定3-2 を改訂してアルファ修飾子を塞いだので、
> **淡い塗りを書く方法が1つも無くなった。** 保留したまま表現手段だけが消えたため、
> [Issue #87](https://github.com/shun2218-dev/sashigane/issues/87) を立て、**決定5-16 で解いた。**
>
> 保留の理由だった「ページ地との差が 3:1 に届かない」は、**要求する理由が無かった。**
> 決定5-9 で status を色だけで伝えないと決めてあるので、塗りは唯一の手がかりではない。
> 面の梯子自身も 1.30:1 で成立している。

#### 保証しない範囲

**`on-*` は `--sg-color-{名前}` の塗りに対してだけ解いてある。**
`--sg-color-{名前}-mark` は 3:1 しか満たさない別の段であり、その上に `on-*` を載せると割る。

```
明色: on-accent を accent-mark の塗りに載せた最悪  3.11  ✗（全360色相）
暗色:                                              6.30  ✓
```

`-mark` は**印**（アイコン・境界・チャートのマーク）のための段であって、
文字を載せる面ではない（決定5-7）。塗りとして使ってよいが、**その上に文字を置かない。**

**これは検査にできない。** 教訓3 は「機械的に検査できるものは文書ではなく検査にする」と
言っているが、ここで守りたいのは**2つのトークンの組み合わせ方**であり、
`check:token-usage` が見ているのは名前の集合である。組み合わせは CSS の1つの規則の中で
起きるとは限らず（Tailwind のクラス、コンポーネントの props、実行時の合成）、
**利用側の書き方を先回りして列挙することになる。** 教訓5 の禁止リストと同じ形になる。

#### 副作用: `--sg-color-bg-page` の使い道が消えた

サンプルページを直したところ、`--sg-color-bg-page` の参照が**ゼロになった。**
唯一の使い道が「前景に借りる」だったということである。

これは [Issue #65](https://github.com/shun2218-dev/sashigane/issues/65)
（`--sg-color-bg-*` が残っていて素の CSS からは面を塗るだけにできる）の証拠になる。
**この決定では消さない。** 面の色を読む需要が本当にゼロかは、まだ確かめていない。

#### 検査

- `test/color.test.ts` — **全360色相 × 両モード × 面4段 × 全5ランプ**で、
  塗りの上の文字が 4.5:1 以上。端の選び方を逆にすると**8件が落ちることを確認した**
- `scripts/check-sample-page.mjs` — サンプルページが5つとも実際に使っていること（原則3）。
  ボタン2種と塗りのバッジ4種で踏む
- `scripts/check-tailwind-adapter.mjs` — `text-on-accent` / `text-on-danger` が出ること

### 決定 5-15: 塗りの状態変化は、塗りの段を1段ずらす

> [Issue #83](https://github.com/shun2218-dev/sashigane/issues/83)。
> 決定1-15 で不透明度を退けたので、**それが代用していた需要を色で満たす必要がある。**

#### 観測 — 4本とも色を差し替えていた

| | 塗りボタンの hover |
|---|---|
| ichirizuka | `background: #dee5e7`（別の色） |
| pylabo | `filter: brightness(1.12)`（明度を上げる） |
| holosphere | `hover:bg-white/10`（面をアルファで組んでいる文脈） |
| pdf-merge-app | `hover:bg-primary/90`（shadcn） |

**不透明度そのものを動かしているものは1本も無い。** どれも「別の色にする」形である。

#### 決定: 面から遠ざかる向きへ1段

`--sg-color-accent-strong` / `--sg-color-danger-strong`。
`colorText` の段から**面から遠ざかる向きへ1段**動かす（明色は濃く、暗色は明るく）。

**保証は増える方向にしか動かない。** 塗りの上の文字はランプの端にあり（決定5-14）、
塗りが端へ寄れば対比は増えるだけである。

| | 塗りの上の文字 | 塗り自体の対比 |
|---|---|---|
| 通常（決定5-14） | 4.50:1 | 4.50:1 |
| 1段ずらした状態 | **6.04:1 以上** | **6.04:1 以上** |

全360色相 × 両モード × 名前を持つ面すべてで測った。

#### 塗りを持つランプすべてに出す — **改訂（2026-08-29）**

> **当初版を撤回した。** 「押せる塗りは2種類しかない。pdf-merge-app（shadcn）の
> 塗り variant は `default` と `destructive` の2つ」を根拠に accent と danger だけにしていた。
> **shadcn の生成コードは「過去の実装」ですらない**（教訓7、
> [Issue #88](https://github.com/shun2218-dev/sashigane/issues/88)）。
>
> しかも同じ PR の中で、pdf-merge-app の `opacity-50` 42件のうち41件を
> 「shadcn の生成コードだから観測に数えない」と切り捨てている。
> **同じ規則を片方向にだけ適用していた。**

`-mark` も `on-*` も同じ規則で全ランプに出している。**規則が同一のランプ間で
非対称を作らない。** 非対称は、利用側から見ると**逃げ道の有無**になる。

##### 原則3 の単位は「役割」であって「役割 × ランプ」ではない

原則3 は「セマンティックは実際に使う場所が1つ以上あるものだけ定義する」と言っている。
これは**役割を発明しないための歯止め**であり、ランプの一覧を欠けさせるためのものではない。

サンプルページは `accent-strong` と `danger-strong` を使っている。
`warning` / `success` / `info` の `-strong` と `--sg-elevation-front` は
**サンプルページでは未使用**で、`check:sample-page` がそう報告する。
**それは正しい報告である。** 役割としての使用場所はあり、
欠けているのは同じ規則で機械的に導かれる残りのランプと段だけである。

#### hover の控えにも同じ役割が出る

`-strong` も `--sg-color-*` なので、hover の控え（決定5-13）が自動的に写す。

```css
--sg-color-hover-accent-strong: var(--sg-primary-700);
```

**これは意図した挙動である。** `data-sg-interactive` の行の中に塗りボタンがあるとき、
行を hover すると文脈が1段深くなり、**その面での「1段強い段」**へ移る。
役割の意味が面によって変わらないという決定5-12 の性質が、ここでも保たれる。

#### 塗りを持たない要素は面の文脈で解く

輪郭だけのボタンは `data-sg-interactive` を付ける（決定5-13）。hover 中だけ1段深い面になり、
背景と前景が一緒に動く。**塗りを持つ要素にこれを使うと、hover の規則の
`background-color` が塗りに勝つ**ので、そちらは段の差し替えで表す。

#### 検査

- `test/fill-state.test.ts` — 1段ずらすと余裕が増えること、名前を持つ面では
  動かす先が必ず存在すること、warning / success / info には出ていないこと
- `scripts/check-sample-page.mjs` — サンプルページが実際に使っていること（原則3）
- `scripts/check-tailwind-adapter.mjs` — `bg-accent-strong` が出て `bg-warning-strong` が出ないこと

### 決定 5-16: 淡い塗りは「色のついた地」として持ち、その上の段を解き直す

> [Issue #87](https://github.com/shun2218-dev/sashigane/issues/87)。
> 決定5-14 が「ページ地との差が 3:1 に届かない」として保留していた論点。
> 決定3-2 の改訂でアルファ修飾子を塞いだ結果、**表現手段がゼロになった**ので決めた。

#### 需要

roles.md が **pylabo と holosphere で独立に観測**している。status は3つの変種を持ち、
そのうち1つが「淡い背景（元色の 12〜15%）— 帯・バッジの地」である。
決定5-14 の観測表でも、p と h で**最も多い**組み方は「淡い塗り＋アクセント色の文字」だった。

#### 保留の理由は、このシステム自身の規則で解ける

決定5-14 はこう書いていた。

```
淡い塗りとページ地の差   1.60 / 1.36  ✗（部品の境界は 3:1）
```

**3:1 を要求する理由が無い。** WCAG 1.4.11 が 3:1 を求めるのは
「その部品や状態を**識別するのに必要な**部分」である。
決定5-9 で **status を色だけで伝えるコンポーネントは作らない**（アイコンまたは
テキストラベルを必須にする）と決めてあるので、**淡い塗りは意味の唯一の手がかりではない。**

そして**面の梯子自身が 1.30:1 で成立している**（`bg-page` → `bg-surface`）。
面どうしの差に 3:1 を要求していないのに、色のついた地にだけ要求する理由が無い。

**淡い塗りは「塗り」ではなく「色のついた地」である。**

#### 観測どおりの組み方は、そのままでは成立しない

「淡い塗り＋その色の文字」を素直に書くと割る。

| | 明色（`danger`） |
|---|---|
| 段500 の文字を段100 の地に置く | **4.02:1** |
| 段400 のマークを段100 の地に置く | **2.84:1** |

**淡い塗りを面とみなして段を解き直す**（決定5-12 と同じ考え方）。

| モード | 地 | その色の文字 | 中間色の本文 | 面との差 |
|---|---|---|---|---|
| 明色 page | 段100 | 段600（4.87） | 10.55 | 1.21 |
| 明色 surface | 段200 | 段700（4.85） | 7.72 | 1.22 |
| 明色 inset | 段300 | 段800（4.56） | 5.39 | 1.25 |
| 暗色 page | 段900 | 段300/400（4.51） | 10.57 | 1.12 |
| 暗色 surface | 段800 | 段300（4.56） | 8.27 | 1.15 |
| 暗色 inset | 段700 | 段200（4.85） | 6.23 | 1.16 |

全360色相・両モード・名前を持つ面すべてで解ける。

#### 決定

```
--sg-color-{名前}-subtle      淡い塗り。面のすぐ外側の段
--sg-color-on-{名前}-subtle   その上に載せるその色自身。塗りに対して解く
```

塗りを持つランプすべて（accent + status 4色）に出す。名前は決定5-14 の
「塗りの上の文字は `on-{塗りの名前}`」に従う。塗りの名前が `danger-subtle` なので
`on-danger-subtle` になる。

**段は面のすぐ外側を取る。** 塗り自身は要件を持たないので、
「要件を満たす最も浅い段」がそのまま「最も淡い段」になる。
`gridline`（決定5-13 の第4の段）と同じ段を指す——どちらも「面のすぐ外側」だからである。

**アイコンにも文字と同じ段を使う。** 文字の段は 3:1 も必ず満たす。
決定5-7 がマークを1段明るい側に置いたのは**チャート系列を見分けるため**であり、
帯の中のアイコンには当てはまらない。役割を増やす理由が無い。

#### 保証しない範囲

**中間色の前景は `text-default` しか載らない。**

| 前景 | 淡い塗りの上（全360色相・両モード・全面の最悪） |
|---|---|
| `text-default` | **5.39** ✓ |
| `text-muted` | **4.27** ✗ |
| `text-faint` | **3.21** ✗ |

帯の本文に `text-muted` を使うと、明色の深い面で割る。
**サンプルページはこれを踏まないように `text-default` で書いてある。**
検査は `--sg-color-*` の名前しか見ないので、この組み合わせは捕まらない（教訓5）。

**`--sg-color-{名前}-mark` を淡い塗りの上の枠線に使うと 2.52:1 になる。**
境界は装飾で要件を持たない（決定5-12）ので割ってはいないが、
**帯の地に対しては弱い。** 枠線が状態の唯一の手がかりになる組み方をしないこと（決定5-9）。

##### 16進の丸めは保護されない

`on-*-subtle` の余裕は **4.555**（全360色相・両モード・全面の最悪）しかない。
`colorRequirements` はページ地に対する要件しか持たないので、
決定2-6 改訂（[Issue #52](https://github.com/shun2218-dev/sashigane/issues/52)）の
**丸めで割ったときだけ寄せる仕組みは、この組には効かない。**

**測った。** 16進に落とした後の最悪は **4.563** で、5400 組すべてが 4.5 を満たしている。
丸めは対比を上下どちらにも動かすので、いまはたまたま上に動いている。
**余裕が薄いことは変わらない**ので、段の解き方を変えたら測り直すこと。

これは `on-*`（決定5-14）と同じ扱いである。あちらも塗りに対して解いてあり、
ページ地に対する要件の表には載っていない。

#### 退けた案: 色のついた面（`data-sg-surface="danger"`）として持つ

塗るだけの道が構造的に無くなるので魅力的だが、**面を名乗ると約束が大きすぎる。**
面は「その中のすべての役割が成立する」ことを意味する（決定5-12）ので、
識別色もチャートの罫線も解き直す必要が出る。**帯やバッジにチャートは入らない。**

塗りとして持てば、対になる前景は `on-*-subtle` の1つで足りる。
決定5-14 が不透明な塗りで採った形と同じである。

#### 検査

- `test/fill-state.test.ts` — その色自身が 4.5:1 を満たすこと、**解き直さないと割ること**、
  中間色は `text-default` だけが載ること、面のすぐ外側の段であること
- `scripts/check-sample-page.mjs` — 10個すべてに使う場所があること（原則3）
- `scripts/check-tailwind-adapter.mjs` — `bg-danger-subtle` / `text-on-danger-subtle` が出て、
  `bg-neutral-subtle` は出ないこと（中間色は面であって塗りではない）

│  │  │  ├─ generate/            スケール導出・不変条件テスト
│  │  │  └─ index.ts
│  │  ├─ dist/                   ← .gitignore
│  │  └─ package.json            ← dependencies を空に保つ
│  └─ ui/                        @sashigane/ui
│     ├─ src/…                   内部 import は @sashigane/ui/… に統一
│     ├─ components.json
│     └─ package.json

├─ docs/

### 決定 4-1: コンポーネントパッケージは `packages/ui`

> **原則4の記述（`packages/components`）からの変更。**

shadcn monorepo の公式慣例に合わせる。alias が `@sashigane/ui/components/...` となり、
レジストリビルド時の `@/components` 置換も自然になる。

### 決定 4-2: `@/` エイリアス問題の対処

パッケージ内では `@sashigane/ui/...` を使い、レジストリビルド時に正規表現で `@/...` に置換する。

```jsonc
// packages/ui/tsconfig.json
{ "compilerOptions": { "paths": { "@sashigane/ui/*": ["./src/*"] } } }
```

```js
content = content.replace(/@sashigane\/ui\/(components|lib|hooks|types)/g, "@/$1");
```

shadcn CLI には公式の monorepo 対応がある（`shadcn init --monorepo`）。
各 workspace に `components.json` が必要で、`style` / `iconLibrary` / `baseColor` を
全 workspace で揃える必要があり、Tailwind v4 では `tailwind` 設定を空にする。

**CLI 4.5.0 に `components.json#style` を無条件に書き換えるバグがある**
（[shadcn-ui/ui#10496](https://github.com/shadcn-ui/ui/issues/10496)）。
サードパーティレジストリに影響するため、CLI のバージョンを固定して扱う。

### 決定 4-3: 配布の3段階

`registry:base` は実在する（公式の型定義に "Use for entire design systems" として存在）。

| 導入深度 | registry type | 内容 |
|---|---|---|
| `@sashigane/tokens` | `registry:theme` 相当 | `cssVars` / `css` のみ。React 非依存 |
| `@sashigane/<component>` | `registry:ui` | コンポーネント単体 |
| `@sashigane/base` | `registry:base` | 全部 |

registry item は `cssVars`（`theme` / `light` / `dark`）と `css`（`@layer` / `@utility` /
`@keyframes` を注入）を持てるため、**トークンのみの配布は registry の機構だけで実現できる。**

### 決定 4-6: バージョンは揃える。出所はトークン層の中に1つ

> [Issue #93](https://github.com/shun2218-dev/sashigane/issues/93)。
> [branching.md](./branching.md) が唯一の未決定として残していた論点。

#### 揃える

**「別にする」理由は、ほぼ全部が npm の依存解決を前提にしている。**
`tokens ^1.0 に依存する button 2.3` を解いてくれる主体がいるから、独立に動かせる。

**この設計にはその主体がいない。** 原則6 は npm publish せず、レジストリ方式で
利用側リポジトリにコードを落とす。**依存範囲を書く場所も、解決する仕組みも無い。**

そして契約は **CSS 変数名**である。コンポーネントが `var(--sg-elevation-front)` を
参照していて、利用側のトークンが古くてその変数が無いと、
**宣言ごと無効になって消える。エラーは出ない**（教訓4）。

| | 別バージョン | 単一バージョン |
|---|---|---|
| 組み合わせ | `tokens 1.2 × button 2.1` が生まれる。**誰も検査していない** | 「同じタグから取ったもの同士」だけを保証すればよい |
| 壊れ方 | 静かに消える | 組み合わせが作れない |
| 代償 | — | トークンだけの利用者にも版が上がる |

代償は軽い。決定3-4 が**生成日時を入れないと決めている**ので、
中身が変わっていなければ再取得してもバイト単位で同じで、diff は出ない。

**条件つきである。** コンポーネントを別リポジトリへ出すなら前提が変わる。
そのときは「同じタグから取ったもの同士」が成り立たなくなるので、決め直す。

#### タグ形式は `v0.1.0`。リポジトリに1本

パッケージごとの `@sashigane/tokens@0.1.0` にはしない。**単位はリポジトリである。**

#### バージョンが指すもの: 配信スナップショットの識別子

branching.md の「レジストリ方式では npm publish しないため、バージョンが何を指すのか」への答え。

利用側が持っているのは**取得した時点のスナップショット**であって、解決された依存ではない。
タグはその識別子である。

#### 出所は**トークン層の中**に1つ

`packages/tokens/package.json` の `version` だけが出所で、
リポジトリのルートも `apps/*` も version を持たない。2箇所に持つと静かにずれる（決定2-6）。

**ルートではなくトークン層に置く理由が2つある。**

1. **原則4。** `check:tokens-isolation` は `packages/tokens/src` が外を参照しないことを
   要求している。ルートの `package.json` を読みに行くと、
   **`packages/tokens` を単体で取り出したときに壊れる**
2. **原則1。** トークンが唯一の正であり、他は全部それに従う。
   デザインシステムのバージョンは**トークンのバージョン**である

**生成器はブラウザでも動く**（テーマビルダーが `toTokensCss` を呼ぶ）ので、
ファイルを読む形にはできない。JSON の import なら両方で成立する。

#### 生成物ヘッダに入れる

決定3-4 が「**バージョン** | 扱いが未決定。決まってから足す」と空けていた場所。

```
生成物。手で編集しない。@sashigane/tokens v0.1.0 が生成する。
```

レジストリ方式では生成物が利用側リポジトリへ落ちる。
**落ちた先で「どのスナップショットを持っているか」を知る手がかりはこれしかない。**

生成日時と違い、**バージョンが動くのはリリースのときだけ**なので、
「内容が同じでも毎回 diff が出る」という決定3-4 の懸念には当たらない。

#### 規則の在り処をタグに固定する

決定3-4 が「タグ固定にするかどうかは、バージョンの扱いと一緒に決める」と保留していた点。

| | 在り処 |
|---|---|
| リリース済み | `.../tree/v0.1.0/docs` |
| 未リリース（`0.0.0`） | `.../tree/HEAD/docs` |

**固定する理由は、配布された生成物より新しい決定を読ませないためである。**
`HEAD` を指したままだと、利用側は「手元の CSS には無い決定」を読むことになる。

未リリースのあいだ `HEAD` にするのは、**固定する先が無い**からである。

#### 破壊的変更の定義: セマンティックの名前が消えるか、意味が変わること

**契約は名前表（`tokens.layers.json`）である。**

| 層 | 契約か |
|---|---|
| セマンティック | **契約。** 利用側が参照してよい唯一の層（原則3） |
| 差し込み口（`--sg-font-brand-*`） | **契約。** 利用側が定義する（決定2-7） |
| プリミティブ | 契約ではない。参照が禁止されている |
| 内部（`--sg-color-hover-*` など） | 契約ではない。同上 |

この定義で数えると、**このセッション（2026-08-29）だけで破壊的変更が3件ある。**

| 変更 | 内容 |
|---|---|
| Issue #65 | `--sg-color-bg-surface` / `-inset` / `-overlay` を落とした |
| Issue #81 | `--sg-elevation-0` 〜 `-3` を落とした（プリミティブなので**契約ではない**） |
| Issue #83 | `--sg-color-hover-bg` を `--sg-color-deeper-bg` へ改名（内部なので**契約ではない**） |

**契約に当たるのは1件目だけである。** 決定5-12 改訂が
「これは破壊的変更である。いま影響が出ないのは、タグを1つも切っていないからである」
と書いたのは正しかった。

##### `packages/tokens` の TS の export は契約ではない

**配布されるのは生成物であって TS ではない**（原則6）。利用側リポジトリへ落ちるのは
`tokens.css` / `theme.css` / `tokens.scss` / `tokens.js` / `tokens.d.ts` の5つで、
`packages/tokens/src` は落ちない。`package.json` も `private: true` である。

`tokens.js` と `tokens.d.ts` が出す**名前**は契約に含まれる。
名前表から機械的に出しているので、上の定義がそのまま当たる。

> **この決定と同じ PR で `DOCS_URL` を `docsUrl()` に変えている**（自己レビュー B1）。
> 名前表は動いていないので、この定義では破壊的変更にならない。
> **書いていない範囲は、次に誰かが判断に迷う。**

**0.x のあいだは破壊的変更でマイナーを上げる**（semver の慣行）。
1.0 の条件は、**レジストリ配信が動いていて、コンポーネントの実需要が固まっていること**である。

#### いまタグを打たない

コンポーネントが1つも無く、レジストリ配信も未実装の状態で `v0.1.0` を切ると、
**配信していないものをリリースしたことになる。**
規則と仕掛けだけ用意し、`version` は `0.0.0`（未リリース）のままにする。

#### 検査

- `scripts/check-output-header.mjs` — 全生成物にバージョンが入っていること。
  **陰性対照つき**（バージョンの行が落ちても、他の行があるので見た目には気づけない）
- `scripts/check-docs-refs.mjs` — **`version` を持つ `package.json` が1つだけであること。**
  文書に書くだけでは守られない（教訓3）。2箇所になった瞬間、この決定が防ごうとしたことが起きる
- `packages/tokens/test/output-header.test.ts` — 出所が1箇所であること、
  **リリース済みのヘッダがツール名とバージョンを離さずに書くこと**

**リリース済みの経路は普段1度も実行されない。** `version` は `0.0.0` のまま長く続き、
最初のタグを切る日に初めて動く。そこで初めて壊れていると分かる形にしないため、
`outputHeader` はバージョンを引数で受けられるようにしてある。

### 保留 4-5: レジストリ配布物の扱い

`.gitignore` は `apps/*/public/r/` を無視している。
原則1「生成物はコミットしない」に従った形だが、**レジストリ JSON を静的ホスティングする場合、
デプロイ時にビルドする前提が要る**。

これは Phase 4 の論点であり、現時点では判断を保留している。
`.gitignore` の記述は暫定であり、決定ではない。Phase 4 で以下のいずれかを選ぶ。

- デプロイパイプラインでビルドして配信する（原則1 を維持）
- 配布物だけは例外としてコミットする（原則1 に例外を作る）

### 決定 4-4: CI で検査すること

原則4「依存は一方通行」の証明として、以下を機械的に検査する。

| 検査 | 実装 |
|---|---|
| `packages/tokens/package.json` の `dependencies` が空 | ✅ `pnpm check:tokens-isolation` |
| `packages/tokens/src` が外部モジュールを import しない | ✅ `pnpm check:tokens-isolation` |
| スケールの不変条件（比率・減算閉包・単調性・記載値との一致） | ✅ `pnpm test` |
| 生成物がコミットされていない | ✅ `pnpm check:no-build-output` |
| `main` への PR が `develop` からのみ | ✅ CI の `branch-flow` ジョブ |
| このファイルの数値表が生成器と一致 | ✅ `pnpm check:docs-scales` |
| **素の HTML に `tokens.css` だけを読み込み、CSS変数が解決すること** | ✅ `pnpm check:tokens-standalone` |
| 生成した Tailwind アダプタが期待どおりのユーティリティを出す | ✅ `pnpm check:tailwind-adapter` |
| **コンポーネントがプリミティブを参照していない**（原則3） | ✅ `pnpm check:token-usage` |
| Tailwind の任意値記法を使っていない（決定3-1 の残る穴） | ✅ `pnpm check:token-usage` |
| `tokens.js` の値が `tokens.css` とずれていない（決定2-6） | ✅ `pnpm check:token-values` |
| 生成した `tokens.d.ts` が型として成立し、プリミティブを引けない | ✅ `pnpm check:token-types` |
| `apps/docs` がビルドできる | ✅ CI |

`check:tokens-standalone` は静的検査である（外部依存の有無と、参照する変数がすべて定義済みか）。
**実ブラウザでの解決は別途目視で確認した。** `apps/docs` を起動して `/standalone.html` を開くと、
`tokens.css` 1枚だけで組んだページが表示される。

2つ目は「`react` を禁止する」ではなく「**相対パスと `node:` 以外を全部禁止する**」形で実装した。
禁止リスト方式だと、リストに無い依存が入ったときに黙って通る（教訓4「静かに失敗するものを疑う」）。

`pnpm verify:coverage` は観測対象4本のローカル clone を前提とするため **CI では動かせない。**
スケールを変更したら手元で実行し、`docs/verification.md` を更新する。

## 6. コンポーネント

> **Phase 3 の入口**（[Issue #95](https://github.com/shun2218-dev/sashigane/issues/95)）。
> Phase 1（トークン層）が完了した時点で、着手前に決めていなかったことが2つあった。

### 決定 6-1: 最初は Card → Button → Badge → Separator → Table。進捗バーは後ろへ置く

原則7 は「最初は5個以内」と言っている。
[roles.md](./roles.md) の「既存4本で3回以上書き直した」は **6つある。1つ多い。**

**数で切らず、「何が他の土台になるか」で並べた。**

| 順 | | 何を決めるか |
|---|---|---|
| 1 | **Card** | 面の宣言（`data-sg-surface`）の使い方。以降のコンポーネントは全部この上に乗る |
| 2 | **Button** | 対話状態（`data-sg-interactive`・`-strong`）と focus の型 |
| 3 | **Badge** | 決定5-9 の「status の非色手がかりを構造的に必須にする」形 |
| 4 | **Separator** | 境界。Table の部品 |
| 5 | **Table** | Card + Separator + 行 hover の**合成**。土台が組み合わさるかの検証台 |

後ろへ置くのは**進捗バー**。6つの中で唯一、**他の何もその上に乗らない。**

#### 「需要が無い」ではない

観測は3回あり、需要はある。**教訓7 が禁じているのは「観測に無いから持たない」であって、
「順番を後ろにする」ことではない。** 5つが済んだら次に作る。

**落とすのではなく並べているので、教訓7 の「この役割が無いと利用側は何を書くのか」には
答えなくてよい。** 答えが要るのは、作らないと決めるときである。

### 決定 6-2: cva で書く。原則3 の強制は「書き方」ではなく「生成された CSS」に当てる

原則6 は**配布**（レジストリ方式）を決めているが、**何で書くかは決めていなかった。**
「shadcn レジストリ方式」という語から書き方まで決まっていると読むのは教訓6 である。

#### 前提が1つ間違っていた

当初は「cva を使うと `check:token-usage` から見えなくなる」を cva の欠点として数えていた。
**測ったら違った。**

| 書き方 | `p-[7px]` が検出できるか |
|---|---|
| `className="p-[7px]"` 直書き | **できる** |
| `cva(...)` の中 | できない |
| `const V = { sm: "p-[7px]" }` のオブジェクト引き | できない |
| `const base = "p-[7px]"` の定数1本 | できない |

検出器は `class=` / `className=` の**属性の位置**を起点に文字列を拾う。
**間接を1段でも挟むと見えない。cva 固有の問題ではない。**
variant を持つコンポーネントはどう書いても間接が入るので、
**検査の変更は cva を選ぶかどうかと独立に要る。**

なお **`--sg-*` の参照検査（原則3 の本体）はファイル全文を走査**しているので**無傷**である。
影響を受けるのは Tailwind クラス側（任意値・素の数値・アルファ修飾子）だけ。

#### 3案を測った

| 案 | 工数 | 誤検出 | 問題 |
|---|---|---|---|
| ヘルパー名を列挙して読む | 実装 **18行**（プロトタイプ実測） | cva 内の variant キー値4本を拾うが全部許可集合を通る | **禁止リスト方式**になる（教訓5）。`tv()` も自作ヘルパーもオブジェクト引きも黙って通る |
| 全文字列リテラルを既定拒否 | 中 | **96本中33本が誤発火**（`"100%"` `"デスクトップ"` `"[data-theme]"` `"#000"`） | 除外の運用が要る。「理由の書けない除外を足さない」と両立しにくい |
| **生成 CSS に規則を当てる** | 新規 305 行 | ほぼゼロ | file:line が CSS に残らない（ソースを引き当てて復元する） |

**誤検出の数は `apps/docs/src` の React ソースで測った。**
`packages/ui` がまだ空だったので代用している。**コンポーネントで測った数ではない。**
コンポーネントは文字列が少ないので誤発火は減るはずだが、
`aria-label` の既定値や `data-sg-surface` の値が残るのでゼロにはならない。

#### 決定

**Tailwind に `packages/ui` を走査させ、生成されたセレクタに規則を当てる**
（`pnpm check:component-classes`）。

Tailwind の候補抽出は**ソースを素のテキストとして読む**ので、cva でもオブジェクト引きでも
`tv()` でも自作ヘルパーでも一括で拾う。**ヘルパー名を列挙しないので、
許可リスト方式（教訓5）のままでいられる。**

規則そのものは `scripts/lib/class-rules.mjs` に置き、`check:token-usage` と**共有する。**
写しを作ると、片方だけ直したときに「同じものに2つの道があって片方だけが安全」になる——
面（決定5-12）でも hover（決定5-13）でも不透明度（決定1-15）でも退けてきた形である。

**検査はコンポーネントより先に入れる。** 検査の無い状態でコンポーネントを書かない。

#### この検査が見逃す範囲（教訓5）

- **Tailwind が候補として読めないもの。** `p-${段}` のような実行時の組み立ては
  Tailwind 自身が拾わないので CSS が生成されない。`check:token-usage` と同じ限界
- **ユーティリティに一致しない文字列。** `rounded-md` は写像していない名前なので
  **CSS が生成されず、エラーも出ず、角丸が付かない**（教訓4）。
  この検査は「書かれたのに出なかったもの」を見ていないので捕まえられない。
  打ち間違い（`bg-acent`）も同じ。[Issue #96](https://github.com/shun2218-dev/sashigane/issues/96)
- **`style` 属性の生値と CSS-in-JS。** トークンを経由しないのでクラスが現れない

#### 実装で2回踏んだもの

どちらも**陽性対照（通るべきものが落ちないこと）が捕まえた。**
発火する側の対照だけでは、両方とも「違反 0 件」に見えていた（教訓2）。

1. **`source(none)` を付けていなかった。** Tailwind は既定でリポジトリ全体を走査する。
   `scripts/` にある**陰性対照のフィクスチャ文字列まで拾って**198件のセレクタが出ていた
2. **セレクタの取り出しを正規表現でやっていた。** `(?:^|[{};])([^{};]*)\{` は
   区切り文字を消費するので、**連続する規則の2つ目以降を丸ごと飛ばす。**
   `@layer utilities` の中身と `@media (hover: hover)` の中身が1件も取れていなかった

### 決定 6-3: 「書いたのに消えた」を、素の Tailwind との差で見る

> [Issue #96](https://github.com/shun2218-dev/sashigane/issues/96)。
> 決定6-2 の検査を実装している最中に見つけた穴。

#### 何が起きるか

写像していない Tailwind の名前を書くと、**CSS が生成されない。
エラーも警告も出ない。角丸が付かないまま、それらしく表示される。**
教訓4「静かに失敗するものを疑う」そのものである。

`packages/ui` に shadcn 風のクラスを18件書いてコンパイルした結果、
**生成されたのは5件で、13件が黙って消えた**（`rounded-md` `text-sm` `font-medium`
`shadow-sm` `h-10` など）。

**消えること自体は意図どおりである。** `check:tailwind-adapter` は
`rounded-md` `font-medium` `shadow-sm` が**生成されないこと**を明示的に検査している。
**穴は「消えること」ではなく「書いても黙っていること」である。**

#### なぜ Phase 3 で効くか

**shadcn を書き慣れた手は `rounded-md` と `text-sm` を書く。**
決定6-2 で cva を採ったので書き方が shadcn に寄り、**語彙も一緒に寄ってくる。**

そして決定6-2 の検査は**生成されたセレクタ**を見るので、
**生成されなかったものは原理的に見えない。**

#### 決定

**同じソースを素の Tailwind でもコンパイルして差を取る。**
素の Tailwind が出すのに我々が出さないものが、書かれたのに消えたものである。

**列挙が要らない。** 「素の Tailwind にはあるが我々には無い名前」は差から出るので、
禁止リストを持たなくてよい（教訓5）。機構は決定6-2 のものをそのまま使う。

| 決めたこと | |
|---|---|
| 置き場所 | **`check:component-classes` に含める。** 走査対象も機構も同じで、コンパイルが1回増えるだけ。別スクリプトにすると抽出処理をもう1つ共有ライブラリに出すことになる |
| `h-10` のように**両方の規則に当たるもの** | **「消えた」側だけで報告する。** 書いた人が受け取るべき事実は「これは生成されない」であって内訳ではない。同じ1件を2回出さない |
| 原因の内訳 | **分けて報告しない。** 説明文に2つの原因（写像していない語彙／スケールの外）を並べ、どちらの直し方も示す |

9回コンパイルして全体で **0.75 秒**。結果を使い回す仕掛けは入れていない。

#### 過剰に検出するもの — コメントに書いた名前

Tailwind はコメントの中も素のテキストとして読む。したがって
「`rounded-md` は写像していない」と**説明を書くと、その説明が落ちる。**
決定6-3 の性質上、**まさにその説明が書かれる**コードである。

言語ごとのパーサでコメントだけを除くのは割に合わない
（`check:token-usage` が `--sg-space-N` で同じ判断をしている）。**逃げ道を用意した。**

| 書き方 | |
|---|---|
| `// rounded-md は写像していない` | **落ちる** |
| ``// `rounded-md` は写像していない`` | **落ちる**（バッククォートは効かない） |
| `// rounded-* の t シャツ語彙は写像していない` | 落ちない |
| `// text-{sm} や shadow-{sm} は写像していない` | 落ちない |

**逃げ道が効くことは陽性対照で確かめている。** Issue #63 で
「文書が案内していた逃げ道が一度も機能していなかった」をやっているため（教訓2）。
対照を壊すと（`rounded-*` を `rounded-md` に戻すと）検査自体が失敗する。

#### 抽出の境界は Tailwind が握っている

同じ名前でも、直前の文字で抽出されたりされなかったりする。

```
/* rounded-md は…    → 抽出される
（rounded-md は…     → 抽出されない（直前が全角の括弧）
```

**「書いたものは全部見ている」ではない。** 上の逃げ道もこの性質の上に乗っているので、
**Tailwind の判定が変われば逃げ道も変わる。** 陽性対照を持っているのはそのためである。

#### この案が捕まえないもの

**どちらのテーマにも無い名前。**
`bg-primary` `text-muted-foreground` `border-input` のような shadcn 固有の名前と、
打ち間違い（`bg-acent`）は、**素の Tailwind でも生成されない**ので差に出ない。

届かせるには「ソースに書かれた class 候補」が要るが、
**候補抽出は Tailwind が握っていて外から呼べない**（CLI は候補を出さない）。
自前で抽出すると、決定6-2 が退けた「全文字列リテラルを既定拒否」に戻る。

**穴として残す。** 見逃す範囲は検査自身のコメントに書いてある（教訓5）。

### 決定 6-4: ドキュメントサイトは Fumadocs。Storybook はいま採らない

> [Issue #99](https://github.com/shun2218-dev/sashigane/issues/99)。
> **Storybook はこのリポジトリで一度も決定されていなかった**（[agent-failures.md](./agent-failures.md) の 2026-08-30）。
> `development-process.md` に理由の書かれていない規則が1本あっただけである。

#### Storybook をいま採らない

**AI 可読の要件は、原則6 のレジストリ配信がほぼそのまま満たす。**

| | |
|---|---|
| ビルド後の `public/r/<name>.json` | `files[].content` に**コンポーネントのソースそのもの**を含む |
| 公式 shadcn MCP | 利用側が `components.json` に `"@sashigane": "https://…/{name}.json"` を書くだけで、エージェントが検索・ソース取得・インストールできる。**こちら側の作り込みは不要** |
| 例（demo） | registry item そのもの。**例を1箇所に置けば、サイトの描画・配信 JSON・利用側へのインストールを兼ねる** |

一方 **Storybook の MCP（`@storybook/addon-mcp`）は dev server を必要とし、
静的ビルドに対応していない**（`localhost:6006/mcp`）。
**手元の開発を助ける道具であって、公開して AI に参照させるものにはならない。**

したがって Storybook は「ドキュメントサイトの代わり」ではなく、
**サイトの上に乗せる開発用の道具**という位置になる。得られるのは隔離ハーネス・controls・
story 生成/テスト・視覚回帰のエコシステムである。

**いまは採らない。** 例を素の React コンポーネントとして置くので後から乗せても手戻りしない。
足すかどうかは**サイトができてから、実際に足りないものを見て決める**（原則7 を道具にも当てる）。

**「観測4本のうち holosphere が Storybook を使っている」は根拠にしない**（教訓7）。

#### 型情報は抽出できる。フレームワークの機能ではない

`react-docgen-typescript` で cva の `VariantProps` がリテラルの union として取れる（実測）。

```
props:
  heading?: string          説明: 見出し。空のときは領域ごと出さない
  interactive?: boolean     既定値: false   説明: 押せるカードにする
  tone?: "surface" | "inset" | null    説明: 面の深さ。決定5-12 の梯子に対応する
  size?: "sm" | "md" | "lg" | null
```

**cva の variant キーに書いた JSDoc がそのまま説明になる。**
型と説明をコンポーネントのソース1箇所に置ける。

拾えないものが2つある。**`defaultVariants` の既定値は署名に現れないので出ない。**
`| null` が付くのは cva の型どおりである。どちらも扱いを決めれば済む。

**`react-docgen-typescript` 2.4.0 は TypeScript 7 で動かない**（`ts.JsxEmit` が未定義）。
いまは TS 5.9 系なので問題ないが、**TS 7 に上げるときに引っかかる。**

#### 土台の選定

**測った。**

| | 版 | 成熟度 | React の生きた例 |
|---|---|---|---|
| **Fumadocs** | 16.15.4 | v1 前ではない。ただし 2024-01 の v8 から2年で v16、**16.x だけで 123 リリース** | MDX で可 |
| Docusaurus | 3.10.2 | **3.x が長い。最も枯れている** | MDX で可 |
| Starlight | 0.41.10 | **v1 前** | React island で可 |
| Nextra | 4.6.1 | **最終更新 2025-12-04。9か月動いていない** | MDX で可 |
| VitePress | 1.6.4 | v1 安定 | **Vue 前提で不自然** |

Nextra と VitePress は上の理由で落ちる。残るのは Fumadocs と Docusaurus と、
現行の Vite を育てる案である。

**Fumadocs を採る。**

> **2026-08-30 改訂。決め手として書いたことが誤っていた。**
>
> 当初は「Fumadocs は Tailwind + shadcn 系なので**サイト自体をトークンで組める**」を
> 決め手にした。**測っていなかった。**
> 実際に重ねると**ビルドが落ちる**（[experiments/fumadocs-adapter-coexistence.md](./experiments/fumadocs-adapter-coexistence.md)）。
>
> ```
> Error: Cannot apply unknown utility class `sm:ps-7`
> ```
>
> `fumadocs-ui/css/lib/base.css` の `@apply` が、`--*: initial` で
> spacing を落とされて解決できない。**chrome をアダプタで組むことはできない。**
>
> 決め手は崩れたが、**採用は維持する。** 残る利点は
> MDX・目次・検索が標準で付き、型表（`fumadocs-typescript`）と llms.txt が公式にあること。
> 代償は**変化の速さ**である（上の表）。

**トークンは CSS 変数の層でなら chrome でも使える**（`tokens.css` を重ねてもビルドは通る）。
アダプタが使えるのは**プレビューとサンプルページ**で、そちらは別ビルドにする。

`registry-template` はドキュメントサイトの土台にはしない。実際に見ると
**タイトル・1行説明・デモだけ**で、props も型も導入手順も無い。**配信の出発点である。**

#### 例は唯一の正を1つ持つ

トークンが唯一の正であるのと同じ形にする。
**例を1箇所に置き、サイトの描画・配信 JSON・型表をそこから出す。**
Storybook を後から足す場合も、story はその例を import する薄い層になる。

```
packages/ui/src/<component>/examples/
  default.tsx   通常
  empty.tsx     空
  edge.tsx      エッジケース
```

**この3つを必須とする。** 追加は自由。**素の React コンポーネントとして書く**ので、
どの土台からでも import でき、型検査も効き、registry item にもできる。

> **場所と形をここで決めたのは、決めないと規則が判定できないからである。**
> `development-process.md` は「例がない時点で自己レビュー不合格」と言っている。
> 場所も形も未定のままだと、**満たしているかどうかを誰も言えない規則**になる。
> 書き換え前の「Storybook のストーリー」は根拠が無かったが**判定はできた。**
> 根拠を得た代わりに判定を失っては、元より悪い（自己レビュー D1）。
>
> **機械的な検査は Card と一緒に入れる**（教訓3）。いま入れても対象が無い。

MDX の中に直接書く案は採らない。**サイトに閉じてしまい、配信 JSON に出せず、
型検査も効かない。** 決定6-4 が「唯一の正から3つを出す」と言っていることと両立しない。

#### 測って決めたこと（2026-08-30）

[experiments/fumadocs-adapter-coexistence.md](./experiments/fumadocs-adapter-coexistence.md)。

| | 決めたこと |
|---|---|
| **サイトをトークンで組む範囲** | chrome は**素の Tailwind**。アダプタは入れられない（ビルドが落ちる）。プレビューとサンプルページは**アダプタで別ビルド**する |
| **プレビューの方式** | **iframe を使わない。** アダプタを通した出力に実行時のリセットは残らない（`--*` の出現数 0、`:root` は `--sg-*` 372 件のみ）ので、別ビルドの CSS を同じページに載せられる |
| **デプロイ先** | **Vercel** |

同名のクラスは出るが、**測った 76 件では値がすべて一致した**（`var()` を解決し
`calc()` を畳んで比較。わざと 1 件ずらして比較器が発火することも確かめてある）。

**「全部一致する」とは言えない。** 決定3-3 が値の一致を約束しているのは radius だけで、
spacing は倍数規約、duration は独自のアンカー（決定1-6）という別の理屈である。
**測った範囲の話にとどめる。**

サイト側の Tailwind に `packages/ui` を走査させなければ衝突自体が起きないはずだが、
**これは推測である**（Fumadocs の既定の走査範囲は未測定）。

**これは規約であって検査ではない。**
[Issue #102](https://github.com/shun2218-dev/sashigane/issues/102) で検査にする。

##### iframe は要らなかった

当初は「Fumadocs を使うならプレビューは iframe で隔離することになる」と書いていた。
**測っていなかった。** そして**iframe を前提に置いて、そこから
フレームワークの選択肢を狭めていた**（教訓8 と同じ形）。

サンプルページも**埋め込む必要がない。** 独立した URL にして、
テーマビルダーが選んだ色をパラメータで渡す。

#### 実装のときに決めたこと（2026-08-30）

| | 決めたこと |
|---|---|
| `sample-page.html` の扱い | **場所を動かさない**（`apps/docs/src/sample-page.html`）。`check:sample-page` がこのパスを見ている（Issue #61）。**Route Handler がビルド時に読み、生成した CSS を差し込んで `text/html` で返す** |
| サンプルページの形 | **独立した URL（`/sample`）。React を1行も通らない。** 色・テーマ・密度・書体を URL パラメータで受け取る |
| レジストリ JSON の配信元 | **同じアプリの `public/r/`**（決定4-1 の構成図どおり） |

##### サンプルページから iframe が消えた

以前はテーマビルダーの中に `srcdoc` で埋め込んでいた。理由は Tailwind ではなく
**`:root` の巻き込み**である——生成物は `:root` と `@media (prefers-color-scheme)` と
`[data-theme]` を書くので、同じドキュメントに入れるとビルダー自身の見た目まで変わり、
「生成物だけで成立したのか」が判別できなくなる。

**別の URL にすれば、隔離そのものが要らない。**
しかも Route Handler にしたことで、**ページが React を通らなくなった。**
実測でスクリプト数は **0** である。
**「React が要らないことを見せるページ」が、実際に React を通らない。**

前セッションで `srcdoc` の iframe のスクリーンショットが断続的に空白になり
見た目の確認ができなかった問題も、これで消えた。

##### `next-env.d.ts` はコミットしない

Next.js が生成し、中身が `.next/` を指す。**原則1 のとおり生成物である**
（`check:no-build-output` が「型定義の生成物」として既に検出した）。

無い状態でも `pnpm typecheck` が通ることは確かめた。
**「通った」が「見ていない」でないことも、わざと型エラーを入れて確かめてある**（教訓2）。

### 決定 6-5: 同名になるクラスは、素の Tailwind と値が一致していなければならない

> [Issue #102](https://github.com/shun2218-dev/sashigane/issues/102)。
> 決定6-4 の実測（[experiments/fumadocs-adapter-coexistence.md](./experiments/fumadocs-adapter-coexistence.md)）で見つかった穴。

#### 何が起きうるか

ドキュメントサイトは **chrome を素の Tailwind、プレビューを我々のアダプタ**で
別々にビルドし、**同じページに載せる**（決定6-4）。このとき同名のクラスが両方に現れる。

**読み込み順で勝った方が効く。** 値が違えば、chrome かプレビューのどちらかが
黙って変わる。**エラーは出ない**（教訓4）。

いま値が揃っているのは決定3-3 の規約のおかげである。**規約であって検査ではなかった。**

#### 決定

**同名になるクラスは値が一致していなければならない。**
一致しない写像は足せない。理由があるなら許可リストに理由つきで書く（教訓5）。

`pnpm check:component-classes` が見る。**決定6-2・6-3 と同じ機構**（我々のビルドと
素の Tailwind のビルドを両方走らせる）を使うので、含めた。

| 決めたこと | |
|---|---|
| 判定 | `var()` を再帰的に解き、`calc()` の掛け算を畳み、`0px` と `0`、`calc(infinity * 1px)` と `9999px` を揃えてから値を比べる |
| 対象 | **`theme.css` の名前空間から候補を組み立てる。** コンポーネントが実際に使ったものだけを見ると、**まだ書かれていない写像のずれに気づけない。** 危険は「書いたか」ではなく「両方が生成しうるか」で決まる |
| 例外 | 理由つきの許可リスト（`PARITY_ALLOW`）。**1件ある**（下記） |

**段は手で並べない。** 並べると写像を増やしたときに、足し忘れた分だけ黙って検査されない
（`check:token-usage` が許す数値を `theme.css` から取っているのと同じ判断）。
現在 **185 件**が対象になっている。

#### 唯一の例外は `ease-in-out`

```
我々: --tw-ease: ease-in-out
素  : --tw-ease: cubic-bezier(0.4, 0, 0.2, 1)
```

**決定1-14 が「イージングは値を持たない」と決めている。**
観測4本にカスタムの `cubic-bezier` は1件も無く、使われていたのは CSS の組み込み語だけだった。
`--ease-*` のリセットで `ease-in-out` が消えるので、**語をそのまま戻している。**

素の Tailwind は自分で曲線を決めるので値は一致しないが、
**こちらは値を決めていない。写像を直す事案ではない。**

#### 対照

**比較器を純粋な関数にしてある。** CSS の文字列2つを渡して、
値が同じものを不一致と言わず、**違うものを検出すること**を毎回確かめる。

実物でも確かめた。`--sg-space-4` を 1rem から 1.25rem に変えると
`p-4` `px-4` `m-4` `size-4` `top-4` `left-4` `inset-4` などが報告される。

#### この検査が見逃す範囲

- **両方が生成しうるのに、候補一覧に入っていない組み合わせ。**
  名前空間とユーティリティ接頭辞の対応は手で持っている（`NAMESPACE_UTILITIES`）。
  **接頭辞を足し忘れた次元は黙って通る。** 段は自動で増えるが、
  **新しい次元を写像したら接頭辞を足す。**

  > **これは実際に起きた。** 最初の版は `ease` を持っておらず、
  > **`ease-in-out` の食い違いを素通りしていた**（自己レビュー F1）。
  > 見逃す範囲としてこれを書いた同じコミットで、既存の次元を4つ取りこぼしていた（教訓3）
- **変種（`sm:` `md:`）。** `--breakpoint-*` はクラスではなく変種を作るので、
  同名クラスの比較には現れない。**値がずれると適用される画面幅が変わるが検出できない。**
  現在は 40/48/64/80rem が素の Tailwind と一致しているが、**確かめたのではなく見ていない**
- **素の Tailwind の版が変わって既定値がずれた場合。** 検査は毎回両方をビルドするので
  **検出はできる**が、原因が我々の側とは限らない

### 決定 6-6: コンポーネントにはテストを添える。実ブラウザで、トークンの保証まで測る

> [Issue #110](https://github.com/shun2218-dev/sashigane/issues/110)。利用者の指示による。
> **「コンポーネントにバグが残らないことを保証しながら進めたい」**

#### なぜ実ブラウザか

保証したいことの中心は、**面の宣言が背景と前景を同時に切り替えること**である（決定5-12）。
決定5-12 が塞いだ穴は「**面を塗ったのに前景が浅いまま**」であり、
**塗るだけの道を無くすことが目的**だった。

**jsdom はこれを測れない。** CSS を解決しないので、「クラスが付いている」ことしか言えず、
「色が変わった」ことは言えない。**塗るだけの道が残っていても通る。**

そして [development-process.md](./development-process.md) はこう書いている。

> それを測るには、**手元で検出できない失敗**を CI が持つ必要がある
> （実ブラウザでの見え方、視覚回帰）。**いまは持っていない。**

**これはその穴の一部を埋める。**

#### 何を測るか

| 層 | 例 |
|---|---|
| props → 出力の写像 | `overlay` なら浮きが付く。`interactive` で属性が付く。`className` は追加であって置換でない |
| 設計の不変条件 | **Card が出すクラスの一覧が、決めたものと一致する**（原則5。塗りのクラスが混ざらない） |
| **トークンの保証** | 面の宣言で**背景が1段深くなる**こと、**前景も面から来る**こと、hover で1段深い文脈になること（決定5-12・5-13） |

**3つ目が本命である。**

不変条件を「`bg-` で始まるクラスが無いこと」ではなく**一覧の一致**で書いたのは教訓5 である。
禁止する形を並べると、並べ忘れたものを黙って通る。

#### 「通った」が「測っていない」でないことを確かめる

**CSS が読み込まれていること自体をテストにしてある。**
読み込まれていなければ以降の計算値は全部ブラウザの既定値になり、
**テストは通るのに何も測っていない**状態になる（教訓2）。

そのうえで**コンポーネントを3通り壊して、狙った件数だけ落ちることを確かめた。**

| 壊し方 | 落ちた数 |
|---|---|
| 面の宣言を外す | 10 / 11 |
| `overlay` の浮きを外す | 1 |
| hover の宣言を外す | 2 |

#### テストがあることを検査にする

**文書に書くだけでは守られない**（教訓3）。`check:component-examples` が、
展示ページと同じ場所で `<component>.test.tsx` の存在も見る。

#### 決めたこと

| | |
|---|---|
| 走らせ方 | `vitest.config.ts` の projects を2つに分ける。トークン層は Node、`packages/ui` は**実ブラウザ**（Playwright / chromium / headless） |
| CSS の作り方 | **利用側と同じ経路で作る。** 事前ビルドした CSS を読み込むと、テストは「そのとき生成された CSS」を見ることになり、**いま書いたクラスが解決するかを測れない** |
| CI の順序 | `build:tokens` を `test` より**前**に置く。コンポーネントのテストが生成物を読むため |

#### 含めなかったもの

**視覚回帰（画像の比較）。** 実ブラウザで計算値を測るのと、見た目を画像で比べるのは別である。
**計算値は「規則が守られているか」を測れるが、画像は「変わったか」しか言わない。**
必要かどうかは、コンポーネントが増えてから判断する。

### 決定 6-7: 押下は表現しない。無効は面を沈めて表す

> [Issue #112](https://github.com/shun2218-dev/sashigane/issues/112)。
> **決定5-13 が Phase 3 送りにした論点を、コンポーネントを書きながら解いた。**

#### 押下（`:active`）— 観測ゼロだった

決定5-13 はこう書いて保留した。

> `active` を「2段深い面」とすると `inset` で5段目を要求して成立しない。
> 例外規則は後から誰も消せなくなる。**押下の表現は Phase 3 で
> コンポーネントを書いてから決める。**

**測った。自作コードで `:active` を使っている箇所は4本とも0件である。**

そして [roles.md](./roles.md) の `bg-active`（i p h）は**押下ではなく選択状態**だった。

| | 実際の中身 |
|---|---|
| pylabo `.is-active` | 選択中のレッスン。`background: var(--bg-inset)` + accent の左境界 |
| holosphere `chipClass(active)` | フィルタの選択。`bg-fuchsia-400/15` = **淡い塗り** |

**どちらも既存の役割で書ける**（`data-sg-surface="inset"` と決定5-16 の淡い塗り）。

**押下は持たない**（原則7）。`bg-active` の保留も、**役割の記録が誤っていた**ことが分かったので解く。

> **観測は「無い」には答えない**（教訓7）。ここで言えるのは
> 「**押下の需要は観測されていない**」までである。
> 需要が出たときは、決定5-13 が挙げた「`inset` で5段目を要求して成立しない」問題に
> 正面から答えることになる。**そのときは観測ではなく設計で決める。**

#### 無効（`disabled`）— 面を沈めて表す

決定1-15 は不透明度を持たないと決め、無効状態はこう記録した。

> 無効状態 | 0.45 | pylabo | **未実装。観測1本なので持たない（原則7）**

**Button には無効がある。** 観測すると2本が書いていた。

| | 表現 |
|---|---|
| ichirizuka | `color: var(--faint)` + `cursor: progress` → **既存の役割で解けている** |
| pylabo | `opacity: 0.45` → **決定1-15 が塞いだ** |

**新しい役割は足さない。** 無効のときだけ `data-sg-surface="inset"` を宣言し、
文字を `text-faint` にする。

**面の仕掛け（決定5-12）に乗るのが要点である。** 背景と前景が同時に沈むので、
**どの variant でも同じ形になる**——塗りが残って「押せそうに見えて押せない」にならない。

#### `className` の衝突は解かない

`tailwind-merge` は入れない。**渡した class が消えないことはテストで固定してある**が、
同じ次元を上書きしたときにどちらが勝つかは生成 CSS の順序で決まる。

**実需要が出てから決める**（原則7）。困った例が出たときに、その例を根拠に入れる。

#### クラス名を組み立てない

`bg-${tone}` のように組み立てると **Tailwind が候補として読めず、CSS が生成されない。**
**しかもエラーにならない**ので、色の付いていないボタンがそれらしく表示される（教訓4）。

実際に一度そう書いて、`bg-accent` から `text-warning` まで**1つも生成されなかった。**
`compoundVariants` に **20 通りを書き下している。** DRY より静的に読めることを優先する。

#### focus は役割で描く。写像が欠けていた

`--sg-color-border-focus` は Phase 1 から**セマンティックとして存在していた**が、
**Tailwind アダプタに写像が無く、コンポーネント層から書く手段が無かった。**
押せるものを作るまで消費者が現れなかったためである。

**写像を足した**（`--color-border-focus`）。`outline-border-focus` として書ける。

ブラウザ既定のアウトラインに任せると、**トークンが唯一の正（原則1）から外れ、
利用側が自分で focus を書くことになる。**

##### `outline-none` を base に置かない

`outline-style: none` が残り、幅と色を足しても**輪郭が描かれない。**
計算値は width 2px / style none / color 継承色になり、**エラーは出ない**（教訓4）。
`focus-visible:outline-solid` で立てる。**実ブラウザのテストが捕まえた。**

#### 動かす対象を決める

`duration-200` だけを書くと **`transition-property` が既定の `all` になり、
outline-color まで遷移する。** focus の輪郭が一瞬遅れ、計算値も遷移前の値になる。

決定1-14 は「**動きは骨組み表示だけを持つ**」と決めており、全部を動かすのは行き過ぎである。
`transition-colors` で対象を絞る。

**これも実ブラウザのテストが捕まえた。** 一度「輪郭が付いていない」と読み違えかけたが、
クラスを1つずつ足して**`duration-200` が原因だと切り分けた**（教訓2）。

#### 塗らない variant の hover は面で作る

`solid` と `subtle` は塗りを1段ずらす（決定5-15）。
**`outline` と `ghost` には塗りが無い**ので、ずらす対象が無い。
**面の hover**（`data-sg-interactive`。決定5-13）を使う。

観測でも pylabo の枠ボタンは hover で色と境界を変えており、
**押せることが見た目から分かる必要がある。**
**塗る variant にだけ hover がある形にしない**——同一のランプ間の非対称は、
利用側から見ると「効くものと効かないもの」になる（教訓7）。

#### `outline` の境界は中立色にする

ランプの色にしない。観測でも ichirizuka（`var(--rule)`）も pylabo（`var(--line)`）も中立で、
**色はランプに、境界は面の骨格に属する。**
`border-danger` は書けるが**選ばなかった。** 書いておかないと、
次に触る人が「揃え忘れ」と読んで直してしまう。

#### hover は4種すべてに要る — **利用者の指摘で直した（2026-08-30）**

当初は `solid` に `hover:bg-*-strong`、`outline` と `ghost` に面の hover を付け、
**`subtle` だけ何も付けていなかった。** 「塗る variant」に分類しながら、
1段ずらす指定を `solid` にしか書いていなかったためである。

> outline や ghost の時にホバーしても見た目が何も変わらず
> ユーザー的にホバーしているのかどうかがわからない（後に subtle だけと判明）

**押せることが見た目から分からない状態は、variant を分けた意味を失わせる。**

##### `subtle` は自分で塗るので、面の hover と衝突する

面の hover は `background-color: var(--sg-color-deeper-bg)`（中立）を塗る。
自分で塗っている `subtle` にこれが当たると、**hover した瞬間に色味が消えて灰色になる**
（実測: 彩度 0.0564 → 0.0096）。

トークン層は `--sg-color-hover-*-subtle`（1段深い**色付き**）を持っており、
面の hover はこの変数も差し替える。**そこで hover のときだけ自分の塗りを優先する**と、
色付きのまま1段深くなる（実測: `oklch(0.2551 0.0564)` → `oklch(0.3245 0.0714)`）。

**面の hover は「面を持つ要素」向けの仕掛けであり、自分で塗る要素には片手落ちである。**
いまはコンポーネント側で回避しているが、**トークン層の側で分けるべきかもしれない。**
コンポーネントが増えて同じ回避が3つ目に出たら、そのとき決める。

##### 遷移を止めないと測れない

色は 200ms かけて動くので、**途中を読むと「変わった」も「色が残っている」も
両方たまたま通る。** 実際、遷移を止めずに書いたテストは
**塗りの再主張を外しても通っていた。** テスト側で遷移を切ってから測る。

#### size は持たない

観測は pylabo の `--lg` 1本のみ。原則7 に従い**最初は持たない。**

### 決定 6-8: 利用者に届く文面に、内部の参照を書かない

> 利用者からの指摘。
>
> > 「決定x-x」も「教訓x」も **AI 向けのドキュメントであって人間向けではない**ので、
> > いちいち記載する必要ない認識です

#### 届いていた

`packages/ui` の JSDoc は**型表としてドキュメントサイトに出る。**
例のソースも**そのまま表示される。** 測ったら、こうなっていた。

| 面 | 件数 | 誰が読むか |
|---|---|---|
| `packages/ui/src`（JSDoc・コメント） | 79 | **利用者** |
| `apps/docs/content`（MDX） | 11 | **利用者** |
| `apps/docs/app`・`components` | 19 | 維持する側 |
| `scripts/` / `docs/` | 313 / 676 | 維持する側 |

**番号だけ書かれても、読む側には辿る先が無い。**
番号の定義はこのリポジトリの `docs/` にあり、
レジストリ配信でコードを受け取った利用者は持っていない。

#### 決定

**利用者に届く面には、理由を平文で書く。**

| 面 | どうするか |
|---|---|
| `packages/ui/src` の **JSDoc** | 番号を書かない。**理由を平文で** |
| 同・**JSDoc でない普通のコメント** | 書いてよい。**型表に出ない**ので利用者に届かない |
| `packages/ui/src` の**例** | ファイル全体が表示されるので書かない |
| `apps/docs/content` の MDX | 書かない。**サイト内のリンクは張れる**ので、必要なら文章でつなぐ |
| **コミットメッセージ** | 番号を書かず、理由をそのまま書く |
| `scripts/` `docs/` `apps/docs/app` | **そのまま。** 維持する側が読むもので、番号の定義がある場所である |
| **テスト** | そのまま。利用者に届かず、根拠を書く場所としてはむしろ適している |

#### ファイルへの参照も書けない

**当初は「ファイル先頭に `docs/decisions.md` への参照を残す」案を出したが、退けた。**
利用者に問われて気づいた——**それはこのリポジトリが一度潰した穴と同じ形である。**

> Phase 2 で ichirizuka にコミットした `app/tokens.css` の先頭は
> 「規則と根拠は docs/decisions.md を参照」と書いていた。**配布先にその文書は無い。**（決定3-4）

`packages/ui/src` は原則6 で**利用側リポジトリへ落ちる。**
リポジトリ相対のパスは落ちた先で必ず壊れる。

**書くなら絶対 URL である**（決定3-4 が生成物に対して既に出している答え）。
そして**利用者にとって有用な URL は設計記録ではなく、そのコンポーネントの展示ページ**である。
コピーされたファイルを開いた人が知りたいのは「これは何で、どう使うか」であって、経緯ではない。

**いまは URL も置いていない。** レジストリ配信が動いていないので、
指す先の URL が確定していないためである。配信を作るときに、
`registry-item.json` の `docs` 欄と合わせて決める。

#### 検査にする

`pnpm check:public-language`。文書に書くだけでは守られない（教訓3）。
Badge・Separator・Table で同じことが起きる。

**JSDoc と普通のコメントを区別している**のが要点で、
「経緯を書くな」ではなく「**出る場所に書くな**」である。

### 決定 6-9: 塗りは宣言する。境界が識別を担う

> [Issue #117](https://github.com/shun2218-dev/sashigane/issues/117)。**利用者の指摘から出た。**
>
> > ボタン内のテキストカラーがダークテーマだと…問答無用で黒になりますが、
> > 濃い色のボタンの背景色と黒文字の相性があまり良くなくて単純にデザインとしてダサいです

#### 決定5-14 の観測表が、自分の出力を否定していた

| 組み方 | i | p | h | s |
|---|---|---|---|---|
| 塗り＝アクセント、文字＝**白** | — | ✓ | ✓ | ✓ |
| **明るい塗り＋暗い文字** | — | — | — | **1件も無い** |

**暗色モードが出していたのは、観測に1件も無い組み合わせだった。**

#### 原因 — 1つの役割が塗りと文字を兼ねていた

`--sg-color-accent` は `bg-accent`（塗り）と `text-accent`（**面の上の文字**）の両方である。
Tailwind の `--color-accent` は**両方のユーティリティを同じ値から作る**ので分けられない。

`colorText` は「面の上の文字が 4.5:1 を満たす最も浅い段」として解かれる。
暗色ではそれが明るい段（400）になり、**白が載らない**（3.11）。
1つの役割で兼ねている限り、どちらかが必ず割れる。

#### 決定: 塗りも宣言する

面は `data-sg-surface` で、hover は `data-sg-interactive` で宣言する。**塗りも同じ形にする。**

```html
<button data-sg-fill="accent">押す</button>
```

宣言が**背景・境界・文字を同時に**与える。**塗るだけの道は用意しない**（原則5 と同じ形）。

| | 解き方 |
|---|---|
| `fill` | **面にもモードにも依存しない。** ランプの明るい端が文字として成立する最も浅い段 |
| `onDeclaredFill` | その塗りに対して対比の高い端。**両モードとも明るい端になる** |
| `fillBorder` | 塗りが面から 3:1 離れていれば塗り自身。離れていなければ面から 3:1 を満たす最も浅い段 |
| `fillStrong` | 文字から遠ざかる向きへ1段。文字は明るい端なので**濃くなる** |

#### 境界が識別を担う — **利用者の提案**

> ボーダーだけ変えずに中の背景色だけ hover 時の色を変えるのでは解決しませんか？

**解決する。** WCAG の非文字要件は「**部品を識別できること**」であって、
それを担うのが塗りである必要はない。

これで**保証を1つも弱めずに済む。** 当初は「暗色の hover で 3:1 を割ることを認める」
としていたが、**取り下げた。**

| 全360色相の最悪 | |
|---|---|
| 塗りの上の文字 | **4.50**（hover 時 6.04） |
| 境界と面 | **3:1 以上**（全モード・全面） |

深い面では塗りだけでは届かない（暗色の surface で 2.56、inset で 2.03）ので、
**境界を面ごとに解いている。**

#### 退けた案

| 案 | なぜ退けたか |
|---|---|
| 塗り専用の役割を足す（`accent-fill` など10個） | **`bg-accent` は生成され続ける。** 塗りに使うと間違いなのに書けてしまう |
| 色を `@theme` から外し、`@utility` で1つずつ定義する | 大きい。**ただし `bg-accent` の footgun を消せる唯一の道**なので、[Issue #117](https://github.com/shun2218-dev/sashigane/issues/117) に残した |
| `@utility` で `bg-accent` だけ上書きする | **できない。** 同じ規則に2つ出て、テーマ由来が後に来て勝つ（実測） |
| 暗色の hover が 3:1 を割ることを認める | **要らなくなった。** 境界が識別を担う |

#### 測り方を2回間違えた

1. **同じ色相を360回測って「全360色相」と書いた。**
   `generatePalette` の引数は `H` で、`h` を渡していたので**同じパレットが返っていた。**
   NaN が出て初めて気づいた
2. **遷移の途中を読んで「hover が効いていない」と読み違えた。**
   色は 200ms かけて動く。**止めてから測る**

### 決定 6-10: 色は `@theme` に載せず、`@utility` で1つずつ出す

> [Issue #117](https://github.com/shun2218-dev/sashigane/issues/117) の残り。
> 決定6-9 で塗りを宣言に移したが、**`bg-accent` は生成され続けていた。**
> 塗りに使うと間違いなのに書けてしまう。

#### 数えた

`@theme` に色を1つ載せると、Tailwind は **23 個**のユーティリティを作る。

```
bg- text- border- border-t- border-x- ring- outline- divide- from- via- to-
fill- stroke- accent- caret- decoration- placeholder- shadow- inset-shadow-
ring-offset- text-shadow- inset-ring-   ＋ アルファ修飾子（bg-accent/50）
```

| | |
|---|---|
| 色の役割 | **53 個** |
| 生成されうるユーティリティ | **1219 個** |
| **実際に書かれていたもの** | **21 個** |

**意図していないものが桁で多い。** しかも決定3-2 が禁じたアルファ修飾子まで作られるので、
**検査で塞ぐしかなかった。**

#### 決定: 出さなければ塞ぐ必要がない

色は `@theme` に載せず、**`@utility` で1つずつ出す。** **85 個**になった（1219 → 85）。

| 役割 | 出すもの | なぜ |
|---|---|---|
| 文字（`default` `muted` `faint`、色つき文字） | `text-` | 文字である |
| マーク（`*-mark`） | `fill-` `stroke-` `border-` | 文字ではない（3:1）。アイコン・線・枠 |
| 境界（`border` `border-subtle` `border-strong`） | `border-` | 枠線 |
| focus の輪郭（`border-focus`） | `border-` `outline-` | 輪郭として描く |
| 淡い塗り（`*-subtle`） | `bg-` | 色のついた地 |
| 塗りの上の文字（`on-*`） | `text-` | 塗り／淡い塗りの上に載る |
| 強い塗り（`*-strong`） | `bg-` | 塗りの状態変化 |
| チャート系列（`chart-1..5`） | `fill-` `stroke-` `bg-` | 塗り・線・凡例 |
| グリッド線（`chart-gridline`） | `stroke-` `border-` | **線である。** 塗りには使わない |
| 連続（`sequential-*`） | `fill-` `bg-` | 色帯 |

**不透明な塗り（`bg-accent`）は出さない。** 塗りは `data-sg-fill` で宣言する（決定6-9）。

#### 構造で塞がったもの

**アルファ修飾子が生成されなくなった。** 決定3-2 が禁じ、検査で落としていたものが、
**そもそも作られなくなった。**

`check:component-classes` は**生成 CSS を読む**ので、もうアルファ修飾子を見られない。
検出器がそう報告した——**検査が「自分はもう機能していない」と言った**のは正しい。
ソースの側は `check:token-usage` が引き続き落とす。**書けてしまうことは変わらない**ためである。

#### 代償

**利用側が書けるユーティリティが、列挙したものに限られる。**
`ring-accent` を focus に使いたい利用者は、こちらが定義していないと書けない。

これが唯一の実質的な代償である。原則7 の「実需要のあるものだけ」と同じ判断で、
**必要になったら足す。**

#### 消しすぎは検査が捕まえる

出さなかったユーティリティを書いても**何も起きず、エラーも出ない**（教訓4）。
`check:tailwind-adapter` が **116 件**について「出るはず／出ないはず」を両方向で見る。

#### 時期

**リリース前に入れた。** 利用者もタグもまだ無いので壊れるものが無い。
後からだと `ring-accent` を使っていたコードが黙って効かなくなる。

### 決定 6-11: 利用者に届く面から内部の参照を落とし、名前を「デモ」に揃える

**利用者に見える文には決定番号を書かない。生成物のコメントも含む。**
**「サンプル」という呼び名は「デモ」に統一する。ただしファイル名と検査名は動かさない。**

| | |
|---|---|
| 対象 | 生成物（`packages/tokens/dist/*`）・ドキュメントサイトの画面に出る文・デモページの本文・**README** |
| 対象外 | JSDoc でないコメント、`scripts/`、`docs/`、`CLAUDE.md`、テスト |
| 検査 | `pnpm check:public-language`（対象を広げた。**`build:tokens` の後に走る**） |
| 呼び名 | 画面・URL は「デモ」（`/demo`）。`sample-page.html` と `check:sample-page` は据え置き |
| 旧 URL | **リダイレクトを置かない。** 理由は下記 |

#### なぜ生成物まで含めるのか

決定3-4 は生成物のヘッダに**絶対 URL** を入れることで、
「番号の定義はここにある」を解決したつもりでいた。

**解決していなかった。** 辿った先はこのリポジトリの和文の設計記録である。
レジストリ配信でコードを受け取った利用者にとって、
`/* spacing — 決定1-2 */` は**読める形になっていない。**

とくにテーマビルダーは、生成した `tokens.css` を**コピペさせるために画面に出している。**
利用者が自分のリポジトリへ貼るテキストに、こちらの内部番号が 31 箇所入っていた。

#### 開発の段取り（`Phase 3`）も同じ

**読む側には何段階あるのかも、いまどこなのかも分からない。**
しかも**進むたびに嘘になる**——実際、README は「Phase 1（トークン層）」のまま、
コンポーネントが2つある状態を指していた。

`check:public-language` が `Phase N` と `フェーズ N` を落とす。
**語そのものを禁じているのではない**——番号が付いた形だけを見ている。

#### 何を失うか

**経緯へ辿る道が生成物から消える。** これは意図した通りである。
理由が利用者に要るものなら平文で書けるはずで、
**平文で書けないなら、それは利用者向けの理由ではない。**

維持する側の経緯は、生成器のソース（`packages/tokens/src/output/*`）の
JSDoc とコメントに残っている。**そちらは配布されない。**

#### 検査が足りていなかった

`check:public-language` は `packages/ui` の JSDoc と MDX しか見ていなかった。
**サイトの実装と生成物とデモページは対象外だった**ため、0 件で緑のまま残っていた。

対象を4種に広げ、**画面に出る文はコメントを落としてから見る**形にした。
陰性対照も 4 件から 7 件へ増やしてある（教訓2）。

#### 旧 URL にリダイレクトを置かない

`/sample` は 404 になる。**いま実害が無いのは、サイトをまだ配信していないため**である
（Issue #101 で、最初のリリース直前まで見送っている）。
外から張られたリンクも、検索の索引も存在しない。

**配信を始めた後に同じ変更をするなら、答えは変わる。**
そのときはリダイレクトが要る。**「不要」ではなく「まだ不要」である。**

#### ファイル名を動かさなかった理由

`apps/docs/src/sample-page.html` と `check:sample-page` は、
**この決定文書と実験記録が名指しで参照している。**
名前を揃えるために記録を書き換えると、**記録の側が事実でなくなる。**

利用者に見えるのは URL とナビゲーションのラベルだけなので、そこだけを揃えた。
`/demo` が `src/sample-page.html` を読むことは `app/demo/route.ts` に書いてある。

### 決定 6-12: プレビュー用 CSS は展示の中だけに効かせる

**別ビルドの出力を同じページに載せるなら、片方を範囲で閉じ込める。**

| | |
|---|---|
| 方法 | ビルド後にセレクタを `[data-sg-preview]` の下へ書き換える（`scripts/scope-preview-css.mjs`） |
| 対象の層 | `@layer base` / `@layer utilities` / `@layer properties` |
| 触らないもの | 層の外の変数宣言（`:root`・`[data-sg-surface]`） |

#### 何が起きていたか

ドキュメントサイトには Tailwind のビルドが2つある。
サイト外枠（fumadocs）のものと、コンポーネントのプレビュー用のものである。
アダプタを外枠に入れるとビルドが落ちるので分けてある（決定6-4）。

**分けた出力が同じ `@layer utilities` に並ぶと、後から読み込む方が勝つ。**
Tailwind が変種を正しい順に並べられるのは**1つのビルドの中だけ**である。

結果、外枠の `.md\:hidden` にプレビュー側の `.flex` が勝ち、
**画面幅で隠れるはずのモバイル用バーが 1024px でも表示されたまま**
高さ 0 の枠から溢れ、ページ上部が切れて見えていた。
右端の目次も同じ理由で 16px の帯として残っていた。

プレビュー側の preflight（`*` と `html` への初期化）も外枠に当たっていた。

#### 退けた案

| 案 | 退けた理由 |
|---|---|
| 外枠の走査対象に fumadocs のソースを足す | `@source` が pnpm の symlink 越しに効かず、実体パスでも出力が変わらなかった |
| ビルドを1つにする | `--*: initial` を外すことになる。**逃げ道を塞いだ意味が消える**（原則3） |
| 展示を iframe に入れる | 隔離はできるが、高さの同期とテーマの受け渡しを持ち込む。決定6-4 で一度捨てた形である |
| 並び順で解く（プレビューを先に読む） | Next.js が自分の CSS を後ろに置くので、こちらから順序を決められない |

#### トークンの読み込みは外枠に任せた

`preview.css` は**トークンの変数を持たない。** 外枠が `public/tokens.css` を読むので、
二重に持つ意味が無い。

**依存が暗黙になる。** 外枠からその1行が消えると展示は色を1つも持たない状態になり、
`--sg-*` が未定義になるだけなので**エラーは出ない**（教訓4）。
`check:component-classes` は生成 CSS を読むので発火せず、
コンポーネントのテストは実ブラウザだが展示ページを見ていない。

`check:component-examples` に**落ちる場所を1つ置いた。**
どちらか一方が `tokens.css` を読んでいることを見る。

#### 副作用

閉じ込めたことで**展示の中ではプレビュー側の特異度が1段高くなる。**
これは意図した向きである——展示の中はプレビューが正しい。

さらに、展示の中の書体が `--sg-text-body-family` に揃った。
以前は外枠の `body` の指定が勝っており、**トークンの書体が見えていなかった。**

#### 0 件を成功にしない

`scope-preview-css.mjs` は、変換が 1 件も起きなければ**落ちる。**
ビルドの出力構造が変わると静かに素通りするため（教訓2）。
変換そのものにも陽性・陰性の対照を 9 件持たせてある。

**さらに結果の側からも見る。** 変換が走ったことと、漏れが無いことは別である。
限定対象の層に目印の付かないセレクタが1つでも残っていれば落とす——
`scopeOne` の場合分けから漏れた形が、そのまま外枠への漏れになるためである。

### 決定 6-13: 検索は既定のまま入れ、引けることを検査する

**索引はページから作り、設定は足さない。ただし「引けること」は機械で見る。**

| | |
|---|---|
| 経路 | `apps/docs/app/api/search/route.ts`。`createFromSource(source)` の1行 |
| 索引 | `source`（MDX のページ木）。**手で持たない** |
| 語の切り出し | 既定（`multilingual`）。**言語を指定しない** |
| クライアント | 既定。`fetch` で `/api/search` を叩く。`RootProvider` に渡す設定は無い |
| 検査 | `pnpm check:docs-search`。**apps/docs のビルドが先に要る** |

#### 言語を指定しない

既定の切り出しは多言語向けで、和文もそのまま扱える。
**実測した**——「トークン」で `/docs` が、「Button」で `/docs/components/button` が引ける。

言語を指定すると**その言語用の切り出しに固定される。**
このサイトは和文と英字が混ざるので、固定する理由が無い。

#### なぜ検査するのか

**検索は静かに壊れる**（教訓4）。
索引が空でも経路は 200 を返し、画面には「見つかりません」と出るだけである。
**入力に対して結果が無いことと、索引が空であることは、見た目で区別がつかない。**

索引はページから作っているので、ページの構造化データが出なくなると
中身だけが消える。**型は通る。**

検査は3つを見る。

1. 和文で引けること
2. **入れ子のページ**が引けること
3. **無い語では 0 件になること**

3 が要る。1 と 2 だけだと**全件を返す壊れ方**を通してしまう。
1・2 と 3 は互いの対照になっており、**どちらか片方だけが成立する状態は作れない**（教訓2）。

**両方の壊れ方で落ちることを確かめてある。** 経路を消すと 404 で落ち、
索引を空にすると「0 件」で落ちる。

#### 引く語を固定しない

2 は**内容から取る。** 最初は `Button` と書いていたが、
**Button を消したら、検索が壊れていなくても落ちる。**
コンポーネントは増減する段階なので、検査対象がその都合で動く形にしない。

`content/docs/components/` の最初のページを読み、その `title` で引いて
そのページの URL が返ることを見る。**ページが増減しても追随する。**

和文の側は索引ページ（`/docs`）に当てている。**こちらは消えない。**

#### 静的書き出しはできなくなる

この経路はリクエスト時に動く。`output: 'export'` に切り替えるなら、
索引を静的に配る形へ替える必要がある。**いまは切り替える予定が無い**（Issue #101）。

### 決定 6-14: 要素の差し替えは `asChild` で行う

**器が要素を作らず、クラスと属性を子へ移す。** `<Button asChild><a/></Button>` は `<a>` 1つになる。

| | |
|---|---|
| 方式 | `asChild`（Slot 方式） |
| 実装 | 自前。`packages/ui/src/internal/slot.tsx` |
| 対象 | Button と Card。**持つなら、以後もこの形で持つ** |
| `disabled` との併用 | **型で塞ぐ。** 実行時にも投げる |

#### 観測

holosphere は **Button のクラス文字列を `<Link>` へ書き写していた。** 11〜13 箇所ある。

```
inline-flex items-center rounded-full px-3 py-1 text-sm   ← Button.ghost とほぼ同じ
```

Button が `<a>` になれなかったので、**見た目だけを手で複製していた。**
Card の側は `as?: ElementType` を持っており、`DashboardCard` が `as="article"` を使っている。

**器を差し替える需要は、4本の中で最も測れる形で出ている。**

#### なぜ `as` ではなく `asChild` か

| | `as` / `render` | `asChild` |
|---|---|---|
| 任意の要素になれる | ○ | ○ |
| **外から包まれる形に効く** | **×** | **○** |
| 多態の型付け | 難しい | 子の型がそのまま効く |
| 依存 | 不要 | Slot が要る（自前） |

決め手は2行目である。pdf-merge-app の `asChild` 3 件は
**Dialog の trigger / close が Button を包む**形だった。
`as` はこの向きに効かない——**包む側が props と ref を子へ渡す**必要があるためである。

Dialog も Tooltip もいずれ要る。**同じ仕組みで両方向を解ける方を選ぶ。**

#### radix の Slot を入れなかった

`@radix-ui/react-slot` を足せば同じことができる。入れていない。

**このファイルは配布先へ落ちる**（原則6）ので、落ちた先で依存が1つ増える。
短く書けるものに依存を足す理由が無い。

#### `disabled` と併用できない

押せない状態は `button` 要素の機能である。リンクには無い。

`disabled` を `a` に付けても**エラーは出ず、何も起きない**（教訓4）。
沈んだ見た目のまま押せてしまうので、
**「押せそうに見えて押せない」の逆**という、より悪い状態になる。

型で塞ぎ、**型を持たない側から来る場合に備えて実行時にも投げる。**
押せない状態が要るなら `button` のままにする。
リンクを押せなくしたいなら、**リンクを出さないのが正しい。**

#### 子は1つだけ

`cloneElement` で移すので、子は要素1つでなければならない。
**要素でない／複数ある場合は投げる。** 黙って通すと、
クラスも属性もどこにも付かないまま「それらしく」描画される。

**複数の中身は、その要素の内側に入れる。**
外側を `div` で包むと**押せない `div` がボタンの見た目になる**ので、
エラーメッセージにその一文を入れてある。

#### 移すときの規則

既定は**子が勝つ。** 子は使う側が直接書いたもので、こちらの既定より意図が強い。
例外は3つだけである。

| props | 扱い |
|---|---|
| `className` | 連結する。こちらが先、子が後 |
| `style` | 混ぜる。同じ鍵は子が勝つ |
| 行事（`onClick` など）・`ref` | **両方に配る。片方を捨てない** |

行事は**子を先に呼ぶ。** 子の側で `preventDefault` した結果を、こちらが見られる。

#### `type` と `disabled` は自分で描くときだけ渡す

`asChild` の子は `a` かもしれず、どちらも意味を持たない。
**渡してもエラーにならない**ので、付いているつもりのまま何も起きない。

#### 「全部が持つ」とは決めていない

`asChild` を**どのコンポーネントが持つべきか**は機械では決められない。
`Separator` に要るかは自明でなく、`Table` にはおそらく要らない。

決めたのは**形**である。`check:component-examples` が見ているのも形だけで、
「持つこと」は見ていない——`asChild` を受け取りながら `cloneElement` を自前で呼ぶと、
移し方が2つになる。**2つになったことは、壊れるまで誰も気づかない。**

はじめは決定の表に「以後のコンポーネントも同じ形にする」と書いていた。
**書いただけだった**（自己レビュー M1）。教訓3 がそのまま当たっていたので、
文言を「持つなら」に直し、機械で見られる部分だけを検査に移した。

#### 測っているもの

props の写像ではなく **DOM の形**を測る——
「`button` の中に `a` が入る」形になっていないことは、計算値では見えない。

**壊して確かめた。**

| 壊し方 | 落ちた件数 |
|---|---|
| `asChild` を無視して常に器を描く | 3 |
| 行事を片方だけにする | 1 |
| `ref` を子だけに配る | 2 |
| `Slot` を使わずに書く | 検査が 1 件で落ちる |

### 決定 6-15: カードの中は複合コンポーネントで分ける

**見出し・補足・本文・操作を区画に分ける。区画は面も色も持たない。**

| | |
|---|---|
| 区画 | `CardHeader` / `CardTitle` / `CardDescription` / `CardBody` / `CardFooter` |
| 面を宣言するもの | **器（`Card`）だけ** |
| 見出しの既定 | `h3`。`asChild` で差し替える |
| 器の役割 | 区画を縦に並べて間を空ける（`flex flex-col gap-surface`） |
| 画像の区画 | **持たない。** 理由は下記 |

#### 観測

holosphere の `DashboardCard` は
「**見出し・ⓘ・補足の塊を、17回手書きしたものを1箇所へまとめた**」と書いてある。

区画に分ける需要は、4本の中で最も回数の多い形で出ている。

#### 観測と違う形を選んだ

**holosphere は props（`heading` / `sub` / `tooltip`）で受けていた。**
こちらは複合コンポーネントにした。理由は利用者の言葉である。

> props で書きまくるのは逆にレンダリング後の形のイメージがしづらくなる気がする

観測は「その形もありうる」を示すだけで、**選ばせるものではない**（決定6-16）。

| | props | 複合 |
|---|---|---|
| 使う側の短さ | ○ | × |
| **描画後の形の見えやすさ** | × | **○** |
| 見出し行に操作を足す | props が増える | そのまま置ける |
| 区画の入れ忘れ | 起きない | 起きる（**検査できない**） |

最後の行が代償である。`CardHeader` を書かなくても崩れないので、
**書き忘れても誰も言わない。**

#### 区画は面を宣言しない

面の宣言が入れ子になると、**段が意図せず深くなる。**
区画は並べ方と文字の役割だけを持ち、色は1つも書かない。

テストが `[data-sg-surface]` の数を数えている。
**壊して確かめた**——区画に面を宣言させると 1 件落ちる。

#### 見出しの深さを決め打ちしない

カードがページのどこに置かれるかで正しい深さは変わる。
既定を `h3` に置き、`asChild` で差し替えられる形にした。

**`div` にして見た目だけ整える道は取らない。** 見出しでないものを見出しに見せると、
読み上げの順序から消える。

#### 操作は下端に寄る

高さの揃った並びに置いたとき、**本文の長さが違っても操作の位置が揃う。**
揃わないと、並べたカードの下端がばらついて読みにくい。

#### 画像の区画を持たない

画像はそのまま中身として置ける。**器の余白いっぱいまで広げる**区画を持っていない。

理由は観測ではなく設計である（決定6-16）。
**広げ方を決めていない**——縦横比、角の丸め、上端だけか両端か。
決めずに口だけ用意すると、**利用側ごとに違う広げ方が生まれる。**

余白を器ではなく区画の側に持たせれば広げられるが、
**区画を使わない書き方から余白が消える。** いまの書き方を壊す変更になるので、
広げ方を決めるときに一緒に考える。

### 決定 6-16: 実需要は観測4本の中の出現回数ではない

**観測は「需要がある」の裏づけに使う。「観測ゼロ」を入れない理由にしない。**

| | |
|---|---|
| 実需要 | 一般に UI を作るうえでの需要 |
| 観測4本の役割 | **裏づけ。** 需要の定義ではない |
| 「3回以上書き直したもの」 | **最初の5個を選ぶための基準。** 選んだものが何を持つかの基準ではない |
| 入れないと決めるとき | **設計上の理由だけを書く。** 「観測に無い」は理由にならない |
| 利用者の申告 | **観測より新しい証拠。** 観測の後ろに置かない |

#### なぜ決めるのか

原則7 の「実需要のあるものだけ」を、**観測4本での出現回数**と読み替えていた。

ボタンのローディング表示を「観測ゼロ」を先頭に置いた形で利用者に示し、
**同じ指摘を2度受けた**（agent-failures.md の 2026-08-30）。

> 私が伝えた需要とは観測対象のサイトやアプリ内の話ではなく、
> **一般的にサイトやアプリを作る上での需要を指しています。**

4本は**過去に書かれたもの**であり、利用者は**いま作ろうとしているもの**を知っている。
どちらが新しい証拠かは明らかである。

#### 教訓7 が発火しなかった

教訓7 は 2026-08-29 に同じ形の失敗から書かれている。
ただし文面が「**役割を落とすときは**」で範囲を切っており、
**コンポーネントが何を持つかには届いていなかった。**

範囲を広げ、原則7 の側にも「実需要とは何か」を書いた。

#### 観測をやめるわけではない

観測は引き続き取る。**取る場所が変わっただけ**である。

| 使ってよい | 使ってはいけない |
|---|---|
| 「17回手書きされた」→ 入れる裏づけ | 「0件だった」→ 入れない理由 |
| どの形で書かれていたか（props か複合か） | その形以外を退ける理由 |

実際、この直後に決める Card の内部構造は**観測と違う形になった。**
観測は holosphere が props（`heading` / `sub`）を選んだことを示していたが、
**利用者は描画後の形が想像しにくいことを理由に複合コンポーネントを選んだ。**
観測は「その形もありうる」を示すだけで、**選ばせるものではない。**
