# 教訓

[agent-failures.md](./agent-failures.md) に記録した失敗から導いた規則。
**すべてこのリポジトリで実際に起きたことに由来する。**

このファイルは CLAUDE.md から `@` で参照され、毎セッションのコンテキストに入る。
**教訓を増やすときは、先に agent-failures.md に失敗を記録してから、ここに足す。**


### 1. 生成規則を書いたら、必ず実行して出力を決定文書と照合する

言葉の上で筋が通ることと、コードが期待どおり動くことは別である。
「規則から値を導く」と主張するプロジェクトで、値を目視確認せずに規則を書いてはならない。

### 2. 検証は生の出力を見る。フィルタした結果だけで結論を出さない

「該当なし」を見たら、まず**フィルタが正しいか**を疑う。
対象が存在しないことと、フィルタが外れていることは区別がつかない。

**「何も検出されなかった」は成功ではなく、検査が機能していない可能性を含む。**
ゼロ件の結果には、意図的に該当するケースを1件作って検査が発火することを確かめる。

（実際、スケールの期待値検査はわざと規則を壊して発火を確認した。同じことを常に行う）

**検査が「通す」と約束したものが、実際に通ることも確かめる。**
発火する側の対照だけを持っていると、**通すはずの書き方が落ちるようになっても気づけない。**
実際、`check:token-usage` が文書で案内していた逃げ道は一度も機能していなかった。

**「手元で緑」と「検査された」も別である。** 検査対象が追跡下のファイルなら、
`git add` していないファイルは検査に入らない。**緑は「対象が無かった」かもしれない。**

**「出なかった」も同じである。** 試したものが生成されなかったとき、
**「できない」ではなく「自分の書き方が壊れている」を先に疑う。**
同じ仕組みで出るはずのものを1つ並べて書き、**仕組み自体が動いていること**を確かめる。
実際、エスケープの書き間違いを「この名前空間は小数を受け付けない」と読み違え、
その結論で Issue を1本立てて決定文書にも書いた。

**尺度を1つ選んで閾値と比べただけの結論も、これに当たる。**
その閾値が**何を測るために決められたか**を確認する。
別の問いのために決めた定数を借りて比べても、答えにはならない。

数値が出て、比べる定数がリポジトリの中にあると、そのまま比べれば答えだと思い込みやすい。
**測れるもので測っただけの結論を、問いへの答えとして扱わない。**

### 3. 機械的に検査できるものは、文書ではなく検査にする

規則を文書に書いた本人が、同じコミットの中でその規則を破った実例がある。
**「書いたから守られる」は成立しない。**

文書は機械化できないものにだけ使う。文書は最後の手段であって、最初の手段ではない。

### 4. 静かに失敗するものを疑う

**遷移の途中の計算値を読まない。** 器が `transition-*` を持つなら、
描画直後の1回読みは補間の途中に当たりうる。同じ色でも書き方が変わるので
（`oklch()` が `oklab()` になる）、文字列の比較が落ちる。
**色を比べるなら `expect.poll` で待つ。**

**手元で緑は「速さが違えば別」を含まない。** 3度踏んで、3度目は CI だけで落ちた
（agent-failures.md の 2026-08-30）。

**待っても足りない。** 別々に描いた2つの木は別々に落ち着くので、
**2つの計算値の一致を条件にしない。**
一致を測りたいなら、一致の根拠になっている宣言（属性）を測る。

**hover を測るなら、hover していない状態を自分で作る。**
テストは1つの文書に描き続けるので、**前のテストのポインタが乗ったまま**になる。
`before` を読む前にポインタを外す。**既定に頼らない。**

3つとも同じ形である——**読む時点の状態を、自分で決めていない。**

**境界は色だけで測らない。** preflight が `border: 0 solid` を当てるので、
**幅 0 の境界にも色が付く。** 色だけを見ると、境界を外しても通る。
実際、Badge で踏んで他を見に行ったら、**Spinner は輪を消しても全部通る状態だった。**


**状態ごとの見た目だけを測ると、移り変わりが写らない。**
状態で器の有無を変えると、**React がその中身を作り直す。**
入力中に状態が入れ替わる場所では、**打っている最中にフォーカスが外れる。**
見た目には何も出ず、文字が入らなくなるだけである。
静止した状態を並べて撮るのではなく、**変わる過程を測る。**

設定ファイルの意味論の誤りは、動かしてもエラーにならない。
権限プロンプトが余分に出るだけで、誰も気づかない。

**エラーにならない仕組みほど、意図どおり動いていることを能動的に確かめる。**

### 5. 検査は「禁止するもの」ではなく「許可するもの」を列挙する

禁止リスト方式は、リストに無いものを黙って通す。
**列挙し忘れたケースがあることに、検査が緑である限り気づけない。**

同じ日に、独立性検査では許可リスト方式（相対パスと `node:` だけ許可）を採り、
生成物検査では禁止リスト方式を採って実際に見逃した。判断を揃える。

許可リストにできない場合は、**検査が原理的に見逃す範囲を検査自身のコメントに書く。**

### 6. 決定済みと推測しない。根拠が書かれていないものは未決定として扱う

指示の中に固有の語（ブランチ名、ツール名、ディレクトリ名）が出てきても、
**それがその領域の決定を意味するとは限らない。**
書かれているのは往々にして、より狭い1点だけである。

**リポジトリ自身の文書も同じである。** `@` で毎セッション読み込まれる文書に
書いてあっても、**[decisions.md](./decisions.md) に根拠が無いものは未決定として扱う。**

> **この一段はもともと無かった。** 文面は「指示の中に」で範囲を切っており、
> 自分たちの文書に書いた規則には届いていなかった。
> 実際、`development-process.md` の「Storybook のストーリー3状態」を
> 決定済みとして扱い、その道具を前提に Phase 3 の計画を立てた。
> **教訓は存在したのに発火しなかった**（agent-failures.md の 2026-08-30）。

着手前に「この領域で決まっていないことは何か」を列挙し、
決まっていないものは決定として扱わない。

**判断の経緯を説明するとき、存在しなかった思考を再構成しない。**
「検討していない」が答えなら、そう答える。
後付けの理屈は原因を隠し、同じ失敗を再発させる。

### 7. 観測は「需要がある」には答えるが、「無い」には答えない

観測対象は**デザインシステム無しで書かれた実装**である。
そこに無いものは、**そのプロジェクトの事情であって設計の答えではない。**

**「実需要」は観測4本の中での出現回数ではない。**
一般に UI を作るうえでの需要を指す。観測はその裏づけに使う道具であって、
**需要の定義ではない。**

> **この一段はもともと無かった。** 文面は「役割を落とすときは」で範囲を切っており、
> **コンポーネントが何を持つか**には届いていなかった。
> 実際、ボタンのローディングを「観測ゼロ」を先頭に置いた形で利用者に示し、
> **同じ指摘を2度受けた**（agent-failures.md の 2026-08-30）。
>
> **利用者の申告は観測より新しい証拠である。** 観測の後ろに置かない。

「4本にモーダルが無い」は「モーダルの浮きを持つべきでない」を意味しない。
**生成コード（shadcn など）は「過去の実装」ですらない。**

原則2 の「値のソースにしない」は値だけの話ではない。
**何を持つかの線引きにも同じことが当たる。**

**役割を落とすときは、先に「この役割が無いと利用側は何を書くのか」に答える。**
答えが「書けない」なら、落とす理由は観測ではなく設計でなければならない。
とくに逃げ道（プリミティブ参照・任意値記法・素の数値・アルファ）を塞いだ後は、
**役割が無いことが、そのまま書く手段が無いことになる。**

**規則が同一のランプ間で非対称を作らない。** 非対称は利用側から見ると逃げ道の有無になる。

### 8. 選択肢を出すとき、利用者が挙げていない軸で優劣をつけない

「依存が減る」「構成が単純になる」は**こちらが持ち込んだ価値**である。
**利用者が挙げた要件だけで比べる。** 足したい軸があるなら、
**軸として採るかどうかを先に聞く。**

自分の軸で優劣をつけた比較表は、利用者が自分の要件で判断できない形になる。
**要件を1つ勝手に足すと、選択肢を狭めたことに自分では気づけない。**

**調べた結果その軸が不要だと分かったら、比較表から外す。**
残っていると判断の重みがそこに残り続ける。
